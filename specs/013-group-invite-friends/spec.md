# Feature Specification: 邀請好友加入組團（Invite Friends to Join a Group）

**Feature Branch**: `[013-group-invite-friends]`

**Created**: 2026-09-07

**Status**: Draft

**Input**: User description: "開團管理介面，團長可以發送邀請給自己的好友加入組團"

## Clarifications

### Session 2026-09-07

- Q: 受邀好友接受邀請時，若團設有通關密碼，邀請是否讓其略過密碼直接加入，還是仍須驗證密碼正確？ → A: 略過密碼直接加入——受邀視同團長已親自授權，密碼保護僅適用於一般（非受邀）加入路徑，不影響邀請這條入口。
- Q: 受邀好友按下「接受」時若團剛好已達人數上限，這筆邀請本身應該變成怎樣？ → A: 邀請維持「待回覆」不變（好友可日後再次嘗試接受），並額外通知團長「這次接受嘗試因額滿而失敗」，讓團長可主動處理（例如調高人數上限）。
- Q: 團長送出邀請後、好友回應之前，若雙方的好友關係被解除，這筆待回覆邀請該如何處理？ → A: 自動失效——好友關係解除的當下，該筆待回覆邀請自動結束，對方之後點擊通知只會看到邀請已失效，無法再接受加入。

### User Story 1 - 團長從好友列表發送邀請 (Priority: P1)

我是團長，我希望能在自己的開團管理頁面直接從我的好友列表挑選好友，發送邀請請他們加入這個團，而不必請對方自己去搜尋組團編號或等我口頭告知。

**Why this priority**：這是本功能存在的核心價值——沒有「送出邀請」這個動作，後續的接受/查看狀態都無從談起。

**Independent Test**：團長於管理頁面的邀請區塊選擇一位好友並送出邀請，驗證系統成功記錄這筆邀請，且不會重複發送給同一位仍在等待回覆的好友。

**Acceptance Scenarios**:

1. **Given** 團長已登入會員身分建立此團，且好友列表中有一位尚未加入本團、也沒有待處理邀請的好友, **When** 團長對該好友送出邀請, **Then** 系統成功建立一筆待處理的邀請紀錄。
2. **Given** 團長已對某位好友送出一筆待處理中的邀請, **When** 團長嘗試再對同一位好友送出邀請, **Then** 系統拒絕重複發送，並告知該邀請已在等待回覆中。
3. **Given** 某位好友已經是本團的現有成員, **When** 團長查看好友列表的邀請區塊, **Then** 該好友 MUST 清楚標示為「已在團內」，且不可再對其發送邀請。

---

### User Story 2 - 好友接受或拒絕邀請 (Priority: P2)

我收到朋友傳來的組團邀請通知，我希望能直接點擊通知查看是哪個團的邀請，並選擇接受（直接加入）或拒絕，而不必自己再去搜尋組團編號。

**Why this priority**：邀請送出後，若受邀者無法方便地回應，這個功能就只完成一半——但即使沒有這條，團長仍可用既有的「分享組團編號/連結」方式讓對方手動加入，因此優先度次於送出邀請本身。

**Independent Test**：受邀好友收到邀請通知後，分別測試「接受」使其成為該團成員，以及「拒絕」使邀請結束但不加入，兩條路徑互不影響。

**Acceptance Scenarios**:

1. **Given** 我收到一則尚未處理的組團邀請通知, **When** 我點擊該通知, **Then** 系統導向可查看邀請詳情（團名、邀請人）並可選擇接受或拒絕的畫面。
2. **Given** 我選擇接受一則組團邀請，我目前未活躍於任何其他團、且該團尚未額滿（無論該團是否設有密碼）, **When** 我確認接受, **Then** 我成為該團的正式成員，可如同一般加入者查看賽程與戰績。
3. **Given** 我選擇接受一則組團邀請，但該團設有通關密碼, **When** 我確認接受, **Then** 系統 MUST 直接讓我加入，不要求我輸入通關密碼——受邀視同團長已親自授權，密碼保護僅用於一般（非受邀）加入路徑（Clarifications Q1）。
4. **Given** 我選擇拒絕一則組團邀請, **When** 我確認拒絕, **Then** 該邀請結束、我不會加入該團，且我的通知列表清楚反映此邀請已被我拒絕。

---

### User Story 3 - 團長查看已發送邀請的狀態 (Priority: P3)

我是團長，我希望能在管理頁面看到我對每位好友發送的邀請目前是待回覆、已接受還是已拒絕，這樣我才知道還可以再邀請誰、不必自己一一詢問。

**Why this priority**：這是錦上添花的可視性功能——即使沒有這條，團長仍可透過查看輪替名單得知誰已加入，只是無法區分「還沒回應」與「拒絕了」。

**Independent Test**：團長對三位好友分別送出邀請，其中一位接受、一位拒絕、一位尚未回應，驗證管理頁面的邀請區塊正確顯示三種不同狀態。

**Acceptance Scenarios**:

1. **Given** 團長已對數位好友送出邀請，狀態各異（待回覆／已接受／已拒絕／已失效）, **When** 團長開啟管理頁面的邀請區塊, **Then** 每位受邀好友旁 MUST 清楚顯示其目前的邀請狀態。
2. **Given** 某位好友先前拒絕了邀請, **When** 團長想再次邀請該好友, **Then** 系統 MUST 允許重新送出邀請（拒絕不永久封鎖再次邀請）。
3. **Given** 某位受邀好友嘗試接受邀請，但當下團已額滿而接受失敗, **When** 該次失敗發生, **Then** 團長 MUST 即時收到通知，得知這位好友的接受嘗試因額滿而失敗（Clarifications Q2）。

---

### Edge Cases

- 團長送出邀請當下，該團人數尚未額滿，但受邀好友點擊「接受」時團已滿額——接受動作 MUST 失敗並清楚告知已額滿，不得讓成員數超過上限；該筆邀請 MUST 維持待回覆狀態（好友可日後再次嘗試接受），且系統 MUST 通知團長這次接受嘗試因額滿而失敗（Clarifications Q2、FR-013）。
- 受邀好友點擊「接受」當下，已是另一個團的活躍成員（一人僅能同時活躍於一個團的既有規則）——接受動作 MUST 失敗並清楚告知需先離開目前的團。
- 團在受邀好友回應之前被解散——受邀好友點擊該通知/嘗試接受時，MUST 清楚告知此團已不存在，不得誤導其成功加入一個已不存在的團。
- 團長嘗試邀請一位其實還不是好友關係的會員——MUST 被拒絕，本功能的邀請對象僅限於已確立的好友關係（好友申請/搜尋非本功能範圍）。
- 開團時未以會員身分建立（匿名建團）——團長沒有對應的會員好友清單，管理頁面 MUST NOT 顯示邀請好友功能（見 Assumptions）。
- 受邀好友在邀請仍待回覆時，自行透過其他管道（組團編號、連結）先行加入了該團——該筆邀請 MUST 視為已無意義，不得再要求對方重複處理，管理頁面應反映其已在團內。
- 邀請仍待回覆期間，團長與該好友的好友關係被解除（任一方主動解除）——該筆邀請 MUST 自動失效，受邀者之後點擊該通知/嘗試接受 MUST 被告知邀請已失效，不得完成加入（Clarifications Q3、FR-014）。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系統 MUST 讓以會員身分建立本團的團長，從自己已確立的好友關係中挑選一位或多位好友發送組團邀請。
- **FR-002**: 系統 MUST NOT 允許團長邀請非好友關係的會員（僅限好友列表內的對象）。
- **FR-003**: 系統 MUST 阻止對同一位好友重複發送「仍待回覆中」的邀請——同一位好友同一團同時最多僅能有一筆待處理邀請。
- **FR-004**: 系統 MUST 阻止對已是本團現有成員的好友發送邀請，並於好友列表清楚標示其已在團內。
- **FR-005**: 受邀好友 MUST 能即時收到邀請通知（沿用既有通知機制），並可從通知直接前往可查看邀請詳情、選擇接受或拒絕的畫面。
- **FR-006**: 受邀好友選擇「接受」時，系統 MUST 依現行加入團的既有規則（人數上限、一人同時僅能活躍於一個團）判斷是否成功加入，任何一項不符 MUST 清楚告知原因且不得完成加入。
- **FR-007**: 受邀好友接受邀請時，系統 MUST 讓其略過該團的通關密碼直接加入，不要求輸入密碼——受邀視同團長已親自授權，密碼保護僅適用於一般（非受邀）加入路徑（Clarifications Q1）。
- **FR-008**: 受邀好友選擇「拒絕」時，系統 MUST 將該邀請結束，不將其加入該團，且 MUST NOT 阻止團長未來再次邀請同一位好友。
- **FR-009**: 團長 MUST 能於管理頁面查看自己對每位好友發送的邀請目前狀態（待回覆／已接受／已拒絕／已失效）。
- **FR-010**: 系統 MUST 僅將邀請通知投遞給實際受邀的那位好友，MUST NOT 讓其他會員看到或收到不屬於自己的邀請。
- **FR-011**: 若團在受邀好友回應前已被解散，系統 MUST 讓後續查看/接受該邀請的操作明確告知團已不存在，不得使其成功加入一個已解散的團。
- **FR-012**: 非以會員身分建立的團（匿名建團）MUST NOT 提供邀請好友功能——此功能僅適用於團長本身具備會員好友身分的情境。
- **FR-013**: 受邀好友嘗試接受邀請時，若因該團已達人數上限而失敗，系統 MUST（a）讓該筆邀請維持待回覆狀態，不轉為其他終態，讓好友可日後再次嘗試；且（b）即時通知團長這次接受嘗試因額滿而失敗（Clarifications Q2）。此為「已額滿」此一失敗原因專屬的行為——其餘導致接受失敗的原因（例如好友當下已活躍於另一個團、團已解散）不在此限，僅告知當事的受邀好友本人即可，不需另外通知團長。
- **FR-014**: 一筆邀請仍處於待回覆狀態期間，若團長與受邀好友的好友關係被解除（任一方主動解除），系統 MUST 讓該筆邀請自動轉為失效，受邀好友後續點擊該通知或嘗試接受 MUST 被明確告知邀請已失效，MUST NOT 允許其完成加入（Clarifications Q3）。

### Key Entities *(include if feature involves data)*

- **GroupInvite（組團邀請）**：代表團長對某位好友發出的一筆邀請。包含：所屬團、邀請人（團長）、受邀人（好友）、目前狀態（待回覆／已接受／已拒絕／已失效），以及建立時間。同一團對同一位好友，「待回覆」狀態至多同時存在一筆（FR-003）。「已失效」專指好友關係於待回覆期間被解除的情況（FR-014），與「已拒絕」（好友主動選擇不加入）語意不同，兩者 MUST 分開呈現，不得混為一談。
- **Group（團）**：既有實體，本功能新增「僅會員建立的團」才可使用邀請功能的限定條件（FR-012）。
- **Member（會員）**：既有實體，邀請人與受邀人皆為會員身分。
- **FriendRequest / 好友關係**：既有實體，決定「誰是誰的好友」，本功能的可邀請對象完全依此既有關係決定，不重新定義好友關係本身。
- **Notification（通知）**：既有實體，本功能新增兩種通知情境——（1）投遞給受邀好友的「組團邀請」通知；（2）投遞給團長的「邀請因額滿而接受失敗」通知（FR-013）。兩者皆沿用既有通知機制的列表、未讀計數、已讀/未讀、點擊導向等既有行為，不需重新設計。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**：團長從好友列表送出邀請後，2 秒內受邀好友（若正在使用系統）即可在畫面上看到通知提示。
- **SC-002**：受邀好友從收到通知到完成加入（未額滿、對方目前無其他活躍團的情境），無論該團是否設有通關密碼，全程一次操作（點擊通知 → 接受）即可完成，不需自行查找組團編號、也不需輸入密碼。
- **SC-003**：團長不會意外對同一位好友重複發送待處理邀請——重複發送的嘗試 100% 被系統擋下。
- **SC-004**：團長查看邀請狀態時，100% 準確反映每位受邀好友的最新真實狀態（待回覆／已接受／已拒絕／已在團內）。
- **SC-005**：所有邀請的接受結果，100% 一致略過通關密碼驗證（FR-007）——不會有部分邀請仍被要求輸入密碼、部分沒有的不一致情況。
- **SC-006**：邀請因額滿而接受失敗時，團長（若正在使用系統）2 秒內即可在畫面上看到通知提示；事後查看邀請狀態列表，該筆邀請 100% 仍正確顯示為待回覆，而非被誤標記為失敗或已結束。
- **SC-007**：好友關係解除後，任何一筆與該關係相關、原本待回覆的邀請，100% 無法再被接受——不存在「關係已解除，但對方仍成功用舊邀請加入」的情況。

## Assumptions

- 僅有以會員身分建立本團的團長，才能使用邀請好友功能；匿名建立的團沒有對應的會員好友清單，此功能對其不開放（FR-012）。
- 可邀請對象僅限團長既有的好友關係，不在本功能內提供另一套「搜尋任意會員並邀請」的入口——若要邀請尚非好友的人，需先透過既有的好友系統加為好友。
- 邀請不會過期失效，而是持續維持「待回覆」直到受邀好友接受、拒絕，或該團解散（解散後接受操作自然失敗，見 Edge Cases），不另外設計獨立的邀請逾期機制。
- 拒絕邀請（好友主動選擇不加入）不會通知團長；團長是透過管理頁面的邀請狀態列表主動查看，而非被動收到「已被拒絕」的通知（沿用好友系統「解除好友不通知對方」的既有精神，保持單向、低干擾的通知量）。此與「接受嘗試因額滿而失敗」（FR-013）不同——後者屬於系統性失敗、且團長可能可以主動處理（調高上限），因此才需要即時通知團長；純粹的「拒絕」則沒有團長可採取的後續行動，故不通知。
- 一筆邀請只對應一位受邀好友；一次選擇多位好友發送，等同於各自獨立建立多筆邀請，彼此的接受/拒絕互不影響。
- 通知投遞管道沿用現行「應用內即時提示」範圍（不含瀏覽器/裝置系統推播），與既有通知機制的既定範圍一致。
- 接受邀請略過通關密碼是刻意的設計決定（Clarifications Q1）：邀請本身即代表團長已對這位好友個別授權，密碼保護的目的是擋下「未經團長同意」的加入者，受邀者不在此列；團長若想避免邀請被濫用，仍可透過「不邀請」或（若未來支援）撤回邀請來控制，而非依賴密碼。
