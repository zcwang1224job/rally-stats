# Feature Specification: 訪客即時戰況頁面建立帳號並綁定戰績

**Feature Branch**: `028-guest-stats-binding`

**Created**: 2026-09-15

**Status**: Draft

**Input**: User description: "如果非登入玩家在團戰的即時畫面（進行中/已完結），可以立刻建立帳號並綁定戰績"

## Clarifications

### Session 2026-09-15

- Q: 當訪客開啟自己的個人查看連結時，若瀏覽器目前剛好已經是某個會員的登入狀態，「建立帳號並綁定戰績」入口該如何處理？ → A: 直接沿用目前已登入的 session 一鍵綁定——入口文字改為「將本場戰績綁定到我的帳號」，不需再輸入帳密，也不需先建立新帳號或另外登入。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 訪客在自己的即時戰況頁面建立新帳號並綁定戰績 (Priority: P1)

以訪客（非會員）身份加入某團的球友，透過自己專屬的個人查看連結瀏覽該團的即時戰況（比賽進行中）或賽後總結（比賽已完結），看到「建立帳號並綁定戰績」的入口，點擊後直接在同一個畫面完成帳號註冊（可使用 Email/密碼或既有的 Google/LINE 快速登入方式），註冊成功後，這位訪客在本團的所有比賽紀錄立即歸戶到這個新帳號，之後用這個帳號登入就能在「會員專區 -> 對戰紀錄」看到這些戰績，不會因為當初是以訪客身份參與而遺失。

**Why this priority**: 這是本功能的核心價值——把訪客現場玩完球「順手」建立帳號的黃金時機直接接上戰績保存，省去「先自己去註冊、再想辦法回頭找回這場戰績」的斷點（目前系統沒有任何方式讓訪客事後找回戰績）。沒有這條，整個功能不成立。

**Independent Test**: 讓一位訪客以個人查看連結進入某團的即時戰況頁面（不論該團當下是進行中或已完結），點擊「建立帳號並綁定戰績」完成註冊，可獨立驗證：(1) 新帳號建立成功、(2) 該訪客在本團的既有與後續比賽紀錄，登入後都能在對戰紀錄中查到，且與一般會員的戰績呈現方式一致。

**Acceptance Scenarios**:

1. **Given** 訪客透過個人查看連結瀏覽一個進行中的團，且自己尚未綁定任何帳號，**When** 訪客點擊「建立帳號並綁定戰績」並以 Email/密碼完成註冊，**Then** 系統成功建立會員帳號，並將這位訪客的名冊身份與新帳號建立對應關係，畫面在不中斷、不需重新導覽的情況下，直接以「已登入會員」的狀態繼續顯示同一份即時戰況。
2. **Given** 訪客透過個人查看連結瀏覽一個已完結的團，**When** 訪客點擊「建立帳號並綁定戰績」並以 Google 或 LINE 帳號完成快速註冊，**Then** 系統同樣成功建立帳號並完成綁定，且這場（及本團其他)已完結的比賽紀錄立即可在該帳號的對戰紀錄中查到。
3. **Given** 訪客已成功綁定帳號，**When** 訪客（或任何人）之後再次開啟同一個個人查看連結，**Then** 畫面 MUST NOT 再顯示「建立帳號並綁定戰績」的入口，改為正常呈現該訪客身份已對應會員帳號後的檢視畫面。
4. **Given** 訪客在本團的名冊狀態是「已離場」或「已被踢出」（不影響其歷史比賽紀錄的真實性），**When** 訪客透過個人查看連結建立帳號並綁定，**Then** 系統仍 MUST 成功綁定，不因名冊目前狀態而拒絕。
5. **Given** 該團已被團長解散，**When** 訪客透過（解散前產生、仍然有效的）個人查看連結建立帳號並綁定，**Then** 系統仍 MUST 成功綁定，讓訪客保留這段已結束活動的歷史戰績。
6. **Given** 訪客開啟自己的個人查看連結時，瀏覽器目前剛好已經是某個會員的登入狀態，**When** 訪客點擊入口（此時入口文字改為「將本場戰績綁定到我的帳號」），**Then** 系統直接沿用目前的登入 session 完成綁定，不需再輸入帳密，也不需要另外建立新帳號或走登入流程。

---

### User Story 2 - 已有會員帳號的訪客改用登入方式完成綁定 (Priority: P2)

球友本身其實已經是本系統的會員，但這次是在沒有登入的狀態下以訪客身份加入某團（例如用別人的裝置，或忘記先登入），在自己的即時戰況／賽後總結頁面看到綁定入口時，選擇「使用現有帳號登入」而非「建立新帳號」，登入成功後同樣完成戰績綁定。

**Why this priority**: 這是 User Story 1 的自然延伸——沒有它，已有帳號但當下未登入的球友會被迫「被動」建立一個重複帳號才能保住這場戰績，造成一人多帳號的資料品質問題；但即使沒有這條，核心的「訪客即時綁定戰績」價值已經由 US1 達成，因此優先度次於 US1。

**Independent Test**: 讓一位已有會員帳號、但目前未登入的訪客開啟自己的個人查看連結，選擇「使用現有帳號登入」並完成登入，可獨立驗證登入後這場（及本團其他）比賽紀錄立即出現在該既有帳號的對戰紀錄中，且系統沒有額外建立一個新帳號。

**Acceptance Scenarios**:

1. **Given** 訪客在即時戰況頁面看到綁定入口，**When** 訪客選擇「使用現有帳號登入」並輸入正確的既有帳號登入方式（Email/密碼或 Google/LINE），**Then** 系統完成登入並將這位訪客的名冊身份與該既有帳號綁定，不建立新帳號。
2. **Given** 訪客在「建立帳號」流程中輸入的 Email 已被既有帳號註冊，**When** 系統偵測到重複，**Then** 系統 MUST 提示此 Email 已有帳號，並引導訪客改用登入方式完成綁定，而不是直接註冊失敗了事。

---

### Edge Cases

- 訪客的名冊身份其實早已被綁定過（例如訪客自己開了兩個分頁，或重新整理後又點了一次)：系統 MUST 確保同一筆名冊身份最終只會對應到一個帳號，不會因重複點擊或併發請求而綁定到兩個不同帳號，也不會重複建立帳號。
- 訪客綁定帳號時使用的暱稱／顯示名稱與其名冊項目中原本登記的暱稱不同：綁定僅建立名冊身份與帳號的對應關係，不影響該場次歷史紀錄中原本記錄的參賽暱稱。
- 這位訪客其實在同一次活動中，同一團裡有多筆名冊身份（例如中途被踢出後又重新以訪客身份加入一次）：僅綁定訪客當下所使用的這一筆個人查看連結所對應的名冊身份，不主動尋找或合併其他分開的名冊身份。
- 訪客手上的個人查看連結其實是團長轉交給別人使用的（依現行訪客連結機制，持有連結即視為該訪客本人）：綁定沿用既有個人查看連結的信任機制，不額外要求身份驗證。
- 訪客在「建立帳號」過程中，於送出前放棄離開頁面：系統 MUST NOT 建立不完整的帳號或造成名冊身份被綁定到一個未完成建立的帳號。
- 開啟個人查看連結時瀏覽器當下的登入狀態其實不是這位訪客本人（例如共用裝置上別人忘記登出）：一鍵綁定沿用既有「持有個人查看連結即視為訪客本人」的信任機制，不因這個情境額外要求身份驗證，與現行訪客連結的安全假設一致。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系統 MUST 讓透過個人查看連結瀏覽即時戰況（進行中）或賽後總結（已完結）畫面、且尚未對應任何會員帳號的訪客，看到綁定入口；入口文字與行為 MUST 依瀏覽器當下的登入狀態而異——未登入時顯示「建立帳號並綁定戰績」，已登入時顯示「將本場戰績綁定到我的帳號」。
- **FR-002**: 系統 MUST 讓訪客可直接在同一畫面內、使用系統既有的任一種帳號建立方式（Email/密碼、或既有支援的 Google／LINE 快速註冊）完成帳號建立，無需先行離開此畫面。
- **FR-003**: 帳號建立成功後，系統 MUST 立即將此訪客的名冊身份與新建立的帳號建立對應關係，使該名冊身份下所有已發生與後續發生的比賽紀錄，都歸屬於這個帳號。
- **FR-004**: 系統 MUST 讓此綁定功能同時適用於「團仍在進行中」與「團已完結（含已被解散）」兩種狀態，只要對應的名冊身份尚未綁定過帳號。
- **FR-005**: 系統 MUST NOT 允許同一筆名冊身份被綁定到超過一個帳號；當名冊身份已完成綁定後，系統 MUST 不再顯示「建立帳號並綁定戰績」入口，並改為呈現一般已登入的檢視畫面。
- **FR-006**: 系統 MUST 確保綁定動作具備並發安全性——同一筆名冊身份即使被重複或同時觸發多次綁定請求，最終仍只會成功綁定一次。
- **FR-007**: 帳號建立並完成綁定後，系統 MUST 讓訪客在不中斷、不需重新導覽的情況下，直接以已登入會員的身份繼續檢視原本正在瀏覽的即時戰況或賽後總結內容。
- **FR-008**: 系統 MUST 讓已擁有會員帳號、但目前未登入的訪客，可選擇「使用現有帳號登入」而非「建立新帳號」來完成同一筆名冊身份的綁定。
- **FR-009**: 當訪客於「建立帳號」流程中輸入的 Email 已被其他帳號註冊時，系統 MUST 提示該 Email 已有帳號，並引導其改用登入方式完成綁定。
- **FR-010**: 帳號建立與登入流程本身（欄位驗證、密碼規則、OAuth 授權等）MUST 沿用系統既有的帳號建立與登入規則，不因透過此入口觸發而放寬或改變驗證邏輯。
- **FR-011**: 綁定動作 MUST NOT 修改該名冊身份原本已記錄在比賽紀錄中的參賽暱稱／顯示名稱。
- **FR-012**: 當訪客開啟個人查看連結時瀏覽器已是登入狀態，系統 MUST 直接沿用該登入 session 完成綁定，不要求重新輸入帳密，也不要求先登出再建立新帳號或登入。

### Key Entities

- **訪客名冊身份（Roster Entry）**：代表一位以訪客身份參與某團活動的球員，本功能為其新增「是否已對應到一個會員帳號」的狀態轉換——從「尚未對應」變成「已對應到某帳號」，且此關係一旦建立即不可再變更對應的帳號。
- **會員帳號（Member）**：透過本功能建立或登入的既有帳號，綁定後成為對應名冊身份及其比賽紀錄的擁有者。
- **比賽紀錄（Match Record）**：附屬於訪客名冊身份之下的比賽參與紀錄；因名冊身份完成綁定而自動歸屬於對應的會員帳號，紀錄本身的內容（如參賽暱稱）不因綁定而改變。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 訪客從點擊「建立帳號並綁定戰績」到完成綁定、能在對戰紀錄中看到本團戰績，全程可在 2 分鐘內、且不需離開原本的即時戰況／賽後總結畫面完成。
- **SC-002**: 已綁定的名冊身份，其名下所有既有與後續比賽紀錄，100% 會出現在對應帳號的對戰紀錄中，且與一般會員的戰績顯示方式沒有落差。
- **SC-003**: 任何名冊身份在系統中最終只會對應到一個帳號，即使在重複點擊或同時多裝置操作的情況下也不例外。
- **SC-004**: 使用「使用現有帳號登入」路徑完成綁定的訪客，不會因此在系統中被建立出重複的帳號。

## Assumptions

- 綁定的範圍是「訪客當下所使用的這一筆個人查看連結所對應的名冊身份」，不涉及同一人可能在其他團擁有的其他、彼此獨立的訪客名冊身份（系統目前沒有跨團的訪客身份概念，每次以訪客身份加入不同團都是各自獨立的名冊項目）。
- 綁定不會反向修改比賽紀錄中已經記錄下來的參賽暱稱／顯示名稱，僅建立名冊身份與帳號之間「戰績歸屬」的對應關係。
- 個人查看連結本身的信任機制沿用既有訪客連結設計（持有連結即視為該訪客本人），本功能不為此新增額外的身份驗證。
- 此入口僅出現在訪客自己的個人查看連結頁面，不出現在不具備訪客身份對應資訊的公開/大螢幕賽況畫面。
- 「建立帳號並綁定戰績」入口所提供的帳號建立方式，與系統目前既有支援的方式一致（Email/密碼、Google、LINE），不需為此功能新增額外的註冊管道。
