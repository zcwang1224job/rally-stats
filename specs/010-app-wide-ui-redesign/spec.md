**Feature Branch**: `[010-app-wide-ui-redesign]`

**Created**: 2026-09-02

**Status**: Draft

**Input**: User description: "web ui 根據ui 資料夾中的ScoreBoardUI.drawio進行修改"（經與使用者確認範圍：整個 App 依 `ui/ScoreBoardUI.drawio` 的 7 個頁面全部重新設計，且好友系統這次一併完成）

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 計分板重新設計 (Priority: P1)

球場邊觀眾/選手看計分板時，畫面改為深色背景搭配左右兩色（洋紅／藍）巨大分數面板，讓比分在遠距離、球場燈光下依然一眼可辨識；面板下方顯示該隊參賽者暱稱，畫面一角顯示「即將登場」的下一組參賽者提示。

**Why this priority**: 計分板是本次重新設計的直接起點（檔名即為 ScoreBoardUI），也是全系統中唯一「純顯示、無互動」的畫面，視覺改版風險最低、效益（遠距離可讀性）最直接，適合優先交付。

**Independent Test**: 可獨立開啟任一場地的計分板連結，在單打與雙打兩種模式下確認深色背景、雙色分數面板、參賽者暱稱與「即將登場」提示皆正確顯示，無需依賴其他使用者故事。

**Acceptance Scenarios**:

1. **Given** 一場正在進行中的比賽，**When** 開啟該場地的計分板連結，**Then** 畫面呈現深色背景，左側面板（洋紅色）與右側面板（藍色）分別顯示雙方目前比分，字級大到可在數公尺外清楚辨識。
2. **Given** 雙打比賽，**When** 檢視計分板，**Then** 每側分數面板下方以隊伍代表色文字顯示該隊兩位參賽者的暱稱（垂直排列）。
3. **Given** 該場地下一輪已排定下一組參賽者，**When** 檢視計分板，**Then** 畫面一角顯示「即將登場」提示與該組參賽者暱稱；若尚無排定的下一組，則不顯示此提示區塊。
4. **Given** 比賽比分即時變動，**When** 管理員在控制板按下 +1/-1，**Then** 計分板畫面 MUST 在既有即時同步機制下更新為最新比分，行為與現行系統一致（本故事僅改變呈現方式，不改變同步機制）。

---

### User Story 2 - 控制板重新設計 (Priority: P1)

管理員操作控制板時，同一畫面可同時看到並操作多個場地（不需切換分頁），每個場地區塊內比分置中、加減分按鈕分置比分兩側方便單手操作，並在下方提供「下一場」與「提前結束」操作。

**Why this priority**: 與計分板同屬本次改版最直接對應的檔案內容，且控制板是管理員在球場邊最頻繁操作的畫面，版面易用性直接影響比賽進行順暢度，優先度與計分板並列最高。

**Independent Test**: 可獨立開啟全部場地控制板連結，在多場地情境下確認每個場地區塊的加減分按鈕、下一場、提前結束操作皆可正確運作，無需依賴其他使用者故事。

**Acceptance Scenarios**:

1. **Given** 一個團有 2 個以上場地正在進行比賽，**When** 開啟全部場地控制板，**Then** 畫面依序顯示每個場地各自的區塊，每個區塊皆可獨立操作，不需切換頁面即可同時監看多場比賽。
2. **Given** 檢視任一場地區塊，**When** 檢視版面配置，**Then** 該場地比分置於區塊中央，左隊的「+1」「-1」按鈕在比分左側、右隊的「+1」「-1」按鈕在比分右側，「下一場」與「提前結束」按鈕位於比分下方。
3. **Given** 管理員點擊某場地的「+1」，**Then** 該場地比分即時更新，其餘場地區塊不受影響（沿用既有的單場地獨立寫入邏輯）。
4. **Given** 單一場地控制板（非全部場地版本），**Then** 僅顯示該場地一個區塊，版面配置與全部場地控制板中單一場地區塊的呈現方式一致。

### User Story 3 - 開團管理頁改為側邊欄式導覽 (Priority: P1)

管理員進入管理頁時，畫面改為左側固定分類導覽（場地、賽程、輪替名單、團名、管理權限資訊、管理員設定），點擊左側項目即可切換右側對應內容，不需再於單一長頁面中上下捲動尋找設定項目。

**Why this priority**: 管理頁是操作項目最多、最複雜的畫面，目前為單頁全部展開的捲動式版面；改為分類導覽對管理員的操作效率影響最大，且此改版不涉及任何新業務邏輯，風險與計分板/控制板相當，故列為同一優先度。

**Independent Test**: 可獨立進入任一團的管理頁，確認左側每個分類項目點擊後皆能正確切換至對應內容區塊（場地列表、賽程控制、輪替名單、團名編輯、管理權限資訊、比賽模式與排程機制設定），且既有的解散、重新產生 PIN 碼/連結等操作皆可從對應分類內正確觸發，無需依賴其他使用者故事。

**Acceptance Scenarios**:

1. **Given** 管理員進入管理頁，**When** 檢視畫面版面，**Then** 左側顯示「場地」「賽程」「輪替名單」「團名」「管理權限資訊」「管理員設定」等分類項目，預設選中其中一項並顯示其內容。
2. **Given** 管理員點擊左側「場地」項目，**Then** 右側顯示場地列表，每個場地皆可個別開啟「顯示計分板連結/QR Code」與「顯示控制板連結/QR Code」，並提供新增場地、刪除場地的入口。
3. **Given** 管理員點擊左側「賽程」項目，**Then** 右側顯示賽程控制內容（含現行系統已有的 Next Round／Auto Next Round、每場地的比分控制區塊），並顯示目前的比賽模式與排程機制供快速檢視。
4. **Given** 管理員點擊左側「團名」項目，**Then** 右側顯示團名編輯表單；點擊左側「管理權限資訊」，**Then** 右側顯示組團編號與管理 PIN 碼，並提供既有的「重新產生 PIN 碼」操作。
5. **Given** 管理員點擊左側「管理員設定」項目，**Then** 右側顯示比賽模式（單打/雙打）與排程機制（公平輪替/手動安排/固定搭檔循環賽/個人全混搭循環賽）的編輯選項與「解散」操作；此區塊內任何設定變更 MUST 沿用既有的版本衝突與即時廣播機制，不因版面改變而改變其行為。
6. **Given** 此團已解散（唯讀模式），**When** 進入管理頁，**Then** 左側導覽項目仍存在，但各分類內容改為唯讀呈現，與現行系統的唯讀行為一致。

### User Story 4 - 首頁改版 (Priority: P2)

訪客與會員造訪首頁時，改為頂部圖示化導覽列（嘎團、開團、登入/會員入口圖示），取代目前條列文字連結的呈現方式。

**Why this priority**: 首頁是入口頁面，改版範圍相對單純（樣式與圖示化，不改變導覽邏輯——009 規格已建立的全站導覽殼層邏輯維持不變），優先度次於三個高互動頻率的核心操作畫面。

**Independent Test**: 可獨立開啟首頁，在訪客與已登入會員兩種狀態下確認頂部圖示化導覽列正確顯示對應入口，無需依賴其他使用者故事。

**Acceptance Scenarios**:

1. **Given** 訪客造訪首頁，**When** 檢視頂部導覽列，**Then** 以圖示呈現「嘎團」（前往揪團列表）、「開團」（前往建立揪團）、「登入」等入口，取代現行純文字連結。
2. **Given** 已登入會員造訪首頁，**Then** 「登入」圖示改為會員專屬入口圖示，其行為與 009 規格既有的登入狀態感知邏輯一致。

---

### User Story 5 - 嘎團／加入流程改版 (Priority: P2)

使用者瀏覽揪團列表、輸入通關密語、輸入暱稱、或透過 QR Code 連結加入時，畫面改為卡片式列表（含篩選、分頁）與置中彈窗式的密碼/暱稱輸入流程。

**Why this priority**: 加入流程涉及的畫面數量多、但每個畫面本身的業務邏輯已由既有規格（001/004）完整定義，此故事純粹是版面與互動方式的調整，優先度與首頁相同。

**Independent Test**: 可獨立走過「瀏覽列表 → 篩選 → 輸入密碼（若需要）→ 輸入暱稱或確認 → 加入成功」全程，以及「開啟 QR Code 加入連結 → 顯示對應加入畫面」，確認每個畫面版面正確呈現，無需依賴其他使用者故事。

**Acceptance Scenarios**:

1. **Given** 使用者進入揪團列表，**When** 檢視畫面，**Then** 以卡片呈現各團（團名、創建者、人數、比賽模式、場地、活動時間），並提供依場地名稱／場地 ID 篩選與分頁導覽。
2. **Given** 使用者點擊某張團卡片的「加入」，**When** 該團設有通關密碼，**Then** 顯示置中彈窗要求輸入密碼；密碼錯誤時彈窗內顯示錯誤提示，不關閉彈窗。
3. **Given** 密碼驗證通過（或該團無需密碼）且使用者為訪客，**Then** 顯示置中彈窗要求輸入暱稱；若為已登入會員，直接顯示確認加入畫面而不要求輸入暱稱。
4. **Given** 使用者透過 QR Code 掃描開啟加入連結，**Then** 直接顯示對應的加入畫面（密碼或暱稱輸入，視該團設定而定），並提供「返回」動作。

### User Story 6 - 會員頁面版面改版 (Priority: P2)

會員進行註冊、登入、忘記密碼、首次登入設定暱稱、或檢視自己的會員資訊時，改用置中卡片式表單版面，會員資訊頁改為條列「登出／對戰紀錄／好友／個人設定」的選單式呈現。

**Why this priority**: 這些畫面的登入/驗證/暱稱設定邏輯已由既有規格（006 之 US1-3）完整實作，此故事同樣純屬版面調整，優先度與首頁、加入流程相同。

**Independent Test**: 可獨立走過註冊、登入、忘記密碼、首次登入設定暱稱、檢視會員資訊選單等畫面，確認版面正確呈現且既有功能（送出表單、導向對應下一步）不受影響，無需依賴其他使用者故事。

**Acceptance Scenarios**:

1. **Given** 訪客進入註冊/登入/忘記密碼頁面，**Then** 畫面呈現置中卡片式表單，包含既有系統已定義的欄位（Email、密碼、確認密碼視頁面而定），視覺風格與其餘頁面一致。
2. **Given** 已登入會員首次登入且尚未設定暱稱，**Then** 顯示置中卡片要求輸入暱稱，確認後才可繼續使用其餘會員功能（沿用既有規格的鎖定邏輯）。
3. **Given** 已登入會員檢視自己的會員資訊，**Then** 畫面以選單方式條列「對戰紀錄」「好友」「個人設定」入口與「登出」動作。

---

### User Story 7 - 完成好友系統與會員團記錄復原功能 (Priority: P3)

會員可搜尋其他會員的使用者編號並發送好友邀請、檢視與篩選好友列表、接受或拒絕收到的邀請、解除既有好友關係；已登入會員也可在會員頁面看到自己建立過的所有團，並對任一團一鍵重設管理 PIN 碼、無縫進入管理頁。

**Why this priority**: 此為既有 `006-member-friends` 規格中尚未完成的部分（後端 API 端點與前端畫面皆未建置）——功能性需求已由該規格完整定義，本故事的範圍是「依該規格完成建置，並套用本次的新版面設計」；由於是全新功能建置（而非既有畫面改版），風險與工作量皆高於前六個故事，故列為最低優先。

**Independent Test**: 可用兩個已完成 Email 驗證的會員帳號，獨立驗證搜尋加好友、接受/拒絕邀請、好友列表篩選、解除好友等完整流程；亦可用一個會員帳號建立的團，獨立驗證「忘記管理 PIN 碼」的重設流程；均無需依賴其他使用者故事。

**Acceptance Scenarios**:

1. **Given** 會員搜尋另一位會員的使用者編號，**Then** 依雙方目前關係狀態（尚無關係／已發送待處理／待我回覆／已是好友）顯示對應的操作按鈕或狀態標籤，且無法對自己或未驗證帳號發送邀請。
2. **Given** 會員的好友列表，**When** 輸入部分暱稱或使用者編號進行篩選，**Then** 僅顯示符合篩選條件的好友。
3. **Given** 會員收到好友邀請，**Then** 可在對應畫面選擇「接受」（雙方成為好友）或「拒絕」（邀請關閉，不成為好友）。
4. **Given** 會員與另一會員已是好友，**When** 點擊「解除好友」並在二次確認彈窗確認，**Then** 雙方好友列表立即不再顯示對方，且對方不會收到任何通知。
5. **Given** 已登入會員曾以自己的帳號建立過某團（不論該團是否已解散），**When** 在會員頁面對該團點擊「忘記管理 PIN 碼」並確認，**Then** 系統核發新的管理 PIN 碼與管理 Token，直接導向該團的管理頁，不要求輸入原 PIN 碼；匿名建立的團不會出現在此列表中，亦不提供此復原入口。

### Edge Cases

- 控制板單一畫面同時顯示多個場地時，其中一個場地的比賽已用「提前結束」中止，該場地區塊如何呈現？（沿用現行系統既有的「已捨棄」狀態呈現方式，不因版面改版而改變比賽紀錄判定邏輯——見 Constitution 原則 III。）
- 計分板尚未有任何比賽開始（場地剛建立、輪替尚未產生第一場比賽）時，分數面板要顯示什麼？（顯示雙方預設分數（0）與「等待比賽開始」提示，不顯示參賽者暱稱區塊，直到有比賽被排入該場地為止。）
- 開團管理頁的左側導覽在手機寬度下如何呈現？（沿用既有規格 007/008 已建立的行動裝置優先設計原則與觸控尺寸標準，側邊欄在窄螢幕下 MUST 收合為可展開的選單，不得因固定側邊欄而壓縮版面寬度導致內容無法操作。）
- 好友系統的新畫面如何融入既有的全站導覽殼層（009 規格）？（好友列表、新增好友、回覆好友申請等頁面比照會員頁面的現行作法，套用 009 已建立的全站導覽殼層，不需要獨立的導覽邏輯。）
- 使用者已在別的分頁對同一筆好友邀請按下「接受」，此分頁的「回覆好友申請」畫面尚未重新整理時再次點擊「接受」或「拒絕」？（依既有樂觀鎖定慣例，第二次操作將收到「找不到此邀請」等對應錯誤提示並要求重新整理清單，不產生重複的好友關係或錯誤狀態。）

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 計分板 MUST 採用深色背景，並以左右兩色（洋紅／藍）巨大分數面板呈現雙方目前比分。
- **FR-002**: 計分板 MUST 在分數面板旁/下方顯示該隊參賽者暱稱；雙打時 MUST 同時顯示該隊兩位參賽者暱稱。
- **FR-003**: 計分板在該場地已排定下一組參賽者時，MUST 顯示「即將登場」提示與該組參賽者暱稱；無排定時 MUST NOT 顯示此提示區塊。
- **FR-004**: 控制板（含全部場地控制板）MUST 在同一畫面內同時呈現多個場地各自的操作區塊，不需切換分頁即可監看與操作全部進行中的場地。
- **FR-005**: 每個場地區塊 MUST 將比分置於中央，左隊「+1」「-1」置於比分左側、右隊「+1」「-1」置於比分右側，「下一場」「提前結束」置於比分下方。
- **FR-006**: 開團管理頁 MUST 改為左側固定分類導覽（場地、賽程、輪替名單、團名、管理權限資訊、管理員設定）搭配右側對應內容區塊的版面，取代現行單頁全展開捲動版面。
- **FR-007**: 管理頁左側各分類項目 MUST 各自對應到現行系統已有的功能區塊（場地管理、賽程控制、輪替名單、團名編輯、管理權限資訊與 PIN 碼重設、比賽模式/排程機制設定與解散），MUST NOT 遺漏任何現行已存在的管理操作。
- **FR-008**: 管理頁側邊導覽在窄螢幕（手機寬度）下 MUST 收合為可展開的選單，維持既有的行動裝置優先與觸控尺寸標準（Constitution 原則 VII）。
- **FR-009**: 首頁 MUST 改為頂部圖示化導覽列，呈現嘎團、開團、登入/會員入口；此改版 MUST NOT 改變 009 規格已定義的登入狀態感知與導覽殼層行為。
- **FR-010**: 揪團列表 MUST 改為卡片式呈現（團名、創建者、人數、比賽模式、場地、活動時間），並保留既有的依場地名稱/場地 ID 篩選與分頁功能。
- **FR-011**: 加入團流程（通關密碼輸入、暱稱輸入、確認加入）MUST 改為置中彈窗式呈現；已登入會員 MUST 略過暱稱輸入直接進入確認畫面，訪客 MUST 顯示暱稱輸入。
- **FR-012**: 會員的註冊、登入、忘記密碼、首次登入暱稱設定 MUST 改為置中卡片式表單版面，既有欄位與驗證邏輯 MUST 維持不變。
- **FR-013**: 會員資訊頁 MUST 改為選單式呈現「對戰紀錄」「好友」「個人設定」入口與「登出」動作。
- **FR-014**: 系統 MUST 提供會員搜尋其他會員使用者編號並發送好友邀請的功能，搜尋結果 MUST 依雙方關係狀態（尚無關係／已發送待處理／待我回覆／已是好友）顯示對應操作或狀態；MUST NOT 允許對自己或未完成 Email 驗證的帳號發送邀請。
- **FR-015**: 系統 MUST 提供好友列表（可依暱稱或使用者編號篩選）、接受/拒絕收到的好友邀請、以及解除既有好友關係（單方面動作，解除後 MUST NOT 通知對方）的功能。
- **FR-016**: 解除好友關係與拒絕好友邀請後，雙方 MUST 仍可重新發送好友邀請，不受先前解除/拒絕紀錄限制。
- **FR-017**: 系統 MUST 提供已登入會員檢視自己建立過的所有團（不論是否已解散）的列表，並可對任一筆團記錄一鍵重設管理 PIN 碼、核發新管理 Token 並直接導向管理頁，不要求輸入原 PIN 碼；匿名建立的團 MUST NOT 出現在此列表，亦 MUST NOT 提供此復原入口。
- **FR-018**: FR-014～FR-017 所涉及的資料模型、API 合約與其餘既有驗收情境，MUST 沿用 `specs/006-member-friends/` 已定義之內容，本規格不重複定義、亦 MUST NOT 與其牴觸。
- **FR-019**: 好友系統與會員團記錄復原功能之新增頁面 MUST 套用 009 規格已建立的全站導覽殼層，比照會員頁面現行作法。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 在 3 公尺外的距離，使用者可正確讀出計分板上的比分數字（透過巨大字級與高對比配色達成）。
- **SC-002**: 管理員可在不切換分頁的情況下，於控制板同時監看並操作一個團內所有進行中場地的比分。
- **SC-003**: 管理員從管理頁左側導覽點擊任一分類到看見對應內容，反應時間在使用者感知上為「立即」（不經過整頁重新載入）。
- **SC-004**: 找 5 位以上未曾使用過本系統改版介面的受測者，分別操作「加入一個團」與「搜尋並發送好友邀請」兩項任務，90% 以上可在無人協助的情況下獨立完成。
- **SC-005**: 好友系統與會員團記錄復原功能上線後，會員可自助完成「搜尋好友 → 發送邀請 → 對方接受 → 雙方看見彼此在好友列表」全流程，以及「遺失管理 PIN 碼 → 自助重設 → 重新進入管理頁」全流程，皆不需要任何人工協助或客服介入。
