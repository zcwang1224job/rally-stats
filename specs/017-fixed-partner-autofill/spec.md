# Feature Specification: 固定搭檔循環賽——手動配對後，剩餘未配對者自動隨機配對

**Feature Branch**: `[017-fixed-partner-autofill]`

**Created**: 2026-09-09

**Status**: Draft

**Input**: User description: "固定搭檔循環賽-可以選擇手動或自動配對, 若選手動配對完，剩下沒有配對的人就由系統隨機配對"

## Clarifications

### Session 2026-09-09

- Q: 隨機配對的觸發時機——管理員按下「產生下一輪賽程」時自動觸發？搭檔設定畫面上需要管理員另外按一個「隨機配對剩下的人」按鈕才觸發？還是兩者都要？ → A: 兩者都支援——搭檔設定畫面提供按鈕讓管理員可以提前配好並檢視、視需要調整，若管理員沒按就直接產生賽程，系統仍會在當下自動補齊，確保絕不會有人被漏掉。
- Q: 系統隨機配對產生的搭檔關係，要不要保留下來（跟管理員手動指定的搭檔一樣持續有效）？ → A: 不保留——只在「即將產生／已經產生的那一輪賽程」有效，MUST NOT 寫入正式搭檔資料；下一次產生賽程時，若這些成員仍然沒有正式搭檔，系統重新隨機配一次（配對組合可能與前一輪不同）。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 沒被手動配對到的人不再被排除在賽程外 (Priority: P1)

我是團的管理員，團的比賽模式是「固定搭檔」，配對來源設為「手動配對」。我自己把想要配成搭檔的人一組一組指定好之後，還有一些人我沒空/不確定怎麼配、就先跳過了。我希望不需要幫每一個人都手動配對，剩下的人系統會自動幫他們隨機配成搭檔，這樣產生賽程時才不會有人因為沒被配對而整個消失在賽程外。

**Why this priority**：這是本功能存在的核心原因——目前手動配對模式下，沒有搭檔的現役成員會被「產生下一輪賽程」整批悄悄排除、完全不會出現在該輪任何一場比賽裡，管理員也不會收到任何提示。人數一多，管理員很難每個人都手動配對完，這個缺口會直接造成部分成員打不到球。

**Independent Test**：一個固定搭檔、手動配對模式的團，現役成員為偶數人，管理員只手動配對其中一部分人、刻意留下至少兩人沒配對，接著直接產生下一輪賽程（不先使用搭檔設定畫面上的預覽按鈕）；可獨立驗證：賽程涵蓋所有現役成員（含原本沒被手動配對的人），沒有人被排除在外。

**Acceptance Scenarios**:

1. **Given** 一個固定搭檔、手動配對模式的團，現役成員 8 人，管理員只手動配好其中 6 人（3 組），剩下 2 人沒有搭檔, **When** 管理員不經預覽、直接產生下一輪賽程, **Then** 系統 MUST 自動把剩下那 2 人配成一組搭檔，該輪賽程 MUST 涵蓋全部 8 人。
2. **Given** 一個固定搭檔、手動配對模式的團，管理員完全沒有手動配對任何人, **When** 管理員直接產生下一輪賽程, **Then** 系統 MUST 把全部現役成員兩兩隨機配成搭檔，賽程 MUST 涵蓋所有現役成員。
3. **Given** 一個固定搭檔、手動配對模式的團，管理員已經把所有現役成員都手動配對完畢、沒有任何人剩下, **When** 管理員產生下一輪賽程, **Then** 系統 MUST NOT 更動任何一組管理員已手動指定的搭檔，也 MUST NOT 觸發任何隨機配對動作。

---

### User Story 2 - 產生賽程前，可以預覽並調整這次要用的隨機配對結果 (Priority: P2)

我是團的管理員，手動配對完想配的人之後，我想在真正產生賽程之前，先看看剩下的人會被系統配成怎樣，如果不喜歡其中一組（例如想讓某兩位球友這次搭檔），我想直接換掉、而不是等賽程出來才發現。我也希望這個「換一下」的操作方式跟我平常手動配對時一樣，不用學新的東西。

**Why this priority**：US1 解決了「有沒有配到」的問題，但隨機配對畢竟不是管理員自己選的，讓管理員能在產生賽程前先看到、視需要調整，才不會讓「系統隨機配對」變成一個管理員無法掌控的黑盒子。優先度低於 US1，因為即使暫時沒有預覽功能，US1 本身已經解決「不會被排除在賽程外」這個更急迫的問題（產生賽程當下系統仍會自動補齊）。

**Independent Test**：一個固定搭檔、手動配對模式的團，管理員部分手動配對後，在搭檔設定畫面上主動觸發「剩下的人隨機配對」預覽；可獨立驗證：畫面上會顯示系統即將用於下一輪賽程的暫時配對結果，管理員可以用既有「點選兩位成員重新配對」的操作方式換掉其中一組，且這個調整不會變成長期固定的正式搭檔——事後查看正式搭檔清單，看不到這組暫時配對。

**Acceptance Scenarios**:

1. **Given** 管理員在搭檔設定畫面上，對目前還沒有搭檔的現役成員主動觸發「剩下的人隨機配對」, **When** 系統完成隨機配對, **Then** 畫面 MUST 顯示這次即將用於下一輪賽程的暫時配對結果，並 MUST 讓使用者能清楚分辨這是暫時配對、而非正式搭檔。
2. **Given** 管理員正在檢視上述暫時配對結果, **When** 管理員點選其中一人、再點選另一位目前暫時配對不同的成員, **Then** 系統 MUST 用與重新指定正式搭檔完全相同的操作方式，把這兩人重新配成一組暫時配對。
3. **Given** 管理員已經預覽/調整過這次要用的暫時配對, **When** 管理員接著產生下一輪賽程, **Then** 系統 MUST 使用管理員最後調整過的那個暫時配對結果，MUST NOT 另外重新隨機配一次。
4. **Given** 管理員預覽過暫時配對結果、但沒有做任何調整就離開畫面（沒有產生賽程）, **When** 管理員之後重新查看搭檔設定畫面, **Then** 這組暫時配對 MUST NOT 出現在正式搭檔清單中。

### User Story 3 - 「自動配對」模式不受影響 (Priority: P3)

我是團的管理員，配對來源設為「自動配對」（不是「手動配對」）。我希望這個新功能不會影響到我原本每輪重新智慧配對的既有體驗。

**Why this priority**：確保本功能不會有非預期的副作用波及另一個既有模式，屬於回歸驗證性質，優先度最低。

**Independent Test**：一個固定搭檔、配對來源為「自動配對」的團產生下一輪賽程；可獨立驗證：賽程配對結果與本功能上線前的既有「自動配對」邏輯行為一致（依歷史配對次數重新計算，不讀取手動搭檔資料），未受本功能影響；搭檔設定畫面上也不會出現本功能新增的「隨機配對剩下的人」按鈕。

**Acceptance Scenarios**:

1. **Given** 一個固定搭檔、配對來源為「自動配對」的團, **When** 管理員產生下一輪賽程, **Then** 系統 MUST 沿用既有的自動配對邏輯，MUST NOT 套用「隨機配對剩餘未配對者」這個手動配對模式專屬的行為。

---

### Edge Cases

- 現役成員人數為奇數：既有規則已規定人數為奇數時 MUST 拒絕產生賽程；本功能不改變這條既有規則，也因此「補齊隨機配對後仍有一人配不到」的情況不會發生（未配對人數在通過既有偶數檢查後必然也是偶數）。
- 團切換到「手動配對」模式的當下、或有新成員加入時，既有機制已經會嘗試依加入順序把未配對的人湊成正式搭檔——若這些既有機制已經讓所有人都配對完成，本功能的隨機配對 MUST 沒有任何人可配、不觸發任何動作。
- 管理員重新指定某組正式搭檔，導致原本兩人的舊搭檔都變成未配對：這些人 MUST 依本功能規則，在下次產生賽程時比照「剩餘未配對者」處理。
- 管理員在同一輪賽程產生「之前」多次重新觸發預覽：每次觸發 MUST 重新隨機配對當下仍未配對的成員，不需要保留前一次未被採用的預覽結果。
- 管理員預覽/調整了暫時配對，但在產生賽程前，剩餘未配對成員的名單發生變化（例如又有人被踢除、或原本要配對的人被別的正式搭檔異動影響）：系統 MUST 在真正產生賽程前重新驗證這份暫時配對是否仍然只涵蓋「目前確實未配對」的現役成員；不再未配對或不再現役的成員 MUST NOT 出現在最終用於產生賽程的配對中。
- 管理員預覽/調整了暫時配對，但還沒產生賽程就離開了搭檔設定畫面（例如切換到別的分頁、或關閉瀏覽器）：由於暫時配對本來就 MUST NOT 被寫入正式搭檔資料（FR-004），這次的調整結果 MUST NOT 被保留——管理員之後重新回到搭檔設定畫面、或直接產生賽程，系統 MUST 視同尚未預覽過，依 FR-001/FR-002 的規則重新處理（重新隨機配對，而非沿用先前已離開畫面時的調整結果）。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 當團的配對來源設定為「手動配對」時，系統 MUST 在搭檔設定畫面上提供一個「剩下的人隨機配對」的操作，讓管理員可以在產生賽程前，主動將目前所有「沒有正式搭檔」的現役成員兩兩隨機配對，並檢視結果。
- **FR-002**: 只要現役成員總人數為偶數，若管理員在產生下一輪賽程時，尚有現役成員沒有正式搭檔（不論管理員是否用過 FR-001 的預覽操作），系統 MUST 在產生賽程的當下自動將這些人兩兩隨機配對，讓該輪賽程涵蓋全部現役成員，不再因為部分成員未被手動配對而將其排除在賽程外（US1）。
- **FR-003**: 隨機配對（不論透過 FR-001 的預覽操作或 FR-002 的自動補齊）MUST 只影響「目前沒有正式搭檔」的現役成員，MUST NOT 更動任何管理員已手動指定、目前仍然有效的正式搭檔配對（US1 驗收情境 3）。若管理員（或前端）提交的暫時配對清單中，同一位成員出現在超過一組配對裡，這些包含該重複成員的組合 MUST 全部視為無效、一律不採用——該成員 MUST 改依 FR-002 的自動補齊機制重新處理，MUST NOT 因為清單本身內部有重複，就讓該成員同時被排進兩個不同隊伍。
- **FR-004**: 系統隨機配對產生的搭檔關係 MUST 只在「即將產生或已經產生的那一輪賽程」中有效，MUST NOT 被寫入或視為正式、跨輪持續有效的搭檔關係。下一次產生賽程時，若這些成員仍然沒有正式搭檔，系統 MUST 重新隨機配對一次，配對組合可能與前一輪不同（US2）。
- **FR-005**: 當團的配對來源設定為「自動配對」時，系統 MUST NOT 提供或套用本功能新增的「隨機配對剩餘未配對者」相關操作與行為（不論是 FR-001 的預覽操作或 FR-002 的自動補齊），MUST 完全沿用既有的自動配對既有邏輯（US3）。
- **FR-006**: 管理員在調整 FR-001 產生的暫時配對預覽時，MUST 能使用與既有「點選兩位成員重新配對正式搭檔」相同的操作方式（點選兩位成員互相配對），不需要學習新的操作方式（US2）。這個調整動作的對象範圍 MUST 限制在「目前這份暫時配對所涵蓋的成員」之間——MUST NOT 允許選取任何已有正式搭檔的成員來源，避免管理員誤以為自己更動了正式搭檔、但實際上系統只當成暫時配對的一部分處理。
- **FR-007**: 若管理員產生賽程前已用 FR-001 預覽/調整過暫時配對，系統 MUST 直接採用該調整後的結果來產生賽程，MUST NOT 另外重新隨機配對一次（US2 驗收情境 3）。
- **FR-008**: 暫時配對在畫面上呈現時，MUST 以圖示或文字（而非僅靠顏色）與正式搭檔明確區隔，確保色盲或無法辨色的使用者也能分辨兩者差異（US2 驗收情境 1，沿用專案既有無障礙原則）。

### Key Entities *(include if feature involves data)*

- **正式搭檔配對（Partnership）**：兩位現役成員之間持續有效的固定搭檔關係，只在「固定搭檔」比賽模式下有意義。既有機制已支援「管理員手動指定」與「系統依加入順序自動湊對」兩種產生方式；一位成員在同一時間只能有一組有效的正式搭檔配對。本功能不改變這個實體本身。
- **暫時隨機配對（Temporary Random Pairing）**：本功能新增的概念——針對目前沒有正式搭檔的現役成員，為了「即將產生或已經產生的那一輪賽程」臨時湊出的搭檔組合。只在那一輪賽程的產生過程中有意義，MUST NOT 被視為、也 MUST NOT 轉換成正式搭檔配對；每次重新計算都可能得出不同組合。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 「手動配對」模式下，只要現役成員總人數為偶數，管理員 100% 能成功產生涵蓋所有現役成員的循環賽賽程，不會有任何現役成員因為沒被手動配對而缺席該輪賽程。
- **SC-002**: 管理員完成想要的手動配對後，不需要為每一位剩餘未配對的成員逐一手動操作，即可讓賽程涵蓋所有現役成員。
- **SC-003**: 管理員調整暫時配對預覽所需的操作步驟數，與調整一組正式搭檔所需的操作步驟數相同。
- **SC-004**: 「自動配對」模式下產生賽程的行為，在本功能上線前後 100% 一致，不受任何影響。
- **SC-005**: 事後查看正式搭檔清單時，100% 不會看到任何一組只存在於單一輪次的暫時隨機配對。

## Assumptions

- 「隨機」指的是從當下所有未配對的現役成員中均勻隨機兩兩配對，不套用「自動配對」模式既有的、依歷史配對次數最佳化的智慧配對邏輯——這正是本功能與既有「自動配對」模式的核心差異：一個是單純隨機補洞，一個是持續智慧優化。
- 本功能僅適用於比賽模式為「固定搭檔」、且配對來源設定為「手動配對」的團；不改變比賽模式為其他類型、或配對來源為「自動配對」的既有行為。
- 現役成員人數為奇數時，既有的「產生下一輪賽程」規則已會直接拒絕（要求偶數人才能產生賽程），本功能沿用此既有規則，不另外處理奇數人的情況。
- 暫時配對預覽的呈現方式，沿用既有「搭檔設定」畫面上「顯示所有正式搭檔與未配對成員」的既有呈現邏輯，僅新增「剩下的人隨機配對」這個操作與其暫時配對結果的顯示，不需要另外設計一套全新的畫面。
