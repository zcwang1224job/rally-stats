# Quickstart: 決勝分二次確認

驗證 [contracts/live-state-additions.md](./contracts/live-state-additions.md) 與四個計分畫面。決策見 [research.md](./research.md)，判定邊界見 [data-model.md](./data-model.md)。

## 前置準備

沿用既有本地開發環境。**這次沒有 migration**——沒有新資料表、沒有新資料庫欄位、沒有新端點。有新增語系 key（與 038 不同）。

部署順序：**後端先、前端後**。新欄位是純新增；新版前端搭舊版後端時讀到 `undefined`，判定函式回傳 `false`，四個畫面退回現行的直接加分——**不會壞，只是確認框不會出現**。回滾只要前端退版。

自動化測試：

```bash
# 後端（於 apps/api）
python -m pytest tests/contract -k "schedule or court_state"   # 兩個 schema 的新欄位
ruff check app/ tests/ && mypy app/

# 前端（於 apps/web）
npm test -- --watch=false
npm run lint && npx tsc --noEmit -p tsconfig.app.json
```

> 從 `.claude/worktrees/` 執行：後端把主 checkout 的 `apps/api/.venv/bin` 放到 `PATH`（`conftest.py` 會 shell out 到 `alembic`），前端 symlink 主 checkout 的 `node_modules`。**背景測試跑完之前不要結束回合**。

手動情境需要：一個**未啟用**「比賽詳細設定」的團、1 面場地、4 位球員、一場進行中的比賽。目標分 21、上限分 30（預設值）。四個畫面的連結都先準備好：管理頁、單一場地控制連結、全場地控制連結、記分板連結。

## 情境 1：一般賽末點會先確認（US1，FR-001～FR-004）

把比分打到 **20:15**，按下領先方的「+」。

**預期**：
- 分數**沒有**立刻加上去，先跳出確認框（FR-001）。
- 內容說明這一分會結束比賽、結果會計入戰績、無法復原（FR-002）。
- 按「確認」→ 分數變 21:15，比賽結束（FR-003）。

**再測一次取消**：重來一場打到 20:15，按「+」後按「取消」。
**預期**：比分**維持 20:15**、比賽仍在進行中，且可以立刻再按一次「+」正常運作（FR-004）。

## 情境 2：deuce 不會跳確認（US2 Scenario 2，FR-009）

把比分打到 **20:20**，按任一方的「+」。

**預期**：**不跳確認**，直接變成 21:20。因為只領先 1 分還沒贏——這是本功能最容易寫錯的地方。

接著在 **21:20** 按領先方的「+」。
**預期**：**跳確認**（22:20，達標且領先 2）。

## 情境 3：打到上限分會跳確認（US2 Scenario 3，FR-009）

把比分打到 **29:29**，按任一方的「+」。

**預期**：**兩邊都會跳確認**——達到上限分 30 即獲勝，不看分差（FR-010）。

順便確認 **28:29** 按下 28 那方的「+」**不跳**（29:29 既沒到上限、也沒領先 2）。

## 情境 4：不該打擾的時候完全不打擾（US2，FR-006、FR-007、SC-002）

從 0:0 一路計分到 19:15，全程計算跳出確認框的次數。

**預期**：**0 次**。點擊次數與本功能實作前完全相同。

任何比分下按「-1」。
**預期**：直接減分，不跳確認（FR-006）。

## 情境 5：詳細設定開啟時維持現狀（FR-005、SC-006）

到管理頁把「比賽詳細設定」**打開**，然後**換輪或開新的一場**（既有比賽沿用建立當下的快照）。把新的一場打到 20:15，按「+」。

**預期**：跳出的是 **038 的詳細記錄視窗**，**不是**本功能的確認框，而且不會先問一次再跳視窗。流程與 038 完成後完全相同。

## 情境 6：四個畫面一致（US3，FR-011）

同一場未啟用詳細設定的比賽打到 20:15，分別從**管理頁場地控制**、**單一場地控制連結**、**全場地控制板**、**記分板**按下決勝分的「+」。

**預期**：四個畫面都跳確認框，文案相同、確認與取消的行為相同。

## 情境 7：Esc 鍵取消後還能再按（research.md 風險註 1）

打到 20:15，按「+」跳出確認框後，**用鍵盤按 Esc** 關掉它。然後再按一次「+」。

**預期**：確認框**正常再次出現**。比分全程維持 20:15。

> 這一條務必手動測。`<dialog>` 的 Esc 關閉不會經過元件的 `cancel()`，而 jsdom 沒有實作 `<dialog>`，所以單元測試驗不出這條路徑。若實作把狀態清除掛在取消鈕而非原生 `close` 事件上，這裡就會卡死——按 Esc 之後決勝分再也按不動。

## 情境 8：取消後計分按鈕沒有被鎖死（research.md 風險註 2）

承情境 7，Esc 取消之後，先按幾次「-1」再按「+」。

**預期**：每一次都正常生效。若實作在開啟確認框前取得了計分防連點鎖，這裡會表現成「所有計分按鈕都沒反應」。

## 情境 9：快速連點決勝分（FR-014）

打到 20:15，**快速連按兩次**「+」。

**預期**：只跳一個確認框；確認後只加一分（21:15），不會變成 22:15。

## 情境 10：確認期間比分被別人改掉（Edge Case，FR-013）

打到 20:15，在管理頁按「+」跳出確認框後**先不要動**；用另一個畫面幫**對手**加一分（變 20:16）。回到管理頁按「確認」。

**預期**：該分正常計入變成 21:16，比賽**確實結束**（21:16 仍達標且領先 2）。

再測一次更極端的：20:20 的情況下不會跳確認，所以改用 **20:19** → 跳確認 → 期間對手追平到 20:20 → 按確認。
**預期**：變成 21:20，比賽**不結束**（只領先 1）——系統接受伺服器判定，不因為曾經跳過確認框就強制結束比賽。

## 情境 11：離線行為（FR-012）

切斷網路直到畫面出現離線提示，再按「+」。

**預期**：依既有離線規則停用，與其他計分操作一致。
