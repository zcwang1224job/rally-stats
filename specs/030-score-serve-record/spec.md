# Feature Specification: 加分時記錄發球者與站位資訊

**Feature Branch**: `030-score-serve-record`

**Created**: 2026-09-15

**Status**: Draft

**Input**: User description: "加分時候要紀錄發球者是哪一位球員，發球雙方的站位資訊"

## Clarifications

### Session 2026-09-15

- Q: 使用既有「-1」修正比分時，是否也要建立一筆對應的發球者/站位紀錄？ → A: 只有加分（+1）才記錄——貼近字面上「加分時候」的意思，-1 修正比分不會另外產生一筆發球/站位紀錄。
- Q: 這次功能範圍是否包含一個讓使用者事後查看這些發球/站位紀錄的畫面？ → A: 不包，只先完成資料紀錄——本次只做「加分時自動記錄」這件事，查看方式（是否新增畫面、要不要疊加在既有比分時間軸上）留待未來另行規劃。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 加分當下自動留下發球者與站位紀錄 (Priority: P1)

比賽進行中每次加分時，系統自動把「這一分是哪一位球員發球」以及「加分當下雙方球員各自的站位」保存下來，不需要計分員或球員另外手動輸入或操作。

**Why this priority**: 這是本功能最核心的行為——沒有「紀錄」這個動作，後續任何回顧、查詢、統計都無從談起。

**Independent Test**: 對一場正在進行中、已知目前發球者與站位的比賽加一分，之後查詢這次得分事件，確認除了比分本身之外，還能查到「誰發球」與「雙方站位」。

**Acceptance Scenarios**:

1. **Given** 一場正在進行中、目前發球者與站位已知的比賽，**When** 該場比賽加一分（比分變動），**Then** 系統 MUST 針對這次加分建立一筆對應紀錄，內容包含「這一分由哪一位球員發球」以及「加分當下雙方（單打 2 位、雙打 4 位）球員各自的站位」。
2. **Given** 一次加分已經留下對應的發球者/站位紀錄，**When** 之後重新整理計分板頁面、或關閉再重新打開，**Then** 剛才那筆紀錄 MUST 仍然存在，不會消失也不需要重新計算才能得知。

---

### User Story 2 - 每一分的紀錄各自獨立、不被後續動作覆蓋 (Priority: P2)

比賽持續進行、比分不斷變動時，每一分當初留下的發球者/站位紀錄必須維持原樣，不會因為之後又發生了更多加分（或修正比分）而被覆蓋或改寫成最新狀態。

**Why this priority**: 如果歷史紀錄會被之後的動作覆蓋掉，等於無法真正回顧「當時」的發球狀況，這筆資料的價值會大打折扣，但即使沒有這一層保證，User Story 1 的即時記錄仍有基本價值，因此優先度次之。

**Independent Test**: 對一場比賽連續加多分，檢查最早那一分的發球者/站位紀錄是否仍保留當時的原始內容，而不是被之後的分數覆蓋成最新狀態。

**Acceptance Scenarios**:

1. **Given** 一場比賽已經加過第一分並留下對應的發球者/站位紀錄，**When** 該場比賽之後又加了第二分、第三分，**Then** 第一分當初留下的發球者/站位紀錄 MUST 維持不變，不會被第二、三分的資訊覆蓋。
2. **Given** 一場比賽已經累積多筆發球者/站位紀錄，**When** 事後依序查詢這些紀錄，**Then** 查詢結果 MUST 依得分先後順序，各自對應到當時正確的發球者與站位，不會全部顯示成同一份「目前最新」的資訊。

---

### Edge Cases

- 比賽剛開始（0:0，尚未發生任何加分）時沒有任何得分事件，因此也不會有任何發球者/站位紀錄——這是預期狀態，不是缺漏。
- 比賽中途被取消或放棄（abandoned）時，已經留下的發球者/站位歷史紀錄 MUST 不受影響、繼續保留。
- 使用既有「-1」動作修正比分時，MUST NOT 建立對應的發球者/站位紀錄（Clarifications 2026-09-15）；已經留存的加分紀錄不受這次修正影響。
- 一場比賽的計分板連結被重新產生（既有的連結失效重發功能）後，先前已經留下的發球者/站位紀錄 MUST 不受影響，不會因為連結換了就消失或錯亂。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系統 MUST 在每一次比賽加分（既有的 +1 動作）發生時，建立一筆與該次得分事件相對應的紀錄，內容包含「這一分由哪一位球員發球」。
- **FR-002**: 系統 MUST 在同一筆紀錄中一併保存「加分當下雙方球員（單打 2 位、雙打 4 位）各自的站位」，比照既有「計分板發球站位顯示」功能所定義的正規發球順序規則計算而得。
- **FR-003**: 每一次加分產生的發球者/站位紀錄 MUST 各自獨立保存；之後再發生的加分或比分修正 MUST NOT 覆蓋掉先前已經留下的紀錄。
- **FR-004**: 使用既有「-1」動作修正比分時，系統 MUST NOT 建立對應的發球者/站位紀錄；只有「加分（+1）」動作才會建立這筆紀錄（Clarifications 2026-09-15）。
- **FR-005**: 系統 MUST 以資料形式保存每一分對應的發球者與站位資訊，使其具備既有比賽紀錄查詢權限的使用者未來可被取得；本次功能範圍不包含新增任何查看/顯示畫面，查看方式留待未來另行規劃（Clarifications 2026-09-15）。
- **FR-006**: 每一筆發球者/站位紀錄 MUST 在其對應的得分事件本身仍保留期間持續可查詢，不因計分板頁面重新整理、連結重新產生、或裝置切換而遺失或改變。
- **FR-007**: 系統 MUST NOT 在沒有發生加分動作的時間點（例如比賽尚未開始、或已結束後沒有新得分）建立發球者/站位紀錄。

### Key Entities *(include if feature involves data)*

- **得分發球紀錄（Score Serve Record）**：附屬於既有「得分事件」（每一次加分動作）的延伸資訊，記錄該次得分發生當下的發球者（哪一位球員）以及雙方球員（單打 2 位、雙打 4 位）各自的站位；每一次得分各自對應一筆，彼此獨立保存、不互相覆蓋。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 100% 的加分動作事後都能查到對應的發球者與站位紀錄，不會出現「有得分但查不到當時發球者」的缺漏。
- **SC-002**: 針對同一次歷史得分，不論何時查詢其發球者/站位紀錄，得到的結果都相同，不會因為比賽之後繼續進行而跟著改變。
- **SC-003**: 加分動作因為同時記錄發球者/站位資訊，使用者在計分板或控制板上感受到的加分反應速度與現況相比沒有變慢；此為非阻塞式的品質關卡，透過確認「新增的紀錄寫入與既有加分寫入共用同一次操作、不新增額外的網路往返」來驗證，不要求另外建置效能量測基礎設施。

## Assumptions

- 本功能所指「發球者」與「站位」之計算規則，沿用「計分板發球站位顯示」功能（029-serve-rotation-display）所定義的正規發球順序規則與站位定義，不重新定義一套新規則；若該功能尚未上線，本功能視為以其定義的規則為準的後續延伸，兩者共用同一套計算邏輯。
- 本功能記錄的對象是既有「得分事件」（每一次加分動作）機制，沿用其既有的保存期間與存取權限設計，不另外設計新的保留期限或存取權限規則。
- 本功能範圍為「記錄」本身；不包含另外設計畫面讓使用者查看這些歷史發球/站位資訊（Clarifications 2026-09-15），查看方式留待未來另行規劃。
