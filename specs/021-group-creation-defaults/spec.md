# Feature Specification: 開團流程優化——合理預設值與自動預設場地

**Feature Branch**: `[021-group-creation-defaults]`

**Created**: 2026-09-10

**Status**: Draft

**Input**: User description: "優化開團流程，開團建立頁面團名若沒有輸入，系統預設為 使用者暱稱+"的羽球團。比賽模式預設為單打，人數上限預設4人，排程機制預設為公平輪替，系統自動建立一個預設場地，名稱為"球場一"，並新增球場更名的功能"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 最少輸入即可完成開團 (Priority: P1)

我是想快速揪一場球局的使用者，我不想在開團當下還要想團名該取什麼、也不想逐一確認每個進階選項該選哪個。我希望「團名」欄位可以留空直接送出，系統會自動幫我用「我的暱稱＋的羽球團」當作團名；而比賽模式、人數上限、排程機制這些欄位，一打開表單就已經是最常見的組合（單打、4 人、公平輪替），我不需要逐一確認每一項才能送出。

**Why this priority**：這是使用者明確要求的核心優化——降低開團這個第一步驟的輸入門檻，讓「想打球」到「團建好了」之間的距離最短。這是整個功能存在的起點，沒有這一項，後續「開團後自動有球場」的價值也無從談起。

**Independent Test**：開啟開團表單，只填寫必要的帳號/密碼類欄位並把「團名」留空，直接送出，驗證團建立成功且團名自動帶入「{建立者暱稱}的羽球團」；再開一次表單，確認比賽模式/人數上限/排程機制三個欄位一開始就分別是單打/4人/公平輪替，不需要額外調整即可直接送出。

**Acceptance Scenarios**:

1. **Given** 使用者開啟開團表單，**When** 使用者將「團名」欄位留空並送出其餘必要資訊，**Then** 系統 MUST 成功建立團，且該團的名稱 MUST 為「{建立者暱稱}的羽球團」（建立者暱稱依實際身份：登入會員為其既有暱稱，訪客為本次填寫的暱稱）。
2. **Given** 使用者開啟開團表單，**When** 使用者查看「比賽模式」「人數上限」「排程機制」三個欄位的初始狀態（尚未手動調整前），**Then** 這三個欄位 MUST 分別已經是「單打」「4 人」「公平輪替」。
3. **Given** 使用者不滿意任何一項預設值，**When** 使用者手動修改團名或任一預設欄位，**Then** 系統 MUST 完全採用使用者手動輸入/選擇的值，不得被預設值覆蓋或限制原有可選範圍。

---

### User Story 2 - 開團後立即有可用球場 (Priority: P1)

我是剛建好團的團長，我希望團一建立好，系統就已經幫我準備好一個可以直接使用的球場，讓我不需要先跳到球場管理畫面手動新增一個球場，才能開始安排比賽、產生計分板連結。

**Why this priority**：沒有球場，整個團就無法真正開始運作（無法排點、無法計分）——這是開團流程裡最後一哩、卻常被忽略的必要步驟。自動補上這一步能讓「開團」到「可以開始打球」的距離最短，價值與 User Story 1 同等重要，因此並列最高優先度。

**Independent Test**：完成開團（不論團名/其他欄位是否使用預設值），立即查看球場管理畫面，驗證已經存在一個名為「球場一」的球場，且該球場與手動新增的球場一樣可以正常使用（產生計分板/控制板連結、被排入賽程等）。

**Acceptance Scenarios**:

1. **Given** 使用者剛成功建立一個團，**When** 使用者（或系統本身)查看該團的球場列表，**Then** 列表 MUST 已經包含一個名稱為「球場一」的球場，不需要任何額外操作。
2. **Given** 這個自動建立的「球場一」，**When** 團長對它執行既有球場可以做的任何操作（例如產生計分板連結、控制板連結、刪除、排入賽程），**Then** 這些操作 MUST 與對待任何手動新增的球場完全一致，不受任何特殊限制。
3. **Given** 開團流程本身因故失敗（例如驗證未通過、資料不合法），**When** 系統回報開團失敗，**Then** 系統 MUST NOT 留下任何因這次失敗嘗試而產生的球場資料。

---

### User Story 3 - 團長可以幫球場重新命名 (Priority: P2)

我是團長，不論是系統自動取名的「球場一」不夠好記，還是我當初手動新增球場時打錯字，我希望可以直接在球場管理畫面把球場改成我想要的名稱，不需要刪除重建（刪除重建會讓這個球場既有的計分板/控制板連結全部失效）。

**Why this priority**：這是延伸自動預設場地（User Story 2）而變得更有感的能力——場地一律先取名「球場一」，團長很可能想換成更好辨識的名字；但即使沒有這一項，User Story 1、2 的核心價值（開團快、開團後即可用）依然成立，因此優先度次於前兩者。

**Independent Test**：在球場管理畫面對任一現有球場（含自動建立的「球場一」）觸發更名，輸入合法的新名稱，驗證球場列表立即顯示新名稱、既有的計分板/控制板連結不受影響（不是重新產生一組新的）；再嘗試把名稱改成與同團內另一個現役球場相同，驗證系統拒絕並提示名稱重複。

**Acceptance Scenarios**:

1. **Given** 團長在球場管理畫面看到一個現有球場，**When** 團長觸發更名並輸入一個合法且不重複的新名稱，**Then** 系統 MUST 成功更新該球場的名稱，球場列表 MUST 立即顯示新名稱。
2. **Given** 球場更名成功，**When** 團長查看該球場既有的計分板連結、控制板連結，**Then** 這些連結 MUST 維持不變、仍可正常使用（更名不影響既有連結）。
3. **Given** 團內已存在一個名為「A」的現役球場，**When** 團長嘗試把另一個球場也更名為「A」，**Then** 系統 MUST 拒絕這次更名並提示名稱已被使用，MUST NOT 產生兩個同名的現役球場。
4. **Given** 團長想更名的目標球場已被刪除，**When** 團長嘗試對它更名，**Then** 系統 MUST 拒絕並提示該球場已不存在。

---

### Edge Cases

- 訪客身份開團時，「建立者暱稱」欄位本身仍 MUST 依既有規則為必填——本功能新增的是「團名」欄位的預設值，MUST NOT 連帶讓建立者暱稱也變成可留空。
- 使用者將團名欄位留空、但建立者暱稱這輸入了超長或含特殊字元的暱稱——預設團名的組成 MUST 沿用既有暱稱長度上限規則，組成後的團名 MUST 仍符合既有團名長度上限，不得因為自動組成而超出限制。
- 使用者把團名欄位填入純空白字元（看起來像留空但技術上不是空字串）——MUST 視同留空處理，套用預設團名，而不是把純空白字元當作合法團名送出。
- 系統已經支援雙打搭配「固定搭檔」「個人全混搭」等只在雙打才有意義的排程機制——比賽模式預設為單打時，MUST 確保預設的排程機制（公平輪替）在單打模式下本來就合法，不會出現「預設值本身互相衝突」的情況（沿用既有排程機制與比賽模式的既有相容性規則）。
- 更名時新名稱與球場自己目前的名稱完全相同（等於沒有實質變更）——系統 MUST 允許這種操作成功（視為不影響任何東西的合法更新），不得誤判為重複名稱而拒絕。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 開團表單的「團名」欄位 MUST 允許留空（或僅含空白字元）直接送出；此時系統 MUST 自動套用預設團名「{建立者暱稱}的羽球團」，建立者暱稱依實際建立身份決定（登入會員採其既有暱稱；訪客採本次開團填寫的暱稱）。
- **FR-002**: 開團表單的「比賽模式」欄位初始值 MUST 為「單打」。
- **FR-003**: 開團表單的「人數上限」欄位初始值 MUST 為 4 人。
- **FR-004**: 開團表單的「排程機制」欄位初始值 MUST 為「公平輪替」。
- **FR-005**: FR-001~FR-004 之預設值 MUST NOT 限制使用者的既有選擇彈性——使用者仍 MUST 能自由填寫任意合法團名、或切換為系統既有支援的任何其他比賽模式/人數上限/排程機制組合。
- **FR-006**: 團建立成功時，系統 MUST 在同一次建立流程中自動建立一個名稱為「球場一」的球場，使團長不需要額外手動新增即可擁有至少一個可用球場。
- **FR-007**: 若開團流程本身失敗（例如驗證未通過），系統 MUST NOT 建立任何因此次失敗嘗試而產生的球場資料——球場的建立 MUST 與團的建立視為同一個成功/失敗單位。
- **FR-008**: 自動建立的「球場一」MUST 與手動新增的球場具備完全相同的能力與限制（更名、刪除、產生計分板/控制板連結、排入賽程等），系統 MUST NOT 對它施加任何特殊限制或標記。
- **FR-009**: 團長 MUST 能在既有球場管理畫面，將任一現役球場（含自動建立的「球場一」）重新命名；命名規則（長度、允許字元）MUST 與既有新增球場時的既有規則一致。
- **FR-010**: 球場更名成功後，MUST 保留該球場既有的計分板連結與控制板連結不變（不得因更名而失效或重新產生新連結），球場列表與既有引用該球場名稱的既有畫面 MUST 立即反映新名稱。
- **FR-011**: 若更名後的名稱與該團內另一個現役球場的名稱重複，系統 MUST 拒絕本次更名並明確提示名稱重複，MUST NOT 產生兩個同團內同名的現役球場；更名為與自己目前名稱相同時 MUST 視為合法操作允許成功。

### Key Entities *(include if feature involves data)*

- **（既有）Group（團）**：本功能新增「團名可由系統依建立者暱稱自動產生預設值」的規則，以及「比賽模式/人數上限/排程機制」表單初始值的既定慣例；不新增欄位。
- **（既有）Court（球場）**：本功能新增「團建立時系統自動建立一筆初始球場資料」的規則，以及「團長可重新命名」的操作入口；不新增欄位，沿用既有的命名唯一性與計分板/控制板連結機制。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**：使用者只需要填寫帳號/密碼等既有必要欄位、完全不觸碰團名與其他進階選項，即可在 15 秒內成功建立一個可用的團。
- **SC-002**：100% 成功建立的團，在建立完成的當下就已經擁有至少一個名為「球場一」的可用球場，不需要團長任何額外操作。
- **SC-003**：團長在球場管理畫面觸發更名，合法且不重複的名稱 100% 更名成功，且既有的計分板/控制板連結 100% 維持可用、不失效。
- **SC-004**：嘗試把球場改為與團內另一現役球場相同的名稱時，100% 被系統正確拒絕，不會產生重複命名的現役球場。

## Assumptions

- 「使用者暱稱」在計算預設團名時，沿用既有「建立者暱稱」判斷邏輯——登入會員身份開團時為其既有會員暱稱，訪客身份開團時為本次開團表單所填寫的暱稱；此邏輯本身不受本功能影響，訪客仍 MUST 依既有規則填寫暱稱才能開團。
- 球場更名所需的後端更名能力（含名稱唯一性檢查、既有連結不受影響）已經存在於系統中；本功能的實際範圍是在既有球場管理畫面新增對應的操作入口，讓團長能夠使用這個既有能力，不需要重新設計更名機制本身。
- 自動建立的「球場一」在建立當下即為現役、立即可用狀態，與手動新增球場的既有生命週期完全一致，不引入新的球場狀態。
- 比賽模式/人數上限/排程機制的預設值只決定表單「尚未被使用者更動」時的初始畫面狀態，不改變系統既有支援的欄位組合範圍或既有的欄位間相容性規則（例如僅雙打適用的排程機制，選擇規則維持既有邏輯不變）。
- 團名的長度上限沿用既有規則；自動組成的預設團名（暱稱＋「的羽球團」）在既有暱稱長度上限下，恆能符合既有團名長度上限，不需要額外的截斷處理。
