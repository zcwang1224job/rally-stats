# Quickstart: 開團流程優化——合理預設值與自動預設場地

## 前置條件

- 後端、前端服務皆已啟動。
- 一個有效的 Turnstile token（測試環境用既有固定通過用 token）。

## 情境 1：團名留空，自動帶入「{暱稱}的羽球團」（US1）

1. 開啟開團表單（登入會員或訪客身份皆可），不填寫「團名」欄位，填妥
   其餘必要欄位（訪客身份需另外填寫暱稱）。
2. 送出。
   **預期**：`201`，建立成功；查詢該團詳情，`name` MUST 為
   「{建立者暱稱}的羽球團」（登入會員用其既有會員暱稱；訪客用本次
   填寫的暱稱，contracts/group-and-court-api.md）。
3. 重複步驟 1，改為在團名欄位輸入純空白字元（例如兩個空格）後送出。
   **預期**：MUST 視同留空，同樣自動帶入預設團名，MUST NOT 把純空白
   字元當作合法團名寫入。

## 情境 2：開團表單初始值為單打／4 人／公平輪替（US1）

1. 開啟開團表單，尚未手動調整任何欄位。
2. 查看「比賽模式」「人數上限」「排程機制」三個欄位的畫面初始狀態。
   **預期**：分別已經是「單打」「4 人」「公平輪替」，不需要使用者
   額外操作即可直接送出（spec.md FR-002~FR-004）。

## 情境 3：開團後立即有一個名為「球場一」的球場（US2）

1. 依情境 1 或任意合法輸入完成一次開團。
2. 使用回應中的 `admin_token` 呼叫既有
   `GET /groups/{group_id}/courts`。
   **預期**：`200`，球場列表 MUST 已包含一筆名稱為「球場一」的球場，
   不需要團長任何額外操作（contracts/group-and-court-api.md）。
3. 對這個自動建立的球場，呼叫既有「產生計分板連結」等既有球場操作。
   **預期**：MUST 與對任何手動新增的球場完全一致地成功，不受任何
   特殊限制（spec.md FR-008）。

## 情境 4：開團失敗時不留下孤兒球場（US2 Edge Case）

1. 送出一個必然失敗的開團請求（例如 Turnstile token 無效）。
   **預期**：開團請求本身回傳既有錯誤代碼（例如
   `CAPTCHA_INVALID`），MUST NOT 有任何新球場被建立（因為整個團本身
   都沒有建立成功，spec.md FR-007）。

## 情境 5：團長在球場管理畫面重新命名球場（US3）

1. 開啟球場管理畫面（既有「場地」區塊），對任一現有球場（含自動建立
   的「球場一」）觸發「重新命名」。
2. 輸入一個合法且不重複的新名稱並確認。
   **預期**：`200`，球場列表 MUST 立即顯示新名稱；該球場既有的計分板
   連結、控制板連結 MUST 維持原樣可用（不是重新產生的新連結，
   contracts/group-and-court-api.md）。
3. 嘗試把某個球場更名為與同團內另一個現役球場相同的名稱。
   **預期**：`409`，`error_code: "COURT_NAME_ALREADY_EXISTS"`，畫面
   MUST 顯示明確的名稱重複提示，MUST NOT 產生兩個同名現役球場。
4. 把某個球場更名為它目前自己的名稱（沒有實質變更）。
   **預期**：`200`，MUST 視為合法操作成功，MUST NOT 被誤判為重複
   名稱而拒絕（spec.md Edge Cases）。

## 驗證通過標準

- 所有情境的「預期」項目皆吻合。
- `pytest`（後端單元/契約測試，含本 feature 新增、原本完全缺少的
  `rename_court()`／`PATCH /courts/{court_id}` 測試）與 `ng test`
  （Vitest，前端）皆全數通過；`ruff`/`mypy --strict`/`ng lint` 皆無
  錯誤（憲章技術治理關卡）。
- 既有 `test_create_group.py`（001-create-manage-group）與既有球場
  相關測試（002-court-management）全數維持通過，證明本次調整未破壞
  既有開團/球場管理行為（回歸驗證）。
