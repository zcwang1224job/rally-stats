# Feature Specification: 團長手動新增訪客入團

**Feature Branch**: `015-manual-add-guest`

**Created**: 2026-09-08

**Status**: Draft

**Input**: User description: "開團後輪替名單，團長可以手動新增guest（非會員）入團。"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 團長手動新增一位訪客加入輪替名單 (Priority: P1)

團長在開團後，遇到臨時到場、但不方便自行掃碼/輸入密碼加入的球友（例如球友沒帶手機、網路不穩、或團長想直接用自己手機快速登記），可以直接在管理介面輸入這位球友的暱稱，將對方加入該團的輪替名單，不需要對方自行完成加入流程。

**Why this priority**: 這是本功能的核心價值——省去「請對方自行加入」這一步，讓團長能主導現場人員登記，是唯一 P1 才具備 MVP 價值的行為。

**Independent Test**: 團長開一個尚有名額的團，在管理介面手動新增一位暱稱「小明」的訪客，重新整理名冊後「小明」以現役成員身份出現在輪替名單中，且能被排入下一場比賽。

**Acceptance Scenarios**:

1. **Given** 一個現役（未解散）且未達人數上限的團，**When** 團長輸入暱稱並送出「新增訪客」，**Then** 系統建立一筆現役的訪客名冊項目，該訪客立即出現在輪替名單中，並以「尚未上場」狀態參與排點。
2. **Given** 該團目前人數已達 `max_members` 上限，**When** 團長嘗試新增訪客，**Then** 系統拒絕新增，明確提示「已達人數上限」，不建立任何名冊項目。
3. **Given** 團長已成功新增一位訪客，**When** 團長不重新開啟新增流程、直接再輸入下一位暱稱，**Then** 系統允許連續新增多位訪客，不強制中斷流程。

---

### User Story 2 - 團長取得新增訪客的個人查看連結，轉交給對方 (Priority: P2)

團長新增訪客後，若這位訪客其實有帶手機、只是不方便自己完成加入流程，團長可以直接把系統產生的個人查看連結（或 QR code）轉發給對方，讓對方之後能用自己的手機查看賽況與通知，體驗與「自行加入」的訪客一致。

**Why this priority**: 這是在 P1（純登記）之上的加值體驗——沒有它，訪客仍能正常參與比賽與統計，只是無法用自己的裝置查看即時賽況；有了它，手動新增與自行加入的訪客體驗才完全對等。

**Independent Test**: 團長新增一位訪客後，管理介面立即顯示一組可複製的連結／QR code；用另一支裝置開啟該連結，能看到這位訪客本人的即時賽況與輪替狀態，且不需要再輸入密碼。

**Acceptance Scenarios**:

1. **Given** 團長剛成功新增一位訪客，**When** 新增流程完成，**Then** 管理介面立即顯示該訪客專屬的可分享連結／QR code。
2. **Given** 團長已取得某位手動新增訪客的連結，**When** 該訪客本人用自己的裝置開啟此連結，**Then** 對方能直接看到自己的賽況與輪替狀態，無需再次輸入密碼或走一次加入流程。

---

### Edge Cases

- 團長嘗試在已解散的團新增訪客 → 系統拒絕，提示團已解散。
- 暱稱留空、全空白或超過長度限制 → 系統拒絕，比照現行訪客自行加入時的暱稱驗證規則。
- 同一團內已存在相同暱稱的成員 → 允許新增（沿用現行「同團暱稱不要求唯一」的既有規則，不因手動新增而額外限制）。
- 手動新增的訪客之後被團長踢出 → 沿用既有踢人功能即可涵蓋，不需要新的踢人邏輯。
- 團長在新增當下，剛好有其他人透過自行加入使名額滿了（併發搶名額）→ 系統仍需正確擋下超額新增，不得讓現役人數超過 `max_members`。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系統 MUST 讓通過管理驗證的團長，在自己開的團中手動新增一位訪客（非會員）加入輪替名單，只需輸入該訪客的暱稱。
- **FR-002**: 系統 MUST 對手動新增套用與訪客自行加入相同的人數上限檢查（現役人數需小於 `max_members`），額滿時拒絕新增並提示已滿，不建立名冊項目。
- **FR-003**: 手動新增成功後，該訪客 MUST 立即出現在輪替名單中，並以「尚未上場」的初始狀態參與排點，行為與自行加入的訪客完全一致。
- **FR-004**: 手動新增動作 MUST NOT 要求團長輸入該團的加入密碼——此動作已由管理身份驗證把關，無需再次驗證密碼。
- **FR-005**: 系統 MUST 允許暱稱與團內其他既有成員重複（沿用現行規則，不新增唯一性限制）。
- **FR-006**: 手動新增訪客成功後，系統 MUST 提供一組專屬於該訪客的可分享連結／QR code；團長可將此連結轉交給該訪客本人，讓對方之後能用自己的裝置查看個人賽況與輪替狀態，無需再輸入密碼或另外走一次加入流程（體驗對等於自行加入的訪客）。
- **FR-007**: 手動新增功能 MUST 僅適用於現役（未解散）的團；已解散的團 MUST 拒絕新增。
- **FR-008**: 手動新增的訪客名冊項目 MUST 可比照既有訪客項目，被團長透過既有踢人功能移除。
- **FR-009**: 系統 MUST 支援團長連續新增多位訪客，不強制每新增一位就重新開啟一次新增流程。
- **FR-010**: 系統 MUST 在名額因併發（例如同時有人自行加入）而被搶走時，正確擋下手動新增，避免現役人數超過 `max_members`。

### Key Entities *(include if feature involves data)*

- **輪替名單項目（Roster Entry）**：代表一位參與該團輪替與比賽的人員，可能是會員或訪客。本功能新增的是「由團長手動建立、而非本人操作」的訪客項目，與訪客自行加入建立的項目在資料意義與後續行為（排點、統計、被踢出）上完全對等，僅差在建立者是團長而非訪客本人。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 團長能在 30 秒內，於已開好且未額滿的團中新增一位訪客，並讓對方出現在輪替名單中。
- **SC-002**: 手動新增的訪客一旦加入，100% 能與其他成員一樣被正常排入比賽，不需要額外設定或修正步驟。
- **SC-003**: 當團已達人數上限時，100% 的手動新增嘗試會被系統擋下並清楚告知已滿，不會產生超額的名冊項目。
- **SC-004**: 團長新增訪客完成後，能在 10 秒內取得可轉交給該訪客的個人查看連結／QR code。

## Assumptions

- 團長的身份驗證沿用現有管理端驗證機制（即目前踢人、管理面板等功能所使用的同一套團長身份驗證），本功能不引入新的驗證方式。
- 手動新增的訪客資料在系統內部的呈現方式，比照現行「訪客自行加入」建立的項目（無會員帳號綁定），本功能不改變既有訪客資料的呈現方式，只新增「由團長代為建立」這個路徑。
- 暱稱長度與必填規則沿用現行訪客自行加入時的既有驗證規則。
- 本功能不涉及訪客的其他個人資料蒐集（例如聯絡方式），僅需暱稱即可完成新增。
