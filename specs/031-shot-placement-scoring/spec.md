# Feature Specification: 落點詳細計分模式

**Feature Branch**: `031-shot-placement-scoring`

**Created**: 2026-09-16

**Status**: Draft

**Input**: User description: "新增另一種計分方式：繪製一張羽球場的圖，計分時可以在場上標注一個點來記錄羽球落點，並選擇是哪位球員得分，同時記錄下該次得分的落點座標與得分球員，作為比較詳細的計分紀錄模式"

## Clarifications

### Session 2026-09-16

- Q: 落點標記的輸入方式是自由座標還是固定分區？ → A: 自由座標——在球場示意圖上任意點一點，記錄精確的相對座標（浮點數 x/y），不侷限於固定分區格子。
- Q: 詳細計分模式的設定粒度是團層級還是場地層級？ → A: 團層級——跟現有計分板加減分開關（`scoreboard_scoring_enabled`）一致，整個團所有場地共用同一個計分模式設定，不提供場地各自獨立選擇的精細度。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 加分時標記落點與得分球員 (Priority: P1)

計分員（控制板或計分板操作者）在啟用「詳細計分模式」的比賽中要加一分時，畫面顯示一張球場示意圖；計分員在圖上點選羽球實際落地的位置，接着從這場比賽的球員中選出這一分歸功於哪一位球員，確認後系統才真正把分數加一，並把「這一分落在哪裡」與「是哪位球員得分」一併保存下來。

**Why this priority**: 這是本功能存在的唯一理由——沒有這個標記＋選人的互動，就沒有「詳細計分模式」，只是既有的 +1/-1。

**Independent Test**: 對一場已啟用詳細計分模式、正在進行中的比賽執行一次加分：在球場圖上點一個位置、選一位球員、確認，之後查詢該次得分事件，確認能同時查到當初點選的落點座標與所選的球員，且比分確實加一。

**Acceptance Scenarios**:

1. **Given** 一場啟用詳細計分模式、正在進行中的比賽，**When** 計分員在球場示意圖上點選一個落點、選擇一位球員、並確認，**Then** 系統 MUST 將該球員所屬隊伍的比分加一，並建立一筆對應紀錄同時保存這次的落點座標與所選球員。
2. **Given** 計分員已經在球場圖上點選了一個落點，**When** 計分員在確認送出前改點另一個位置或改選另一位球員，**Then** 系統 MUST 以最後一次點選/選擇為準，MUST NOT 因為中途改過主意就記錄下第一次的暫時選擇。
3. **Given** 一場單打比賽（僅 2 位球員）與一場雙打比賽（4 位球員），**When** 計分員進行選擇球員的步驟，**Then** 系統 MUST 只列出該場比賽實際的參賽球員（單打 2 位、雙打 4 位），不得出現非本場參賽者。

---

### User Story 2 - 依團選擇要用簡易計分或詳細計分模式 (Priority: P2)

團的管理員可以針對自己的團設定，這個團之後開始的比賽要用既有的「+1/-1」簡易計分，還是這次新增的「標記落點＋選球員」詳細計分模式；兩者互斥，計分員在同一場比賽中只會看到其中一種介面。

**Why this priority**: 沒有這一層設定，User Story 1 的互動就沒有開關可以決定何時出現，且會強迫所有團都改用比較費工的新流程，但即使沒有這一層，User Story 1 本身作為單一比賽的行為仍可獨立驗證，因此優先度次之。

**Independent Test**: 將某團設定改為詳細計分模式後，之後新建立的比賽開啟計分介面時看到的是落點標記流程；未變更設定的團，比賽開啟計分介面時仍是既有的 +1/-1 按鈕。

**Acceptance Scenarios**:

1. **Given** 一個原本使用簡易計分的團，**When** 管理員將該團設定改為詳細計分模式，**Then** 系統 MUST NOT 影響任何已經在進行中的比賽——這些比賽 MUST 繼續使用它們建立當下就已經決定的計分模式。
2. **Given** 管理員已將團設定改為詳細計分模式，**When** 該團之後建立新的比賽，**Then** 該場新比賽的計分介面 MUST 是落點標記＋選球員的流程，MUST NOT 是舊的 +1/-1 按鈕。

---

### User Story 3 - 修正錯誤的一分時，連同落點紀錄一起處理 (Priority: P3)

計分員在詳細計分模式下標錯落點或選錯球員時，可以用既有的「修正比分」操作把最後一分收回；系統收回分數的同時，也會一併移除那一分當初留下的落點與球員紀錄，避免留下一筆「分數已經不算了，但落點紀錄還在」的不一致資料。

**Why this priority**: 這是資料正確性的保護機制，重要但只有在計分員按錯／選錯時才會用到，發生頻率遠低於 User Story 1 的每分必經流程，因此優先度最低。

**Independent Test**: 在詳細計分模式下記錄一分後，執行既有的「修正比分（-1）」，查詢該場比賽的落點紀錄，確認剛剛那一分的落點與球員紀錄已經一併消失，且比分正確地少了一分。

**Acceptance Scenarios**:

1. **Given** 詳細計分模式下已經記錄了一分（含落點與球員），**When** 計分員對該隊執行既有的修正比分操作，**Then** 系統 MUST 將該隊比分減一，且 MUST 一併移除最後一筆落點與球員紀錄，不得只改分數卻留下舊紀錄。
2. **Given** 詳細計分模式下的比賽尚未有任何一分被記錄（0:0），**When** 計分員嘗試修正比分，**Then** 系統的行為 MUST 與既有簡易模式在同一情境下的行為一致（例如比分維持在下限、不產生負數），不因為是詳細模式而有不同表現。

---

### Edge Cases

- 修正比分移除落點紀錄時，MUST 只移除「最後一筆」，不影響更早之前已經記錄的其他落點/球員紀錄（呼應 User Story 3）。
- 比賽中途被取消或放棄（abandoned）時，已經記錄下來的落點/球員歷史紀錄 MUST 不受影響、繼續保留，比照既有比賽紀錄完整性原則。
- 計分員點選的落點若落在球場示意圖邊界之外（例如明顯出界或手滑點到圖外），系統 MUST 仍然允許記錄（落點座標本身就可能代表「出界」這個事實），MUST NOT 因為落點在邊界外就拒絕這次加分。
- 一場比賽的計分板連結被重新產生（既有的連結失效重發功能）後，先前已經留下的落點/球員紀錄 MUST 不受影響。
- 團的計分模式設定變更時，MUST NOT 回溯影響已在進行中的比賽（呼應 User Story 2 Acceptance Scenario 1，比照既有團設定變更的時間一致性原則）。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系統 MUST 提供一個「詳細計分模式」，計分時以「球場示意圖上點選落點 → 選擇得分球員 → 確認」取代既有的 +1 按鈕動作。
- **FR-002**: 計分員完成落點與球員的選擇並確認後，系統 MUST 將所選球員所屬隊伍的比分加一，且 MUST 建立一筆與這次得分事件相對應的紀錄，內容包含「落點座標」與「得分球員」。
- **FR-003**: 系統 MUST 允許計分員在確認送出之前，重新點選落點或重新選擇球員；確認前的暫時選擇 MUST NOT 被記錄下來，只有最終確認的內容才會被保存（Acceptance Scenario US1-2）。
- **FR-004**: 球員選擇畫面 MUST 只列出當場比賽實際的參賽者（單打 2 位、雙打 4 位），MUST NOT 列出非本場比賽的球員。
- **FR-005**: 系統 MUST 提供團層級的設定，讓管理員可以選擇該團之後建立的比賽要使用既有簡易（+1/-1）計分模式，或這次新增的詳細計分模式；兩者 MUST 互斥，同一場比賽只會使用其中一種計分介面。
- **FR-006**: 團的計分模式設定變更 MUST 只影響變更之後才建立的新比賽，MUST NOT 影響任何已在進行中的比賽；已在進行中的比賽 MUST 維持其建立當下適用的計分模式不變，比照既有團設定變更的時間一致性原則。
- **FR-007**: 系統 MUST 提供既有「修正比分」操作在詳細計分模式下的對應版本：執行時 MUST 將比分減一，且 MUST 同時移除最後一筆落點/球員紀錄，MUST NOT 只改動比分而遺留舊紀錄（Acceptance Scenario US3-1）。
- **FR-008**: 詳細計分模式下每一分產生的落點/球員紀錄 MUST 各自獨立保存，除了透過既有修正比分操作明確收回最後一分之外，MUST NOT 被其他任何動作覆蓋或竄改。
- **FR-009**: 比賽中途被取消或放棄（abandoned）時，系統 MUST NOT 刪除或修改該場比賽已經留存的落點/球員歷史紀錄。
- **FR-010**: 落點座標的記錄 MUST 允許代表球場示意圖邊界之外的位置，MUST NOT 因為落點判定為出界就拒絕記錄這次得分。

### Key Entities *(include if feature involves data)*

- **落點得分紀錄（Shot Placement Record）**：附屬於既有「得分事件」（詳細計分模式下的每一次加分動作）的延伸資訊，記錄該次得分的落點座標（相對於球場示意圖的自由座標，例如 x/y 各為 0~1 的浮點數，而非固定分區代號——Clarifications 2026-09-16）與得分球員（該場比賽的參賽者之一）；每一次得分各自對應一筆，彼此獨立保存。
- **團計分模式設定（Scoring Mode Setting）**：附屬於既有團設定的新選項，決定該團之後建立的比賽要用「簡易（+1/-1）」或「詳細（落點＋球員）」計分模式；粒度為團層級（跟現有 `scoreboard_scoring_enabled` 一致，Clarifications 2026-09-16），該團所有場地共用同一設定，不提供場地各自獨立選擇。變更只影響之後新建立的比賽，並在比賽建立當下快照決定該場比賽採用的模式。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 計分員在詳細計分模式下完成一次完整加分（點落點、選球員、確認）所需時間，中位數在 10 秒以內，確保不會明顯拖慢現場比賽節奏。
- **SC-002**: 100% 詳細計分模式下實際計入比分的得分，事後都能查到對應的落點與球員紀錄；100% 被修正比分收回的得分，其對應紀錄也會一併消失，不會出現「有分數但查無紀錄」或「有紀錄但分數對不上」的落差。
- **SC-003**: 針對同一次歷史得分，不論何時查詢其落點/球員紀錄，得到的結果都相同，不會因為比賽之後繼續進行而跟著改變。
- **SC-004**: 團的管理員能在一分鐘內、不需要額外說明，就能找到「切換計分模式」的設定入口並成功套用。

## Assumptions

- 落點座標僅代表「這一分結束當下，計分員判斷羽球落地的位置」，屬於人工輸入的描述性資訊，系統 MUST NOT 依落點座標自動判定得分歸屬（是否出界、哪隊得分）——得分歸屬完全由計分員選擇的球員決定，落點只是附加的視覺化細節，不影響比分計算邏輯本身。
- 詳細計分模式與既有「計分板發球站位顯示」（029）、「加分時記錄發球者與站位資訊」（030）兩個功能各自獨立、互不取代：即使一場比賽採用詳細計分模式，029/030 既有的發球者/站位計算與記錄邏輯 MUST 照常運作，不因為改用詳細計分模式而停用。
- 本功能範圍為「記錄」本身以及必要的計分互動（球場圖點選、選球員、修正比分的對應處理）；事後瀏覽/視覺化整場比賽落點分布的分析畫面不在本次範圍內，比照 030 的既有前例，留待未來另行規劃。
- 團的計分模式設定比照既有「計分板加減分開關（scoreboard_scoring_enabled）」等團級別設定的存取權限與變更流程，僅團管理員可在管理頁修改，不另外設計新的權限模型。
- 落點採自由座標而非固定分區（Clarifications 2026-09-16）；確切的座標原點/軸向定義、球場示意圖外觀、是否分單打/雙打場地樣式等視覺呈現細節，留待 `/speckit-plan` 階段決定。
