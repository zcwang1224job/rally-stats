# Feature Specification: 刪除帳號

**Feature Branch**: `025-delete-account`

**Created**: 2026-09-14

**Status**: Draft

**Input**: User description: "刪除帳號功能：會員可以刪除自己的帳號。考量到比賽紀錄、輪替名單等資料與其他會員共享（對手、隊友的歷史戰績會引用到這個帳號），刪除時採用匿名化處理（清空 email、密碼雜湊、暱稱改為預設佔位符），帳號立即無法登入，但保留資料列讓既有比賽紀錄不會出現斷裂。需考量台灣個資法與 GDPR 被遺忘權的合理保留期間，以及既有的驗證信/密碼重設 token 需一併失效。"

## Clarifications

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 會員刪除自己的帳號 (Priority: P1)

已登入的會員在個人設定中找到「刪除帳號」選項，經過明確的二次確認後，該帳號被永久刪除（以匿名化方式處理）：帳號立即無法再用於登入，個人資料（Email、密碼、暱稱等可識別個人身分的資訊）被清除或替換為系統預設的佔位內容。

**Why this priority**：這是「刪除帳號」功能本身唯一的核心價值——沒有這個流程，使用者無法行使個資法賦予的刪除權利，功能就不存在。

**Independent Test**：可獨立測試——已登入會員完成刪除帳號流程後，確認無法再用原本的 Email/密碼登入，且該帳號的個人資料已被清除。

**Acceptance Scenarios**:

1. **Given** 已登入且信箱已驗證的會員，**When** 該會員在個人設定中選擇「刪除帳號」並完成二次確認，**Then** 系統 MUST 將該帳號標記為已刪除、清除其 Email 與密碼、將暱稱改為系統預設的佔位文字。
2. **Given** 會員剛完成刪除帳號流程，**When** 該會員（或任何人）嘗試用原本的 Email/密碼登入，**Then** 系統 MUST 拒絕登入。
3. **Given** 會員剛完成刪除帳號流程且當下瀏覽器仍持有登入狀態（尚未登出），**When** 該瀏覽器嘗試繼續使用任何需要登入的功能，**Then** 系統 MUST 視同已登出，要求重新登入（並會失敗，見情境2）。
4. **Given** 會員在「刪除帳號」確認畫面，**When** 該會員取消或未完成確認步驟，**Then** 帳號 MUST 維持原狀不受影響。
5. **Given** 已刪除的帳號原本持有尚未使用的信箱驗證信或密碼重設信連結，**When** 任何人嘗試使用該連結，**Then** 系統 MUST 拒絕（視為無效/已失效）。

---

### User Story 2 - 其他會員查看的既有紀錄不因對方刪除帳號而毀損 (Priority: P2)

已刪除帳號之會員曾經參與的比賽紀錄、曾經加入的團隊輪替名單、曾經建立的好友關係等，對其他仍在使用系統的會員而言，MUST 維持可正常瀏覽，只是該已刪除會員的身分改以系統預設的佔位名稱顯示，不會造成頁面錯誤或資料缺漏。

**Why this priority**：這是本功能「匿名化而非直接刪除資料列」設計選擇存在的意義——如果做不到，直接刪除資料列的簡單做法就足夠了，不需要匿名化的額外複雜度。因此重要，但需要先有 User Story 1（帳號真的能被刪除）才有東西可測試，故列為 P2。

**Independent Test**：可獨立測試——準備一筆已被匿名化的會員資料（模擬情境），確認其他會員查看與其共同參與過的比賽紀錄、團隊歷史時，畫面正常顯示、不出現系統錯誤，且該已刪除會員顯示為系統預設佔位名稱。

**Acceptance Scenarios**:

1. **Given** 甲會員已刪除帳號，乙會員曾與甲會員在同一場比賽對戰過，**When** 乙會員查看該場比賽的對戰紀錄（不論是甲會員刪除帳號前很久參加的舊比賽，或是刪除前才剛結束的比賽），**Then** 系統 MUST 正常顯示該筆紀錄，且甲會員在該筆歷史紀錄中的暱稱 MUST 顯示為系統預設佔位文字，MUST NOT 顯示甲會員當初實際使用的暱稱（Clarifications 2026-09-14）。
2. **Given** 甲會員已刪除帳號且甲會員曾是某個揪團的建立者，**When** 任何人查看該揪團的資訊，**Then** 該揪團 MUST 維持正常運作（場地、賽程、其他成員不受影響）。

---

### Edge Cases

- 使用者嘗試刪除一個**尚未完成 Email 驗證**的帳號：MUST 仍允許刪除（既有規則是未驗證帳號不能用大部分功能，但刪除自己的帳號本身不應該被這條規則卡住）。
- 使用者是**目前有效揪團的建立者**：刪除帳號 MUST NOT 因此被阻擋或要求先解散揪團——揪團在會員刪除後依 User Story 2 的方式繼續正常運作。
- 使用者刪除帳號當下，還有**其他裝置正在使用同一個帳號的有效登入狀態**：MUST 使其失效（見 US1 情境3）。
- 使用者刪除帳號後，**同一個 Email 是否能被拿去重新註冊一個全新帳號**：MUST 可以——匿名化已清空該 Email，原本「Email 必須唯一」的限制不再視該筆已刪除資料為佔用。
- 使用者刪除帳號當下，**該會員在某個團隊仍有進行中（尚未結束）的比賽**：FR-003a 的歷史暱稱快照覆寫 MUST 同樣套用在這類「進行中」的輪替名單紀錄上，不僅限於已結束的比賽——賽程/計分板上正在觀看的其他人，之後看到的也 MUST 是佔位文字，而不是等比賽結束才生效。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系統 MUST 提供已登入會員一個刪除自己帳號的操作入口（個人設定內）。
- **FR-002**: 刪除帳號前，系統 MUST 要求明確的二次確認，防止誤觸（符合既有「破壞性操作需二次確認」原則）。
- **FR-003**: 確認刪除後，系統 MUST 立即清除該帳號的 Email、密碼（雜湊值）、暱稱等可識別個人身分的欄位，暱稱 MUST 替換為系統預設的佔位文字。
- **FR-003a**: 刪除帳號 MUST 一併將該會員過去在所有團隊留下的歷史暱稱快照（即比賽紀錄、輪替名單等畫面顯示暱稱時所依據的獨立快照欄位，非即時讀取帳號暱稱）覆寫為與 FR-003 相同的系統預設佔位文字（Clarifications 2026-09-14）。此為「刪除帳號」情境下對既有「一般改暱稱 MUST NOT 連動更新歷史快照」原則的刻意例外，範圍僅限帳號刪除流程本身，MUST NOT 套用於會員平常主動修改暱稱的既有功能。
- **FR-004**: 刪除帳號後，該帳號 MUST 立即無法登入（含原本 Email/密碼組合，以及任何裝置上已存在的有效登入狀態）。
- **FR-005**: 刪除帳號後，該帳號原本尚未使用的信箱驗證信 token、密碼重設信 token MUST 一併失效。
- **FR-006**: 系統 MUST NOT 直接刪除該會員在比賽紀錄、輪替名單、好友關係、揪團建立者等資料表中的關聯資料列——這些資料 MUST 保留，避免其他會員查看歷史紀錄時發生資料缺漏或錯誤（User Story 2）。
- **FR-007**: 刪除帳號後，該帳號的 Email MUST 被視為未使用，允許用同一個 Email 重新註冊全新帳號。
- **FR-008**: 刪除帳號 MUST 是會員本人才能對自己的帳號執行的操作，系統 MUST NOT 提供任何非本人（含其他會員）代為刪除他人帳號的途徑。
- **FR-009**: 已刪除的帳號 MUST 不再出現在其他會員的好友列表中，即使刪除前雙方已是好友關係（Session 2026-09-14 追加）——與比賽紀錄/輪替名單等歷史紀錄（FR-006，保留並以佔位名稱顯示）不同，好友列表是「目前有效關係」的呈現，不適用「維持顯示歷史」的原則。既有的好友關係資料列本身不刪除（仍可能供其他用途），僅在好友列表的讀取畫面排除已刪除的一方。
- **FR-010**: 比賽紀錄、輪替名單等歷史紀錄畫面顯示已刪除帳號的佔位暱稱時，MUST 使用與一般（未刪除）暱稱有區隔的顏色標示，讓使用者能一眼辨識「這是已刪除的帳號」（Session 2026-09-14 追加）。顏色僅為輔助辨識——佔位暱稱本身的文字（與真實暱稱不同）才是主要區隔依據，不得只靠顏色傳達此狀態。

### Key Entities

- **會員帳號（Member）**：刪除後轉為「已刪除」狀態——Email、密碼雜湊、暱稱等個人識別資訊被清除或替換為佔位值，但帳號本身的資料列與其唯一識別碼（member id）保留，讓既有的比賽紀錄、輪替名單、好友關係、揪團建立者等關聯資料能持續正確關聯到這個「已刪除的使用者」身分。
- **歷史暱稱快照（例如輪替名單中每筆成員紀錄各自保存的暱稱）**：與會員帳號的暱稱是兩份獨立的資料，平常互不連動；但刪除帳號時（FR-003a）例外地一併覆寫為佔位文字，確保該會員過去所有歷史紀錄都不再顯示其實際使用過的暱稱。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 會員完成刪除帳號操作後，100% 無法再用原本的帳號密碼登入。
- **SC-002**: 會員刪除帳號後，其曾經參與的比賽紀錄／揪團歷史，在其他會員瀏覽時 100% 正常顯示（不出現錯誤頁面或空白資料），已刪除會員一律顯示為系統預設佔位名稱。
- **SC-003**: 會員從點擊「刪除帳號」到完成確認、帳號實際被刪除，全程可在 1 分鐘內完成，不需要額外聯繫客服或人工處理。

## Assumptions

- **二次確認方式**：比照既有帳號安全性操作（例如修改密碼需輸入目前密碼）的慣例，刪除帳號的二次確認採用「輸入目前密碼」作為確認方式，而非僅止於一個確認對話框——因為這是一個不可逆且涉及帳號安全邊界的操作，比一般破壞性操作（例如解散揪團、踢除成員）需要更高的確認強度。
- **佔位暱稱的具體文字**：沿用系統既有「已刪除」類狀態的呈現慣例（例如揪團的「已被踢除」「已解散」），使用一個固定、清楚標示「這是已刪除帳號」的預設暱稱字串，實作時決定精確文案。
- **好友關係與搜尋**：已刪除的帳號依 FR-006 保留資料列，但不再是一個「使用中」的帳號——不會出現在會員搜尋結果中，也無法被搜尋到或加為好友（因為這些操作的前提是對方帳號可正常使用）；好友列表本身也排除已刪除的一方（FR-009）。
- **範圍界限**：本功能僅涵蓋會員刪除「自己」的帳號這一件事；不包含管理員代刪除其他會員帳號、批次刪除、或帳號停權/停用（非刪除）等其他機制，這些不在本次範圍內。
- **法規面的保留期間**：台灣個資法與 GDPR「被遺忘權」規範的對象是「可識別特定個人的資料」；FR-003 的匿名化處理（清除 Email、密碼、暱稱等可識別欄位）一旦完成，剩餘保留的比賽紀錄/輪替名單等資料已不再指向可識別的個人，不落入這兩部法規對「個人資料」的定義範圍內。因此本功能不需要額外設計一個「刪除請求後等待 N 天才正式生效」的保留期間或緩衝期——比對使用者原始描述（「帳號立即無法登入」），刪除操作本身就是立即且不可逆的匿名化，這本身即已符合「合理期間內完成刪除」的法規要求，不需另訂政策。
