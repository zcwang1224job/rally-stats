# Quickstart: 運動簡約風視覺改版與行動裝置操作優化

## 前置條件

- `apps/web` 已依 `docs/local-development.md` 啟動（`ng serve` 或 Docker
  Compose 皆可）。
- 瀏覽器開發者工具的裝置模擬模式（Chrome DevTools Device Toolbar 或同等
  工具），設定以下三種視窗尺寸分別測試：
  - **手機直向**：375×667（iPhone SE/8 等常見尺寸）
  - **平板直向**：768×1024
  - **平板橫向 / 桌面**：1024×768（或桌面瀏覽器實際視窗）
- 一個已有 ≥2 位成員、至少 1 個場地、排程機制為 `manual` 或
  `fair_rotation` 的既有測試團（可用 `docs/local-development.md` 的
  smoke test 流程建立）。

## 情境 1：即時計分板與控制板（US1，FR-002~004）

1. 以手機直向（375×667）開啟一個場地的控制板連結。
   **預期**：+1/-1、提前結束按鈕之可點擊區域無需放大即可準確點擊
   （目視估算，或用開發者工具量測元素 `min-height`/`min-width` ≥ 44px）；
   比分數字清楚可辨識，版面無溢出或需要橫向捲動。
2. 以平板橫向（1024×768）開啟同一控制板連結。
   **預期**：版面善用平板寬度，不出現大量未使用空白或按鈕被拉伸變形。
3. 以手機直向開啟對應的計分板連結，觀察連線狀態列（若手動中斷網路模擬）。
   **預期**：連線中斷提示同時有文字（`role="status"`）與圖示/樣式變化，
   不僅靠顏色變化傳達。

## 情境 2：加入團與一般成員視圖（US2，FR-002、FR-003、FR-007）

1. 以手機直向開啟一個團的加入連結，依序完成密碼驗證（若有）與暱稱輸入。
   **預期**：每個步驟的輸入框、送出按鈕皆完整顯示於螢幕內，不需要橫向
   捲動或縮放。
2. 以手機直向開啟一般成員視圖（`/groups/{groupId}/member-view`）。
   **預期**：畫面底部出現固定導覽列（賽程/戰績/對戰紀錄/退出組團），
   點擊可正常切換分頁內容；以平板/桌面尺寸開啟同一頁面，導覽列改為顯示
   於頁面上方（非底部固定）。
3. 以手機直向查看戰績分頁的四狀態表格（需輪次數量足夠多以出現多欄）。
   **預期**：表格本身可橫向捲動查看所有輪次，但不影響頁面其餘部分（例如
   底部導覽列）的版面。
4. 以手機直向點擊「退出組團」。
   **預期**：二次確認彈窗完整顯示於螢幕內，確認/取消按鈕皆可正常點擊，
   彈窗內容與既有確認流程一致（未新增/移除任何確認步驟）。

## 情境 3：開團管理與會員頁面（US3，FR-002、FR-003、FR-006）

1. 以手機直向開啟一個團的管理頁。
   **預期**：團設定、場地管理、賽程控制等區塊有清楚的視覺區隔（例如卡片
   邊框/間距），逐一卷動檢視時不會誤以為按鈕屬於相鄰的其他區塊。
2. 以手機直向觸發「解散團」或「踢除成員」。
   **預期**：二次確認彈窗完整顯示，文字不被截斷，確認/取消按鈕皆可正常
   點擊。
3. 以手機直向登入會員帳號，開啟跨團對戰紀錄頁面（`/member/match-history`）。
   **預期**：彙總統計數字（總場次/勝/敗/勝率）與列表項目清楚可讀，分頁
   按鈕可正常點擊切換頁次。

## 驗證通過標準

- 情境 1–3 之全部「預期」項目皆吻合，且在三種視窗尺寸（手機直向/平板
  直向/平板橫向）下重複驗證皆通過。
- 既有 001–007 之全部前端單元測試（`npm test`）與 lint（`npm run
  lint`）、production 建置（`npm run build`）皆維持通過，且 build 產出
  未超過 `angular.json` 既有 bundle/樣式門檻（constitution 原則 I 之
  blocking check，見 plan.md Performance Goals）。
- 視覺走查（design QA）確認每一頁面的既有功能入口（按鈕/連結/選單項目）
  數量與改版前一致（SC-004）——建議走查者對照改版前的畫面截圖逐一確認，
  而非僅依賴功能測試通過與否。
