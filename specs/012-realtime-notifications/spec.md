# Feature Specification: 即時通知功能（Real-Time Notifications）

**Feature Branch**: `[012-realtime-notifications]`

**Created**: 2026-09-07

**Status**: Draft

**Input**: User description: "增加通知功能，接受到好友申請與未來會有邀請入團的功能，即時收到通知"

## Clarifications

### Session 2026-09-07

- Q: 會員能否把某一則通知「個別刪除」（從列表中移除、不再顯示），還是只能將其標記為已讀，通知本身永久保留在歷史列表中？ → A: 不可個別刪除，僅能標記已讀；所有通知永久保留在歷史列表中。
- Q: 會員打開通知列表時，畫面上當下可見的未讀通知，是否會自動全部轉為已讀，還是仍維持未讀、必須等會員實際點擊/開啟某一則通知才會轉為已讀？ → A: 開啟列表不會自動已讀；只有實際點擊/開啟某一則通知，該則才轉為已讀。
- Q: 當會員的未讀通知數量非常龐大時（例如超過 99 則），畫面上的未讀數量指標應該顯示精確數字，還是封頂顯示（例如「99+」）？ → A: 封頂顯示，超過 99 則時顯示「99+」，不顯示精確數字。

### User Story 1 - 即時收到好友申請通知 (Priority: P1)

當有其他會員對我送出好友申請時，我希望在還在使用系統的當下就能立即被告知有新的申請，而不必自己想到要去好友申請頁面手動確認有沒有新邀請。

**Why this priority**：這是本功能存在的核心價值——把「被動等待對方口頭告知、或自己養成定期檢查的習慣」變成「主動即時得知」。沒有這一條，其餘功能（列表、已讀狀態、導向）都失去意義。

**Independent Test**：由會員 A 對正在使用系統的會員 B 送出好友申請，驗證 B 能在數秒內、且無需重新整理頁面，就看到有一則新通知出現。

**Acceptance Scenarios**:

1. **Given** 會員 B 已登入且正在瀏覽系統其他頁面, **When** 會員 A 對 B 送出好友申請, **Then** B 應在數秒內於畫面上看到新通知的提示（例如未讀數量增加、通知內容出現），且無需手動重新整理頁面。
2. **Given** 會員 B 當下並未開啟系統（離線）, **When** 會員 A 對 B 送出好友申請, **Then** B 下次登入/開啟系統時，應看到該通知以「未讀」狀態呈現，不會遺失。

---

### User Story 2 - 查看與管理通知列表 (Priority: P2)

我希望能打開一個地方看到自己收到過的所有通知，分辨哪些還沒看過、哪些已經看過，這樣即使錯過了即時提示，事後也能補看，不必擔心遺漏。

**Why this priority**：即時提示只能覆蓋「當下正在使用系統」的情境；若沒有可回顧的列表，離線期間累積的通知就無從查證是否已全部處理過，會讓通知功能的可信度大打折扣。

**Independent Test**：讓某會員累積數則通知（含已讀與未讀），開啟通知列表，驗證能依時間新到舊正確排序呈現，且每則的已讀/未讀狀態正確反映。

**Acceptance Scenarios**:

1. **Given** 會員有 3 則通知（2 則未讀、1 則已讀）, **When** 開啟通知列表, **Then** 應依時間新到舊排序顯示全部 3 則，且能清楚分辨每則的已讀/未讀狀態。
2. **Given** 會員有多則未讀通知, **When** 使用「全部標示已讀」操作, **Then** 所有通知應轉為已讀狀態，且未讀數量指標歸零。

---

### User Story 3 - 點擊通知直接前往相關內容 (Priority: P3)

我希望點擊一則通知後，能直接被帶到跟這則通知相關的畫面（例如點擊好友申請通知，就直接進入可以接受/拒絕該申請的畫面），而不用自己再去找。

**Why this priority**：讓通知從「被告知」進化為「可行動」，能實際節省操作步驟；但即使沒有這條，會員仍可透過既有的好友申請頁面自行找到並處理，因此優先度低於前兩者。

**Independent Test**：點擊一則未讀的好友申請通知，驗證系統直接導向可查看/處理該筆好友申請的畫面，且該通知同時轉為已讀。

**Acceptance Scenarios**:

1. **Given** 會員有一則未讀的好友申請通知, **When** 點擊該通知, **Then** 系統應導向可查看/處理該筆好友申請的畫面，且該通知隨即轉為已讀狀態。

---

### Edge Cases

- 會員完全離線（未開啟系統）時收到好友申請，該通知是否仍會被完整保留，並在下次上線時以未讀狀態呈現？
- 同一位會員在短時間內收到多筆好友申請（分別來自不同人）時，是否每一筆都各自產生獨立的一則通知，而不是被合併、覆蓋或遺漏？
- 若某則通知所關聯的好友申請，在會員查看該通知之前，已經被對方撤回、或已透過其他管道（例如好友申請頁）被接受/拒絕，這則通知本身應如何呈現、點擊後應如何反應？
- 當會員的未讀通知數量超過 99 則時，未讀數量指標以「99+」封頂顯示（FR-006）；通知列表本身則採用與系統既有列表一致的分頁瀏覽方式呈現全部歷史（見 Assumptions），不受此上限影響。
- 當會員已經開著通知列表（或好友申請頁）時收到新的好友申請，畫面上的列表/未讀數量是否也會即時更新，而不需要重新整理頁面？

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 當會員 A 對會員 B 送出好友申請時，系統 MUST 為會員 B 建立一則對應的通知記錄。
- **FR-002**: 若會員 B 於好友申請送出當下正在使用系統（維持連線中），系統 MUST 在會員 B 當下所在的畫面即時呈現該通知（應用內即時提示），不需重新整理頁面。此範圍僅限應用內即時提示；若會員當下並未開啟系統頁面/App，本次不透過瀏覽器或裝置層級的系統推播通知主動提示，改由 FR-003 的離線持久化機制涵蓋（下次登入時以未讀狀態呈現）。
- **FR-003**: 若會員 B 於好友申請送出當下未在線上，系統 MUST 保留該通知，並於會員 B 下次登入/開啟系統時，以未讀狀態呈現，不得遺失。
- **FR-004**: 會員 MUST 能檢視自己收到過的通知列表，並依時間新到舊排序呈現。
- **FR-005**: 系統 MUST 讓會員能區分每則通知的已讀/未讀狀態。
- **FR-006**: 系統 MUST 提供一個在系統各主要頁面皆可見的未讀通知數量指標，讓會員不需開啟通知列表也能得知目前有新通知待查看；未讀數量超過 99 則時，指標 MUST 以「99+」封頂顯示，而非顯示精確數字。
- **FR-007**: 會員點擊/開啟一則通知時，系統 MUST 將該則通知標示為已讀，並導向與該通知內容相關的畫面（例如好友申請通知導向可處理該申請的畫面）。
- **FR-008**: 會員 MUST 能透過單一操作，將所有通知一次標示為已讀。
- **FR-009**: 系統 MUST 僅將某則通知投遞給該事件的實際對象（例如好友申請的通知僅投遞給收到申請的一方），MUST NOT 讓其他無關會員看到或收到不屬於自己的通知。
- **FR-010**: 通知功能 MUST 僅開放給已完成信箱驗證的會員使用；尚未完成信箱驗證的會員與訪客（Guest）身分 MUST NOT 能使用此功能——此限制沿用現行好友系統僅限已驗證會員使用的既有規則。
- **FR-011**: 通知的資料結構 MUST 支援多種通知類型（本次僅實作「收到好友申請」一種），以便未來新增其他類型的通知（例如邀請入團）時，不需要重新設計既有的通知列表、未讀數量指標與已讀/未讀機制。
- **FR-012**: 會員 MUST NOT 能個別刪除或隱藏單一則通知——通知一經建立即永久保留在歷史列表中，會員僅能透過已讀/未讀狀態管理查看情形，不提供逐筆刪除功能。
- **FR-013**: 開啟通知列表 MUST NOT 自動將畫面上可見的未讀通知轉為已讀；僅在會員實際點擊/開啟某一則通知時（見 FR-007），該則 MUST 轉為已讀——「全部標示已讀」（FR-008）維持為會員需主動觸發的獨立操作。

### Key Entities *(include if feature involves data)*

- **Notification（通知）**：代表投遞給單一會員的一則通知事件。包含：通知類型（本次僅有「收到好友申請」一種，資料結構須可擴充其他類型）、接收會員、關聯的來源事件（例如是哪一筆好友申請）、已讀/未讀狀態、建立時間，以及足以呈現通知內容、並導向對應目標畫面所需的資訊。
- **Member（會員）**：既有實體（見 006-member-friends），本功能中作為通知的接收者。
- **FriendRequest（好友申請）**：既有實體（見 006-member-friends），本次是唯一會觸發通知建立的來源事件類型。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**：正在使用系統的會員，在收到好友申請後 2 秒內，就能在畫面上看到通知提示，無需手動重新整理頁面。
- **SC-002**：離線期間收到的通知，會員下次登入後 100% 能看到且正確標示為未讀，沒有任何一則遺失。
- **SC-003**：會員無需打開通知列表，只要一開啟系統畫面就能立即看到目前有幾則未讀通知。
- **SC-004**：會員點擊一則通知後，一次操作內即可到達與該通知相關的內容畫面，不需要額外自行搜尋或導覽。
- **SC-005**：未來新增第二種通知類型（例如邀請入團）時，既有的通知列表、未讀數量指標、已讀/未讀呈現方式不需要重新設計即可直接沿用。

## Assumptions

- 通知功能僅開放給已完成信箱驗證的會員使用，訪客（Guest）不在本次範圍內——沿用現行好友系統僅限已驗證會員使用的既有規則。
- 本次僅實作「收到好友申請」這一種通知類型；「邀請入團」功能本身目前尚未存在，其對應的通知不在本次實作範圍內，但通知資料結構的設計 MUST 讓未來該功能上線時，不需要重做既有的通知列表/未讀計數等機制。
- 通知記錄不會自動過期或刪除，會員可回顧完整歷史通知（採用與系統既有列表一致的分頁瀏覽方式，例如對戰紀錄列表的既有分頁模式）。
- 若通知所關聯的好友申請，在會員點擊該通知前已透過其他管道處理完畢（例如已在好友申請頁被接受/拒絕，或被對方撤回），點擊該通知時仍會導向對應畫面，畫面會呈現該申請目前的最新狀態，而不是假裝它還處於待處理。
- 一則好友申請只會產生一則對應通知（不會因為系統重複檢查或多次連線而重複建立）。
- 本次僅實作應用內（in-app）即時提示；瀏覽器/裝置層級的系統推播通知（會員未開啟分頁/App 時仍主動跳出提示）不在本次範圍內，留待未來有實際需求時另行規劃。
