# Feature Specification: 會員首頁重新寄送驗證信

**Feature Branch**: `[020-resend-verification-email]`

**Created**: 2026-09-10

**Status**: Draft

**Input**: User description: "會員註冊後，第一次登入後的畫面，新增重新寄送驗證信件功能，要有防範機制，五分鐘內只能送一次驗證信"

## Clarifications

### Session 2026-09-10（/speckit-analyze 發現後的修復）

- Q: `/speckit-analyze` 發現 Edge Cases 第一項（「第一次點擊 MUST 直接成功」）與 FR-004／SC-003 原文（以「上一次成功寄出驗證信的時間」為基準，含註冊當下自動寄出的第一封信）互相矛盾——若會員剛註冊完 5 分鐘內就點擊「重新寄送」，會被系統誤判為冷卻中而拒絕，違背 Edge Cases 第一項的承諾。如何解決？ → A：讓「第一次點擊必定成功」成真——冷卻判斷基準改為「上一次手動觸發重新寄送的時間」，MUST NOT 將註冊當下系統自動寄出的第一封驗證信算作一次「重新寄送」；會員從未手動觸發過「重新寄送」時視為無冷卻限制。FR-004、SC-003、Edge Cases 第一項已同步修訂為彼此一致。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 在會員首頁重新寄送驗證信 (Priority: P1)

我是剛註冊、信箱尚未驗證的會員。登入後看到的會員首頁只告訴我「請驗證你的信箱」，卻沒有任何按鈕可以再要一封驗證信——如果我找不到當初那封信（進垃圾信件匣、已過期、忘了收），我完全無法自己解決，只能重新走一次註冊。我希望在這個畫面上直接有個「重新寄送驗證信」的按鈕，點了之後系統會寄一封新的驗證信到我的信箱，並清楚告訴我已經寄出。

**Why this priority**：這是本功能存在的核心價值——沒有這個按鈕，未驗證會員一旦錯過或找不到原始驗證信，就完全卡住，無法自行復原。系統其實已經有對應的後端機制（登入後才可觸發、有防濫用機制），只是畫面上從未真正提供這個入口給使用者按。

**Independent Test**：以一個尚未驗證信箱的會員帳號登入，開啟會員首頁，點擊「重新寄送驗證信」，驗證收到一封新的驗證信，且畫面上出現「已寄出」的明確提示。

**Acceptance Scenarios**:

1. **Given** 會員以尚未驗證信箱的帳號登入，**When** 會員開啟登入後的會員首頁，**Then** 畫面上 MUST 在既有「請驗證你的信箱」提示旁邊，看到一個「重新寄送驗證信」的操作。
2. **Given** 會員在該畫面點擊「重新寄送驗證信」，**When** 系統成功寄出，**Then** 畫面 MUST 顯示清楚的「已重新寄出驗證信」成功提示，且會員的信箱 MUST 收到一封新的驗證信（內容與驗證流程與原本註冊時收到的驗證信一致）。
3. **Given** 會員的信箱已經完成驗證（例如已經用別的分頁完成驗證，此畫面尚未更新狀態），**When** 會員仍嘗試點擊「重新寄送驗證信」，**Then** 系統 MUST 明確告知「此帳號已完成驗證」，MUST NOT 再寄出一封多餘的驗證信或顯示不明確的錯誤。

---

### User Story 2 - 短時間內重複要求會被防範機制擋下 (Priority: P1)

我是尚未驗證信箱的會員，我可能因為手滑連續點擊好幾次「重新寄送驗證信」，或者開了兩個分頁各按一次。我希望系統不會因此狂寄好幾封驗證信給我（甚至被別人惡意利用來對我的信箱洗版騷擾），而是清楚告訴我要稍等一下再試。

**Why this priority**：這是使用者明確要求的防範機制，也是這個功能能安全上線的前提——沒有這層防護，這個新按鈕本身就會變成一個騷擾/濫用信箱的破口，跟「新增按鈕」這個核心價值同等重要，缺一不可，故與 US1 並列最高優先度。

**Independent Test**：以尚未驗證信箱的會員帳號登入，連續點擊「重新寄送驗證信」兩次（間隔在 5 分鐘以內），驗證第二次會被拒絕並顯示「請稍後再試」之類的明確提示，且實際只收到第一次那封驗證信，不會收到第二封。

**Acceptance Scenarios**:

1. **Given** 會員剛成功觸發一次「重新寄送驗證信」，**When** 會員在 5 分鐘內再次點擊「重新寄送驗證信」，**Then** 系統 MUST 拒絕這次寄送，MUST NOT 寄出第二封信，並 MUST 顯示明確的提示告知使用者需要稍後再試。
2. **Given** 會員在不同分頁或裝置同時登入同一帳號，**When** 其中一個分頁已經在 5 分鐘內觸發過重新寄送，**Then** 另一個分頁的再次觸發 MUST 一樣被視為同一帳號的重複請求而遭拒絕（防範機制以帳號為準，不分分頁/裝置）。
3. **Given** 會員在被拒絕之後，**When** 距離上一次成功寄出已經滿 5 分鐘，**Then** 會員 MUST 能再次成功觸發重新寄送。

---

### User Story 3 - 按鈕主動反映冷卻中狀態 (Priority: P3)

我是尚未驗證信箱的會員，剛按過「重新寄送驗證信」。我希望畫面上的按鈕能直接告訴我現在還在冷卻中、大概還要等多久，而不是讓我猜測、一直手動重複點擊然後每次都被拒絕。

**Why this priority**：這是體驗上的加分——即使沒有這個主動提示，US2 的防範機制本身已經能正確擋下並提示「請稍後再試」，核心防護與可用性已經成立；這一項只是讓使用者更順暢地理解冷卻狀態，優先度最低。

**Independent Test**：成功觸發一次重新寄送後，立刻查看按鈕狀態，驗證按鈕呈現「冷卻中/暫時無法使用」的樣式，滿 5 分鐘後驗證按鈕恢復可正常點擊。

**Acceptance Scenarios**:

1. **Given** 會員剛成功觸發重新寄送，**When** 會員查看該按鈕，**Then** 按鈕 MUST 呈現明確的「冷卻中」視覺與文字狀態（不僅靠顏色），讓使用者理解目前無法再次觸發。
2. **Given** 按鈕處於冷卻中狀態，**When** 距離上次成功寄出已滿 5 分鐘，**Then** 按鈕 MUST 恢復為可正常點擊的狀態，不需要使用者重新整理頁面。

---

### Edge Cases

- 會員從未驗證過信箱、也從未觸發過任何一次重新寄送（帳號剛註冊完第一次登入，即使距離註冊當下系統自動寄出的第一封驗證信不滿 5 分鐘）——第一次點擊「重新寄送驗證信」MUST 直接成功，不受冷卻機制影響（冷卻機制只限制「重新寄送」彼此之間的連續間隔，MUST NOT 把註冊當下的第一封信算作一次「重新寄送」，見 FR-004）。
- 寄信當下發生系統/網路錯誤（非「已驗證」也非「速率限制」的情況）——MUST 顯示清楚的錯誤提示，MUST NOT 讓使用者誤以為信已經寄出。
- 使用者尚未登入就嘗試觸發此功能（例如透過非正常路徑）——MUST 被拒絕，此功能 MUST 只限登入後才可觸發，與既有驗證信重寄機制的既定存取層級一致。
- 使用者在被拒絕（速率限制）之後重新整理整個頁面——重新整理後畫面仍 MUST 正確反映目前是否還在冷卻中（不因重新整理而讓使用者誤以為可以再次觸發）。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 會員登入後看到的會員首頁，在信箱尚未驗證時，MUST 提供一個「重新寄送驗證信」的操作，與既有「請驗證你的信箱」提示同時呈現。
- **FR-002**: 「重新寄送驗證信」操作 MUST 只在會員信箱尚未驗證時可見／可用；信箱已驗證的會員 MUST NOT 看到這個操作。
- **FR-003**: 觸發「重新寄送驗證信」成功時，系統 MUST 寄出一封新的驗證信到會員註冊時使用的信箱，內容與驗證流程 MUST 與原始註冊時收到的驗證信一致（同一套驗證連結機制），MUST NOT 另外設計一套不同的驗證方式；畫面 MUST 顯示清楚的成功提示，告知使用者信件已重新寄出。
- **FR-004**: 系統 MUST 防止同一帳號在 5 分鐘內被觸發兩次以上的「重新寄送」——以該帳號「上一次手動觸發重新寄送的時間」為基準，未滿 5 分鐘的再次觸發 MUST 一律拒絕，MUST NOT 寄出任何新的驗證信；此限制取代既有「1 分鐘內僅能觸發一次」的舊冷卻時間設定（006-member-friends FR-011），MUST 全面改為 5 分鐘。此判斷基準 MUST NOT 把「註冊當下系統自動寄出的第一封驗證信」算作一次「重新寄送」——會員從未手動觸發過「重新寄送」時，MUST 視為尚無冷卻限制（呼應 Edge Cases 第一項、SC-003）。
- **FR-005**: 因速率限制被拒絕時，系統 MUST 顯示明確告知使用者「需要稍後再試」的提示文字，MUST NOT 顯示不明確或容易讓使用者誤解為系統故障的錯誤訊息。
- **FR-006**: 觸發當下若該帳號信箱已經是「已驗證」狀態，系統 MUST 明確告知「此帳號已完成驗證」，MUST NOT 因此寄出多餘的驗證信，也 MUST NOT 顯示與速率限制相同或含糊不清的錯誤訊息。
- **FR-007**: 「重新寄送驗證信」功能 MUST 只限已登入的會員才能觸發，未登入 MUST 被拒絕，存取層級 MUST 與既有驗證信重寄機制的既定登入要求一致。
- **FR-008**: 按鈕/操作項目 SHOULD 在成功觸發後主動反映「冷卻中」狀態（例如暫時停用並顯示提示），並在冷卻結束（滿 5 分鐘）後自動恢復為可用狀態，讓使用者不需要自行猜測或反覆嘗試；此狀態呈現 MUST 同時使用文字/圖示與視覺樣式，MUST NOT 僅依賴顏色作為唯一的辨識依據。
- **FR-009**: 重新整理頁面或重新進入此畫面時，系統 MUST 能正確反映該帳號目前是否仍處於 5 分鐘冷卻中，MUST NOT 因為前端狀態遺失而誤導使用者以為可以立即再次觸發（實際觸發時仍 MUST 依 FR-004 的伺服器端限制為準）。

### Key Entities *(include if feature involves data)*

- **（既有）Member（會員）**：本功能讀取其信箱驗證狀態（已驗證／未驗證），決定「重新寄送驗證信」操作是否顯示。
- **（既有）驗證信 Token／寄送紀錄**：本功能唯讀既有的「最近一次成功寄出驗證信的時間」作為 5 分鐘冷卻機制的判斷基準；本功能不新增這筆紀錄的資料結構，只調整冷卻的時間長度門檻（由 1 分鐘改為 5 分鐘）。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**：尚未驗證信箱的會員，從登入到成功觸發「重新寄送驗證信」並看到成功提示，整個過程可在 10 秒內完成，不需要離開會員首頁或查閱其他頁面。
- **SC-002**：100% 在上一次成功寄出後 5 分鐘內的重複觸發，都會被系統拒絕並顯示明確的「請稍後再試」提示，不會產生第二封驗證信。
- **SC-003**：任何一個帳號，兩次「重新寄送」觸發之間，100% 間隔至少 5 分鐘；不含註冊當下系統自動寄出的第一封驗證信（呼應 FR-004、Edge Cases 第一項——該封信不算作一次「重新寄送」，不會讓會員剛註冊完就被冷卻機制擋下第一次手動重新寄送）。
- **SC-004**：信箱已驗證的帳號嘗試觸發此功能時，100% 收到明確的「已完成驗證」提示，不會發生寄出多餘信件或顯示不明確錯誤的情況。

## Assumptions

- 「第一次登入後的畫面」係指會員登入成功後導向的既有會員首頁（未驗證時目前僅顯示「請驗證你的信箱」提示的既有畫面）；本功能是在這個既有畫面上新增操作，MUST NOT 另外新增一個獨立的畫面/路由。
- 「重新寄送驗證信」的核心後端機制（登入後才可觸發、依帳號設冷卻時間、核發新的驗證 Token 並寄信）已經存在（006-member-friends FR-011），本功能沿用同一套既有機制，僅將冷卻時間門檻由既有的 1 分鐘調整為使用者明確要求的 5 分鐘，並補上畫面上原本缺少的觸發入口與對應的成功/失敗提示呈現。
- 防範機制沿用既有「以帳號為準、需登入才可觸發」的既定設計，不另外疊加以 IP 或裝置為基準的額外限制——因為此功能本來就要求先登入，風險特性與「忘記密碼」這類免登入即可觸發的端點不同，沿用既有 FR-011 的既定假設。
- 驗證信本身的內容/樣式（郵件範本）沿用既有註冊驗證信的既有設計，本功能不變更郵件內容本身。
- 「會員信箱尚未驗證時，理論上也不應該能使用開團、好友系統等其他功能」這項既有規範（006-member-friends FR-009／專案憲章原則 IV）目前在畫面呈現上尚未完整落實（會員首頁仍會顯示這些功能的連結入口），但這是既有、與本次「新增重新寄送驗證信按鈕」需求範圍無關的既存落差，本功能 MUST NOT 一併處理，留待後續視需要另行規劃。
