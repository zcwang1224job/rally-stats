# Feature Specification: 開團與管理（Create & Manage Group）

**Feature Branch**: `[001-create-manage-group]`

**Created**: 2026-08-31

**Status**: Draft

**Input**: User description: "建立「開團與管理」功能：

使用者故事：作為一個想約球的使用者，我可以建立一個揪團場次（開團），設定團名、是否需要通關密碼、人數上限、比賽模式（單打或雙打）、排程機制（公平輪替 / 手動安排 / 固定搭檔循環賽 / 個人全混搭循環賽）、比賽設定（21 分制 / 15 分制 / 自訂目標分數）、以及選填的活動時間區間（方便其他人在嘎團列表依時間篩選是否適合自己），並取得一組「組團編號」與「管理 PIN 碼」，日後可用這組編號與 PIN 碼重新驗證進入管理頁面繼續管理（此為管理員驗證，非會員帳號登入），不需要註冊會員。

功能需求：
- 建立團時可設定：團名（必填）、通關密碼（選填）、人數上限（必填，正整數，依比賽模式動態決定最小值：單打≥2、雙打≥4，且不可超過系統參數 max_group_members 訂出的硬上限）、比賽模式（單打/雙打）、排程機制（四選一）、活動時間區間（選填，開始~結束需成對填寫且開始早於結束；未填則嘎團列表顯示「未提供時間」）。
- 比賽設定區塊（團級別，預設 21 分制）：21 分制（20:20 起需領先2分、29:29 起先達30分獲勝）、15 分制（14:14 起需領先2分、20:20 起先達21分獲勝，2027年BWF新制提前納入）、自訂（目標分數/deuce門檻/封頂分數三個必填欄位，並驗證彼此邏輯一致）；修改僅影響尚未開始的新比賽，透過每筆比賽建立時快照設定值達成。
- 開團者暱稱：已登入會員直接用會員暱稱；未登入需額外必填暱稱（≤20字）；開團者本人自動加入輪替名單成為參與者（保留管理員身分）；匿名開團者同時核發 Guest Session Token；建立時 current_member_count 初始化為 1。
- 開團表單需整合 Cloudflare Turnstile 防機器人驗證，後端需先驗證 token 有效才建立團。
- 建立成功後產生唯一組團編號（資料庫自增序號，起始 100000，不回收、不設碼數上限）與 6 碼管理 PIN 碼（雜湊儲存），顯示於管理頁。
- 管理員可在管理頁：就地編輯團名與活動時間區間；修改比賽模式（僅影響下一個 Round，且切換為雙打時人數上限需一併調高至≥4）；查看/修改通關密碼明文（僅限管理頁）；主動重新產生管理 PIN 碼（二次確認，舊 token 全部失效並同步核發新 token 給觸發者，具備樂觀並發控制避免兩位管理員互踩）；解散團（二次確認）。
- 解散團的影響：加入連結/QR、單一與全部場地控制板連結、Guest Session Token 全部失效；計分板仍可開啟但顯示「此團已解散」並凍結在最終比分、不再接收即時更新；組團編號+PIN 仍可用於進入唯讀管理頁（可查歷史、不可寫入、不可復原）；尚未收尾（排隊中/進行中）的比賽一律轉為已捨棄，不產生賽果、不計入戰績；解散當下需即時廣播通知所有已連線畫面（逐一對每個場地頻道與團通知頻道發布），並搭配心跳檢查作為離線客戶端的備援。
- 自動解散機制：團持續 1 小時無任何寫入類活動（比分變動、比賽結束、Next Round 觸發（含 Auto Next Round 自動觸發）、成員加入/退出/被踢、管理員任何編輯）即自動解散，效果等同手動解散；純瀏覽不算活動、不重置計時器。
- 未登入使用者以組團編號+管理 PIN 碼重新驗證取得管理權限，此驗證具備防暴力破解機制（錯誤次數限制）。

（驗收情境略，詳見對話紀錄，已於下方各使用者故事中轉譯為 Given/When/Then 場景。）"

## Clarifications

### Session 2026-08-31

- Q: 自訂比賽設定（FR-014）目前只驗證「封頂分數 ≥ 門檻分數」，未驗證封頂分數與目標分數的關係。若封頂分數 < 目標分數（例如目標10、門檻5、封頂8），邏輯上會出現「比賽永遠不可能打到目標分數就先封頂」的矛盾情境。是否需新增此驗證規則？ → A: 封頂分數須 ≥ 目標分數
- Q: FR-035 心跳檢查機制作為離線客戶端的解散通知備援，但未定義檢查週期。SC-004 提到「離線的客戶端最慢在下一次心跳檢查週期內」得知解散，這個週期上限是多久？ → A: 30 秒
- Q: 6 碼「管理 PIN 碼」的字元組成為何？這會影響資料驗證規則、暴力破解防護的組合數估算，以及重新驗證表單的輸入鍵盤設計（行動裝置優先原則）。 → A: 純數字 0-9
- Q: 通關密碼（團的加入密碼）目前規格未定義長度或字元限制，其他文字欄位（團名≤30字、暱稱≤20字）皆有明確上限。通關密碼是否需要長度限制？ → A: 需長度限制，1–20 字

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 建立揪團場次並取得管理權限 (Priority: P1)

一位想約球的使用者（無論是否已登入會員）填寫開團表單——團名、人數上限、比賽模式、排程機制、比賽設定（可用預設值）、選填的通關密碼與活動時間區間——通過機器人驗證後送出，系統建立團、將開團者本人自動加入輪替名單，並導向管理頁，顯示唯一的組團編號與 6 碼管理 PIN 碼供日後重新驗證使用。

**Why this priority**: 這是整個功能的入口，沒有「建立團」就沒有後續任何管理、加入或計分行為，是最小可行產品的核心。

**Independent Test**: 可透過完整填寫開團表單並送出來獨立測試——驗證團被建立、導向管理頁、顯示組團編號與 PIN 碼、開團者出現在輪替名單中，即完成一次完整且有價值的閉環，無需依賴其他功能。

**Acceptance Scenarios**:

1. **Given** 使用者填寫完整且合法的開團表單並完成機器人驗證，**When** 送出表單，**Then** 系統建立團並導向管理頁，顯示組團編號與 6 碼管理 PIN 碼。
2. **Given** 使用者送出開團表單但機器人驗證尚未完成或已失敗，**When** 送出表單，**Then** 系統拒絕建立團並提示「驗證失敗，請重新嘗試」，不會建立任何團。
3. **Given** 使用者成功建立一個團，**When** 查看該團的輪替名單，**Then** 開團者本人已在名單中，不需另外走一次嘎團加入流程；若開團者為匿名身分，瀏覽器同時取得該團的 Guest Session Token。
4. **Given** 使用者未登入即開始建立團，**When** 表單未填寫開團者暱稱、或暱稱超過 20 字、或團名留空/僅空白/超過 30 字，**Then** 系統提示對應錯誤，不可送出；已登入且已設定暱稱的會員則不需填寫暱稱欄位。
5. **Given** 比賽模式為單打，**When** 人數上限填寫為 1 或更小，**Then** 系統提示「單打模式人數上限至少需為 2 人」；比賽模式為雙打時填寫 3 或更小，**Then** 提示「雙打模式人數上限至少需為 4 人」；兩者皆不可送出，滿足對應最小值方可送出。
6. **Given** 系統參數 `max_group_members` 目前為 200，**When** 人數上限填寫超過 200，**Then** 系統提示「人數上限不可超過 200 人」，不可送出。
7. **Given** 使用者未填寫活動時間區間，**When** 送出表單，**Then** 團仍正常建立，該團在嘎團列表的時間欄位明確顯示「未提供時間」；**Given** 僅填寫開始時間，**When** 送出，**Then** 系統提示需一併填寫結束時間，不可送出。
8. **Given** 使用者未調整比賽設定，**Then** 系統預設採用 21 分制；**Given** 切換為自訂並填入合理的目標分數/門檻/封頂組合，**Then** 可正常送出；**Given** 目標分數填 0、負數或留空，或封頂分數小於門檻分數，或封頂分數小於目標分數，**Then** 系統提示錯誤，不可送出。

### User Story 2 - 手動解散團 (Priority: P1)

管理員在管理頁點擊「解散」並完成二次確認後，團立即進入已解散狀態：所有加入/控制連結與 Guest Session Token 失效、計分板凍結在最終比分、尚未收尾的比賽轉為已捨棄、所有已連線畫面即時收到通知並切換為對應唯讀/停用狀態，組團編號與 PIN 碼仍可進入唯讀管理頁查閱歷史紀錄。

**Why this priority**: 解散是團生命週期的終點，直接影響資料完整性（避免懸空比賽狀態）與其他使用者的即時體驗，且與自動解散機制（User Story 5）共用同一套核心行為，優先程度與建立團同級。

**Independent Test**: 可對一個已建立、已有進行中比賽的團觸發解散，獨立驗證各類連結、計分板、管理頁、比賽狀態的最終行為，無需依賴其他未完成功能。

**Acceptance Scenarios**:

1. **Given** 管理員點擊「解散」並在確認彈窗按下確認，**Then** 團狀態變為已解散；加入連結、單一場地控制板連結、全部場地控制板連結開啟時皆顯示「此團已解散」且無法操作。
2. **Given** 團已解散，**When** 使用者開啟該團的計分板連結，**Then** 顯示「此團已解散」與解散當下的最終比分，不再接收任何即時更新。
3. **Given** 團已解散，**When** 管理員以組團編號與管理 PIN 碼重新驗證進入管理頁，**Then** 可查看歷史戰績與對戰紀錄，但所有寫入類操作（編輯、新增場地、踢除成員、Next Round 等）皆為停用狀態，且無法復原已解散的團。
4. **Given** 解散當下有比賽處於「進行中」、另有比賽處於「排隊中」，**Then** 解散後這些比賽狀態皆轉為「已捨棄」，不產生賽果、不計入戰績或對戰紀錄，不會有比賽永遠停留在這兩種狀態。
5. **Given** 某場地的計分板正持續開著、連線正常，**When** 管理員將該團解散，**Then** 該計分板應在約 1 秒內偵測到並切換為顯示「此團已解散」與最終比分；同一團底下其他場地的計分板、控制板、全部場地控制板、以及正開著的管理頁，皆同樣在約 1 秒內收到通知並切換為對應的唯讀/停用狀態，不需等待重新整理或斷線重連。
6. **Given** 某客戶端在解散通知發出的當下剛好離線，**Then** 該客戶端最壞情況下仍會在下一次心跳檢查週期內、或連線恢復時偵測到團已解散並顯示對應提示，不會永遠停留在解散前的畫面。

### User Story 3 - 以組團編號與管理 PIN 碼重新進入管理頁 (Priority: P2)

管理員（無論當初是否以會員身分建立團）弄丟原本的管理頁連結後，透過手動輸入組團編號與 6 碼管理 PIN 碼重新驗證，即可取得管理權限進入管理頁繼續管理，全程不需要註冊會員帳號。

**Why this priority**: 這是「不需要註冊會員也能長期管理」這個核心價值主張的必要支撐，但團建立當下已直接導向管理頁，短期內不影響當次操作，因此優先序略低於建立與解散。

**Independent Test**: 可用一組已知合法的組團編號＋PIN 碼、以及一組錯誤的編號或 PIN 碼分別測試，驗證前者能進入管理頁、後者被拒絕且顯示錯誤訊息，無需依賴其他功能。

**Acceptance Scenarios**:

1. **Given** 已存在的團，**When** 管理員輸入正確的組團編號與 PIN 碼，**Then** 可進入該團管理頁；**When** 輸入錯誤，**Then** 顯示錯誤訊息且不可進入。
2. **Given** 管理員短時間內多次輸入錯誤的 PIN 碼，**Then** 系統套用防暴力破解機制（例如暫時鎖定或延遲），阻止無限次嘗試。
3. **Given** 系統目前已發出的組團編號序號來到 999999，**When** 下一個團建立成功，**Then** 系統正常發出編號 1000000，不需任何額外的格式切換處理，輸入框正常接受此編號。
4. **Given** 某團已解散，**Then** 其組團編號與管理 PIN 碼日後不會被重新分配給任何新建立的團。

### User Story 4 - 管理頁編輯團設定 (Priority: P2)

管理員在管理頁可就地編輯團名、活動時間區間、比賽模式、比賽設定與通關密碼；修改比賽模式或比賽設定僅影響尚未開始的新比賽/新一輪賽程，不會回溯影響正在進行中或已完成的比賽。

**Why this priority**: 建立團之後的日常調整需求（改時間、改密碼、改賽制）很常見，但團即使不具備事後編輯能力也能先跑起來一次性使用，因此優先序次於建立與解散。

**Independent Test**: 可在已建立且有進行中比賽的團上，個別修改團名、時間區間、比賽模式、比賽設定、密碼，並驗證進行中的比賽維持原本規則、新比賽套用新規則，無需依賴其他未完成功能。

**Acceptance Scenarios**:

1. **Given** 管理員在管理頁編輯團名或活動時間區間（成對填寫、開始早於結束的規則同建立時），**Then** 修改成功並即時反映在嘎團列表等顯示位置。
2. **Given** 某團比賽模式為單打、人數上限為 2 人，**When** 管理員將比賽模式改為雙打，**Then** 系統提示人數上限需一併調高至少為 4 人，不可讓修改在人數上限仍為 2 的狀態下生效。
3. **Given** 某團目前為單打模式且賽程表中仍有比賽進行中/排隊中，**When** 管理員將比賽模式改為雙打，**Then** 進行中的單打比賽不受影響、繼續進行；排隊中尚未開始的比賽維持原對戰組合，直到下一個 Round 才依新模式重新排點；**When** 管理員按下「Next Round」，**Then** 系統強制結束目前 Round（未完成比賽視為捨棄），下一個 Round 依新模式產生賽程。
4. **Given** 管理員在某場地比賽進行中時修改了團的比賽設定，**Then** 正在進行中的這場比賽仍依修改前的設定繼續判定勝負，新設定僅套用於後續尚未開始的新比賽。
5. **Given** 某團設有通關密碼，**When** 管理員通過驗證進入管理頁，**Then** 可查看到該密碼的明文內容並可修改；同一組密碼透過無需驗證的畫面（如嘎團加入頁的密碼輸入框）不會被回傳明文，僅能驗證輸入是否正確。
6. **Given** 管理員欲將人數上限修改為超過系統參數 `max_group_members` 目前上限的數值，**Then** 系統拒絕此次修改並提示錯誤（前端與後端皆需執行此驗證）。

### User Story 5 - 團閒置自動解散 (Priority: P2)

團若持續 1 小時無任何寫入類活動（比分變動、比賽結束、Next Round 觸發、成員異動、管理員編輯等），系統自動將其解散，行為與管理員手動解散完全相同，不需要管理員介入；純瀏覽行為不會重置這個計時器。

**Why this priority**: 這是保護系統不被閒置團長期佔用資源、並讓 Guest 身分自然失效的重要機制，但屬於「時間到才觸發」的背景行為，短期示範價值低於建立與手動解散兩個直接互動流程。

**Independent Test**: 可讓一個團在無任何寫入操作下經過模擬的 1 小時，驗證其自動進入已解散狀態且效果與手動解散一致；並讓另一個團持續有寫入活動，驗證其計時器持續重置、不會被自動解散，皆可獨立驗證。

**Acceptance Scenarios**:

1. **Given** 某團自最後一次活動起已超過 1 小時無任何比分變動、成員異動或管理操作，**Then** 系統自動將該團標記為解散，效果與手動解散完全相同（各連結失效、計分板唯讀、管理 PIN 碼僅唯讀可用、未收尾比賽轉為已捨棄）。
2. **Given** 某團持續有計分活動（例如每 10 分鐘一次 +1 操作），**Then** 即使團已開了超過 1 小時，也不會被自動解散，計時器隨每次活動重新起算。
3. **Given** 某團開啟「Auto Next Round」，賽程表自然消耗完畢觸發系統自動產生下一個 Round（過程中無任何管理員手動操作），**Then** 此次自動觸發同樣視為活動，重新起算 1 小時計時。
4. **Given** 某使用者僅開啟計分板頁面查看比分、未進行任何操作，**Then** 此瀏覽行為不會重置該團的無活動計時器。

---

### User Story 6 - 主動重設管理 PIN 碼 (Priority: P3)

已通過組團編號＋管理 PIN 碼驗證、目前正在管理頁內的使用者，可主動點擊「重新產生管理 PIN 碼」，經二次確認後系統核發一組全新的 6 碼 PIN 碼並立即使所有舊 PIN 碼／舊 token 失效，同時同步核發新 token 給觸發者本人，使其能無縫留在管理頁繼續操作。

**Why this priority**: 這是進階的憑證衛生管理功能（收回外洩的 PIN 碼），使用頻率遠低於建立、解散、日常編輯，屬於錦上添花但仍具價值的安全功能。

**Independent Test**: 可在已進入管理頁的狀態下觸發重設，獨立驗證新 PIN 碼可用、舊 PIN 碼與舊 token 皆失效、觸發者本人不需重新登入即可繼續操作，無需依賴其他功能。

**Acceptance Scenarios**:

1. **Given** 管理員已通過驗證進入管理頁，**When** 點擊「重新產生管理 PIN 碼」並在確認彈窗按下確認，**Then** 系統顯示一組全新的 6 碼 PIN 碼，原本的 PIN 碼立即失效、不可再用於進入管理頁；此功能不限已登入會員建立的團，匿名建立的團同樣可使用。
2. **Given** 管理員點擊「重新產生管理 PIN 碼」並確認，**Then** 系統同步為該管理員核發一組新的管理 token，使其可無縫繼續在管理頁進行後續操作，不會因為自己觸發這次重設而被要求重新輸入新 PIN 碼驗證。
3. **Given** 管理員重新產生管理 PIN 碼後，**When** 先前知道舊 PIN 碼的另一人嘗試以舊 PIN 碼重新驗證進入管理頁，**Then** 系統拒絕並顯示錯誤訊息；即使該人手上持有尚未過期的舊管理 token，下一次寫入操作也會因版本號不符而被拒絕。
4. **Given** 兩位管理員幾乎同時各自點擊「重新產生管理 PIN 碼」，**Then** 僅有先送達的請求成功執行，後到的請求因偵測到憑證版本已被搶先變更而被拒絕，並提示「此操作已被其他管理員執行，請重新整理頁面確認最新狀態」；不會出現兩次重設都成功疊加、導致先完成那方剛拿到的新 token 又立即失效的情況。
5. **Given** 管理員 A 正在編輯團名的同時，管理員 B 重新產生某場地的控制板連結，**Then** 兩個操作分屬不同的版本欄位，互不影響、皆可正常成功；**Given** 管理員 A 重新產生團的「加入連結」，管理員 B 幾乎同時重新產生同一團的「全部場地控制板連結」，**Then** 兩者分屬不同版本欄位，互不影響、皆可正常成功；僅當兩位管理員幾乎同時重新產生**同一種**連結時，後到的請求才會因版本衝突被拒絕。

---

### Edge Cases

- 兩位管理員幾乎同時點擊「重新產生管理 PIN 碼」時，如何確保不會兩次都成功疊加執行？（見 US6 情境 4：以版本欄位偵測衝突，後到者被拒絕並提示重新整理。）
- 管理員將比賽模式切換為雙打，但當時人數上限低於 4 時，系統如何避免團落入模式與人數上限互相矛盾的狀態？（見 US4 情境 2：阻擋修改並要求一併調高人數上限。）
- 組團編號序號跨越 999999 → 1000000 這個位數增加的邊界時，前端輸入框與顯示邏輯是否需要特殊處理？（見 US3 情境 3：不需要，序號本身自然增長即可。）
- Cloudflare Turnstile 驗證服務逾時或異常時，建團請求應如何處理，避免無限期卡住使用者？（需有明確的逾時/失敗處理方式，具體逾時秒數與重試策略留待後續規劃決定。）
- 團解散當下若同時有比賽處於「進行中」與「排隊中」，兩者是否都需要被妥善收斂，不留下任何懸空狀態？（見 US2 情境 4：兩者皆轉為已捨棄。）
- 客戶端在 `group.disbanded` 廣播當下剛好離線時，最壞情況下要多久才能得知團已解散？（見 US2 情境 6：下一次心跳檢查週期（上限 30 秒）或重新連線時。）
- 已解散團的組團編號＋PIN 碼是否可能被誤用來「復原」該團或進行任何寫入操作？（不可；僅提供唯讀查閱歷史紀錄。）

## Requirements *(mandatory)*

### Functional Requirements

**建立團（Create）**

- **FR-001**: 系統 MUST 提供開團表單，可設定：團名（必填）、通關密碼（選填）、人數上限（必填，正整數）、比賽模式（單打/雙打，二選一）、排程機制（公平輪替／手動安排／固定搭檔循環賽／個人全混搭循環賽，四選一）、比賽設定（見下方比賽設定區塊）、活動時間區間（選填）。
- **FR-002**: 團名 MUST 為必填，去除前後空白後不可為空字串，且長度不可超過 30 字；不符合時系統 MUST 提示錯誤且不可送出。
- **FR-003**: 人數上限 MUST 依當下選擇的比賽模式動態套用最小值：單打模式最小為 2 人、雙打模式最小為 4 人；低於對應最小值時系統 MUST 明確提示對應訊息（「單打模式人數上限至少需為 2 人」或「雙打模式人數上限至少需為 4 人」）且不可送出。此驗證 MUST 同時存在於前端與後端。
- **FR-004**: 人數上限 MUST 不可超過系統參數 `max_group_members`（預設 200）當下的數值；超過時系統 MUST 提示「人數上限不可超過 X 人」（X 為當下讀取到的參數值）且不可送出。此驗證 MUST 同時存在於前端與後端。
- **FR-005**: 活動時間區間為選填欄位；若填寫其中一個欄位（開始或結束）則另一欄位視為必填，且開始時間 MUST 早於結束時間；不符合時系統 MUST 提示錯誤且不可送出。
- **FR-006**: 若管理員未填寫活動時間區間，任何列出該團的畫面（如嘎團列表）中對應該團的時間欄位 MUST 明確顯示文字「未提供時間」，MUST NOT 留空。
- **FR-007**: 開團表單 MUST 整合防機器人驗證機制，使用者送出表單時 MUST 一併夾帶驗證憑證；後端在建立團之前 MUST 先確認該憑證有效，驗證失敗（無效、逾期、或缺漏）時 MUST 拒絕本次建團請求並提示「驗證失敗，請重新嘗試」，MUST NOT 略過此驗證直接建立團。此驗證與團的通關密碼驗證是彼此獨立的兩件事，不可混用或互相取代。
- **FR-008**: 建立成功後，系統 MUST 產生唯一的「組團編號」——採用可手動輸入辨識的數字序號（單調遞增、永不重複分配、不設碼數上限，不需要特別的位數格式轉換邏輯），以及一組 6 碼「管理 PIN 碼」（僅由數字 0-9 組成）；兩者 MUST 顯示於管理頁供記錄，管理 PIN 碼 MUST NOT 明文儲存。
- **FR-009**: 開團者暱稱來源 MUST 依身分決定：已登入且已設定暱稱的會員直接使用其會員暱稱、不需額外輸入（尚未設定暱稱者 MUST 先完成暱稱設定才能繼續建立團）；未登入（匿名）建立團時，表單 MUST 額外要求輸入暱稱（必填，長度不可超過 20 字，超過時 MUST 提示錯誤且不可送出）。
- **FR-010**: 開團者本人建立成功後 MUST 自動被加入該團的輪替名單成為一般參與者（而非僅有管理員/組織角色），顯示名稱使用其開團者暱稱，且 MUST NOT 需要再另外透過加入流程加入自己建立的團；開團者同時保留管理員身分，可存取僅限管理員的操作。
- **FR-011**: 若開團者為匿名身分，建立團成功時系統 MUST 同時核發該團的 Guest Session Token 給開團者，使其具備與一般訪客參與者相同的身分延續機制；若開團者為已登入會員身分，則 MUST NOT 額外核發此 token（直接以會員帳號辨識）。
- **FR-012**: 團建立當下，系統 MUST 將目前有效成員數初始化為 1（對應開團者本人自動加入輪替名單這件事），作為後續加入團人數上限判斷的起始基準值。
- **FR-037**: 通關密碼為選填欄位；若有填寫，長度 MUST 為 1 至 20 字之間，超過 20 字時系統 MUST 提示錯誤且不可送出。此驗證 MUST 同時存在於前端與後端，並同樣適用於管理頁修改通關密碼時（見 FR-021）。

**比賽設定（Match Scoring Settings）**

- **FR-013**: 系統 MUST 提供獨立的「比賽設定」區塊，決定每一場比賽的目標分數與勝負規則，提供三種模式，預設為「21 分制」：
  - 21 分制：目標分數 21 分；20:20 後需領先對手 2 分才算獲勝；若戰至 29:29，先達 30 分的一方直接獲勝（30 分封頂）。
  - 15 分制：目標分數 15 分；14:14 後需領先對手 2 分才算獲勝；若戰至 20:20，先達 21 分的一方直接獲勝（21 分封頂）。
  - 自訂：需額外填寫三個必填欄位——比賽結束分數（目標分數）、開始需領先兩分才算贏的門檻分數、封頂分數。
- **FR-014**: 選擇「自訂」模式時，系統 MUST 驗證：目標分數為正整數（至少為 1），填入 0、負數、非整數或留空時 MUST 提示錯誤且不可送出；門檻分數 MUST 為正整數且不大於目標分數；封頂分數 MUST 大於或等於門檻分數，且 MUST 大於或等於目標分數（避免出現「比賽永遠不可能打到目標分數就先封頂」的邏輯矛盾），不符合時 MUST 提示數字組合不合理且不可送出。
- **FR-015**: 比賽設定 MUST 為團級別設定，套用於該團底下所有場地的所有比賽，MUST NOT 支援不同場地各自套用不同比賽設定。
- **FR-016**: 比賽設定 MUST 可在管理頁隨時修改；修改後 MUST 僅影響尚未開始的新比賽，MUST NOT 回溯影響正在進行中或已完成的比賽——已進行中的比賽 MUST 維持其建立當下適用的設定值不變。

**管理頁編輯（Manage）**

- **FR-017**: 管理員 MUST 可在管理頁就地編輯團名，規則同 FR-002。
- **FR-018**: 管理員 MUST 可在管理頁編輯活動時間區間，規則同 FR-005、FR-006。
- **FR-019**: 管理員 MUST 可在管理頁修改比賽模式；修改後 MUST 僅影響下一個 Round 開始產生的賽程所使用的模式，MUST NOT 回溯影響或中斷當前 Round 正在進行中的比賽。若管理員希望新模式立即生效，MUST 可透過手動觸發「Next Round」（強制結束目前 Round，未完成比賽視為已捨棄）達成。
- **FR-020**: 若管理員將比賽模式從單打切換為雙打，且當時的人數上限低於 4 人，系統 MUST 同步提示並要求管理員一併調高人數上限至滿足新模式的最小值，MUST NOT 讓修改在人數上限與比賽模式互相矛盾的狀態下生效。
- **FR-021**: 管理員 MUST 可在管理頁隨時查看該團目前設定的通關密碼明文（若有設定），並 MUST 可修改（重新設定）通關密碼；此明文查看功能 MUST 僅限透過組團編號＋管理 PIN 碼驗證後的管理頁提供，MUST NOT 出現在任何無需驗證即可開啟的畫面上。
- **FR-022**: 管理員修改人數上限時，MUST 同樣受 FR-003、FR-004 的最小值與最大值限制約束，且此驗證 MUST 同時存在於前端與後端（後端 MUST NOT 僅信任前端檢查）。

**重新驗證與 PIN 碼管理（Re-authentication & PIN Management）**

- **FR-023**: 未登入使用者 MUST 可透過輸入正確的組團編號與管理 PIN 碼重新驗證，取得該團的管理權限並進入管理頁；輸入錯誤時 MUST 顯示錯誤訊息且不可進入。
- **FR-024**: 組團編號＋管理 PIN 碼的驗證 MUST 具備基本防暴力破解機制（例如錯誤次數限制），以防止 PIN 碼被窮舉猜出。
- **FR-025**: 管理頁 MUST 提供「重新產生管理 PIN 碼」操作入口，任何已通過驗證、目前在管理頁內的使用者皆可觸發，MUST NOT 限制僅限已登入會員建立的團才能使用。觸發前 MUST 提供二次確認流程（告知舊 PIN 碼將立即失效）。
- **FR-026**: 確認重新產生 PIN 碼後，系統 MUST 產生一組全新的 6 碼 PIN 碼並顯示給使用者，原本已核發的所有管理 token（含觸發者當下持有的）MUST 立即全部失效；同一筆操作中，系統 MUST 同步為觸發此操作的使用者核發一組新的有效管理 token，使其可無縫繼續留在管理頁操作，MUST NOT 要求觸發者重新輸入新 PIN 碼才能繼續。
- **FR-027**: 當兩個重新產生 PIN 碼（或其他會使憑證版本異動的操作）的請求幾乎同時送達時，系統 MUST 僅讓先送達者成功執行，後到者 MUST 被拒絕並提示「此操作已被其他管理員執行，請重新整理頁面確認最新狀態」，MUST NOT 讓兩次請求都成功疊加執行。
- **FR-028**: 系統 MUST 對互不相關的可修改面向（例如：團基本設定、加入連結、全部場地控制板連結、單一場地控制板連結、管理憑證版本）使用各自獨立的版本追蹤，MUST NOT 讓修改其中一項的操作被另一項無關操作的並發變更誤判為衝突。

**解散團（Disband）**

- **FR-029**: 管理員 MUST 可在管理頁解散團，觸發前 MUST 提供二次確認流程。
- **FR-030**: 團解散後，加入連結／QR Code、單一場地控制板連結、全部場地控制板連結、Guest Session Token MUST 立即全部失效，開啟或使用時 MUST 顯示「此團已解散」，MUST NOT 能再進行任何加入或操作動作。
- **FR-031**: 團解散後，計分板連結 MUST 仍可開啟，但 MUST 顯示「此團已解散」並停留在解散當下的最終比分作為唯讀紀錄，MUST NOT 再接收任何即時更新。
- **FR-032**: 團解散後，組團編號與管理 PIN 碼 MUST 仍然有效，但僅能開啟唯讀管理頁——MUST 可查看該團解散前的最終戰績、對戰紀錄、賽程歷史，MUST NOT 可進行任何寫入操作（編輯、新增/刪除場地、踢除成員、Next Round 等），且 MUST NOT 能復原已解散的團。
- **FR-033**: 解散當下，若賽程表中仍有比賽處於「排隊中」或「進行中」狀態，系統 MUST 將這些比賽一併轉為「已捨棄」，MUST NOT 產生賽果、MUST NOT 計入任何一方的戰績或對戰紀錄；此規則對管理員手動解散與自動解散機制觸發的情況皆同樣適用，MUST NOT 讓任何比賽的狀態永遠停留在這兩種未收尾狀態。
- **FR-034**: 解散團（不論手動或自動觸發）的同一筆交易後，系統 MUST 立即通知所有已連線的相關畫面（該團底下每個場地各自的即時頻道、以及一個涵蓋全部場地與管理頁的團層級通知頻道皆須各自收到通知，MUST NOT 僅依賴單一群組層級的廣播涵蓋所有場地）；收到通知的畫面 MUST 停止監聽並切換為對應的「此團已解散」提示或唯讀狀態。
- **FR-035**: 系統 MUST 提供心跳檢查機制作為即時通知的備援，心跳檢查週期上限 MUST 為 30 秒，確保剛好在通知發出當下離線的客戶端，最壞情況下仍會在 30 秒內的下一次心跳檢查週期內或重新連線時偵測到團已解散並顯示對應提示。
- **FR-036**: 團若持續 1 小時無任何符合下列定義的活動，系統 MUST 自動將其解散，效果 MUST 與管理員手動解散完全相同（含 FR-030～FR-035 所定義的全部影響範圍），MUST NOT 需要管理員介入。「活動」MUST 涵蓋：任何比分變動、比賽結束（達標或提前結束）、Next Round 觸發（不論管理員手動觸發或系統依既定條件自動觸發）、成員加入/退出/被踢除、管理員在管理頁的任何編輯操作（含建立團本身）；每次符合上述定義的活動發生時，MUST 重新起算 1 小時計時。純粹的唯讀瀏覽行為 MUST NOT 被視為活動、MUST NOT 重置計時器。

### Key Entities *(include if feature involves data)*

- **Group（團）**: 一次揪團場次的核心紀錄。屬性含：團名、通關密碼（可還原加密儲存）、人數上限、比賽模式、排程機制、活動時間區間（選填）、目前有效成員數、狀態（進行中／已解散）、最後活動時間、以及數個彼此獨立的版本欄位（基本設定版本、加入連結版本、全部場地控制板連結版本、管理憑證版本）。
- **Match Scoring Settings（比賽設定）**: 附屬於 Group 的團級別設定，記錄目前生效的模式（21分制／15分制／自訂）與對應的目標分數、deuce 門檻、封頂分數；每筆 Match 建立時複製（快照）當下的數值到該筆比賽紀錄本身，使已進行中的比賽不受後續團設定變更影響。
- **Admin Credential（管理憑證）**: 組團編號（單調遞增、永不重複分配的數字識別碼）與 6 碼管理 PIN 碼（僅由數字 0-9 組成，雜湊儲存）的配對，附帶一個憑證版本號，用於驗證管理身分並於重設時使所有既有管理 token 一併失效。
- **Roster Entry / Player（輪替名單項目）**: 團底下的參與者名單項目，含顯示暱稱、是否為開團者本人、加入時間；開團者建立團成功時自動產生一筆此紀錄。
- **Guest Session Token（訪客身分延續憑證）**: 匿名使用者（含匿名開團者）取得的身分延續憑證，用於後續識別其在輪替名單中對應的 Roster Entry；隨團解散而一併失效。
- **Court（場地，關聯實體）**: 團底下的場地，各自擁有獨立的控制板連結版本；本功能僅涉及其連結因團解散而失效、以及解散通知需逐一送達每個場地各自的即時頻道，場地本身的建立與管理為其他功能範圍。
- **SystemConfig（系統參數，關聯實體）**: 系統層級參數集合；本功能使用其中的 `max_group_members`（人數上限硬上限，預設 200）作為建立與修改人數上限時的驗證依據。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 使用者（含完全未登入者）從開啟開團表單到成功建立團並看到組團編號與管理 PIN 碼，可在 3 分鐘內完成整個流程。
- **SC-002**: 持續無任何寫入活動超過 1 小時的團，100% 會被系統自動轉為已解散狀態，且效果與手動解散完全一致，不需要任何管理員介入。
- **SC-003**: 持續有寫入活動的團，0% 會被誤判為閒置而自動解散——只要活動間隔小於 1 小時，計時器即持續被重置。
- **SC-004**: 團解散後，處於連線狀態的相關畫面（計分板、控制板、全部場地控制板、管理頁）平均在約 1 秒內切換為對應的已解散提示或唯讀狀態；離線的客戶端最慢在 30 秒內（下一次心跳檢查週期）或重新連線後即可得知。
- **SC-005**: 解散後的團，0% 留下任何比賽永遠停留在「排隊中」或「進行中」狀態；所有未收尾比賽皆確實轉為已捨棄。
- **SC-006**: 組團編號在系統運作期間 100% 不重複分配，即使發出的編號數量遠超過正常運作規模的預期範圍，系統仍可持續正常發出新編號。
- **SC-007**: 未通過機器人驗證的建團請求，0% 會成功建立團。
- **SC-008**: 持有正確組團編號與管理 PIN 碼的使用者，可在 30 秒內重新取得管理頁的完整存取權限；持有錯誤憑證者 100% 被拒絕，且系統對短時間內多次錯誤嘗試套用防護機制。
- **SC-009**: 團的通關密碼明文，0% 會出現在任何無需通過管理驗證即可開啟的畫面上。
- **SC-010**: 兩位管理員幾乎同時觸發同一項會變更憑證/連結版本的操作時，100% 僅有一方成功、另一方收到明確的衝突提示，不會發生兩次操作都成功疊加執行的情況。

## Assumptions

- 本功能所引用的周邊功能——嘎團加入流程、單一/全部場地控制板、計分板顯示、一般成員視圖（查看戰績、主動退出）、「忘記管理 PIN 碼」的會員復原流程、比賽正常結束的判定邏輯——皆視為由其他功能規格涵蓋；本規格僅涵蓋團的建立、設定管理、重新驗證與解散（含自動解散）之生命週期，並定義與周邊功能的互動邊界（連結失效範圍、Guest Session Token 核發與失效、比賽設定快照、解散即時通知、比賽狀態收斂）。
- 排程機制的四個選項（公平輪替／手動安排／固定搭檔循環賽／個人全混搭循環賽）在本功能中僅需可被選擇、儲存與後續修改；各排程演算法本身的具體行為由其他功能規格定義。
- 場地（Court）的建立與數量管理為其他功能範圍；本功能僅處理場地相關連結因團解散而失效、以及解散通知需逐一送達每個場地頻道的行為邊界。
- 管理 PIN 碼防暴力破解機制採業界常見作法（例如短時間內多次錯誤嘗試觸發暫時鎖定），確切門檻值（嘗試次數、鎖定時長）留待後續規劃階段決定，不影響本規格定義的使用者可觀察行為。
- 管理 token 的有效期限採一般 session 憑證的合理預設值，實務上進一步受「1 小時無活動即自動解散」機制限制其實際可用時長。
- 「暱稱」在本功能中為純顯示用途的自由文字欄位，不綁定任何帳號身分，其性質與其他功能中訪客加入時所填寫的暱稱一致。
- Cloudflare Turnstile 服務逾時或異常時，系統需有明確且不無限期卡住使用者的失敗處理方式；具體逾時秒數、重試次數等實作細節留待後續規劃階段決定。
