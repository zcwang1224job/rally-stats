# Feature Specification: 加入團（嘎團）（Join Group）

**Feature Branch**: `[004-join-group]`

**Created**: 2026-08-31

**Status**: Draft

**Input**: User description: "建立「加入團（嘎團）」功能：

使用者故事：作為想加入某場揪團的使用者，我可以在開團列表中瀏覽/搜尋公開的場次，查看場地、時間、目前人數，若該團設有通關密碼則需先輸入正確密碼；若我尚未登入，最後需輸入暱稱（Guest 模式）才能加入；若我已登入會員帳號，系統直接使用我的會員暱稱完成加入，不需要再另外輸入暱稱。此外，使用者也可透過管理員分享的「加入連結」或掃描對應的 QR Code，直接進入該團的加入流程，不需要先在開團列表中搜尋。

功能需求（節錄，已定案項目）：
- 加入團流程本次不整合 Cloudflare Turnstile 或任何 CAPTCHA 機制，維持零門檻的 Guest 加入體驗；濫用防範暫時仰賴人數上限、通關密碼、1 小時自動解散等既有機制自然限縮；若未來偵測到實際濫用，另行 `/specify` 評估追加 Turnstile/速率限制等強化手段，本次僅記錄方向、不預先實作。
- 開團列表顯示：團名、開團者暱稱、目前人數/上限、比賽模式、場地名稱、時間、是否需要密碼；「是否需要密碼」狀態不可純粹依賴顏色區分，需同時滿足圖示形狀（鎖上/鎖開）與文字標籤或輔助文字（aria-label/title）至少兩種區分方式，顏色僅作輔助強化。
- 提供依「場地名稱」與「場地 ID」搜尋/篩選開團列表，支援分頁瀏覽；另可依「活動時間區間」篩選，套用時間篩選時未填寫時間區間的團一律排除，未套用時則正常顯示。
- 管理員在管理頁可取得該團專屬的「加入連結」與對應 QR Code（不可猜測的隨機 Token）；掃描或點擊後直接導向加入流程，略過列表搜尋；若團已解散/已滿/連結已失效，顯示對應明確錯誤畫面，不可導向一般錯誤頁或空白頁；後續流程與從列表點擊「加入」完全一致。
- 人數上限檢查分兩層：(1) 前置檢查（UX 用）——真正建立加入記錄之前先讀取 `current_member_count` 是否已達上限，已滿則提早提示並中止，適用所有加入路徑；(2) 最終保證——真正建立 Player 記錄當下改用原子性 `UPDATE ... WHERE current_member_count < max_members` 作為唯一事實依據，前置檢查通過不代表最終一定成功。「目前人數」僅計算 active 狀態 Player，不含 left/kicked，退出/被踢除立即釋放名額。
- 若團設通關密碼，導向密碼頁，錯誤時提示「通關密碼錯誤」可重新輸入；此驗證不設錯誤次數限制或鎖定機制（與需防暴力破解的管理 PIN 碼驗證是不同兩套規則，不可混用）。
- 密碼驗證通過（或無需密碼）後依登入狀態分流：未登入者導向暱稱輸入頁（暱稱僅本次加入顯示用，一經加入即固定不提供修改，欲更換需先退出組團再重新走加入流程）；已登入且已設定暱稱的會員不顯示暱稱頁、直接用會員暱稱完成加入；已登入但尚未設定暱稱者導向首次登入暱稱設定流程，完成後自動接續完成加入。
- Guest 完成加入後核發一次性 Guest Session Token（僅該團範圍有效，不可跨團、不具會員權限），供重新整理/斷線重連後辨識同一身分並還原狀態（不建立新 Player 記錄）；團解散、Guest 主動退出、或被管理員踢除時，該 Token 立即失效，之後需視為無有效 Token、走全新加入流程；長期未使用的失效問題已由團的 1 小時自動解散機制涵蓋，不需額外的獨立過期機制。
- 加入成功後使用者被加入該團的輪替名單/賽程中；已登入會員版本的開團列表另外呈現個人化資訊（如自己已加入的團）。

（完整驗收情境已於下方各使用者故事的 Given/When/Then 場景中完整轉譯，此處保留原始輸入之決策摘要。）"

## Clarifications

### Session 2026-08-31

- Q: 已登入會員透過加入連結/QR Code 再次進入自己已是 active 成員的團時，系統應如何處理？ → A: 自動導向現有狀態，不建立新記錄，不重新走密碼驗證與人數上限檢查
- Q: FR-006「已加入的團」個人化清單範圍是否包含已解散的團？ → A: 僅包含仍為進行中（未解散）的團

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 從開團列表瀏覽並加入公開場次 (Priority: P1)

想加入揪團的使用者在開團列表中瀏覽場次，點擊「加入」後（若該團設有通關密碼則先驗證密碼），依登入狀態完成暱稱處理（Guest 輸入暱稱，或會員直接使用會員暱稱），成功加入該團的輪替名單。

**Why this priority**: 這是「加入團」功能最基本的入口與完整閉環——沒有它，使用者完全無法透過瀏覽列表加入任何團，是本功能存在的核心理由。

**Independent Test**: 可在一個已存在、無密碼保護的團上，以未登入身分完整走過「開團列表 → 點擊加入 → 輸入暱稱 → 加入成功」流程，並另外對一個有密碼保護的團測試密碼驗證步驟，均可獨立驗證，無需依賴 QR Code 或 Guest 身分延續等其他功能。

**Acceptance Scenarios**:

1. **Given** 某團設有通關密碼，**When** 使用者輸入錯誤密碼並送出，**Then** 顯示「通關密碼錯誤」且停留在該頁，可重新輸入。
2. **Given** 某使用者連續輸入錯誤的通關密碼超過 10 次，**Then** 系統仍允許其繼續嘗試輸入，不會鎖定、暫時封鎖，或要求額外的人機驗證。
3. **Given** 使用者尚未登入，且密碼正確或該團無密碼，**When** 使用者輸入暱稱並確認，**Then** 以該暱稱成功加入該團並可看到自己的輪替名單狀態，且瀏覽器取得該團的 Guest Session Token。
4. **Given** 使用者尚未登入並準備以 Guest 身分加入，**When** 輸入的暱稱為空白（或僅有空白字元）、或超過 20 個字元，**Then** 系統提示格式錯誤，不可送出。
5. **Given** 某團內已有一位暱稱為「小明」的 active 成員，**When** 另一位使用者也以「小明」這個暱稱加入該團（Guest 或會員皆可），**Then** 系統允許成功加入、不阻擋此次加入，僅在計分板、賽程頁、戰績、對戰紀錄等畫面顯示時自動為兩人加上區分序號（例如「小明」與「小明⑵」），底層儲存的暱稱資料本身不受影響。

---

### User Story 2 - 透過加入連結／QR Code 直接加入 (Priority: P1)

使用者掃描管理員分享的 QR Code 或點擊加入連結，直接進入該團的加入流程（略過開團列表搜尋），若團已解散、已滿或連結已失效則看到明確的錯誤提示。

**Why this priority**: 這是使用者故事中明確點出的另一個對等入口（現場出示 QR Code 是揪團活動的常見加入方式），與列表瀏覽同屬最小可行的加入路徑，優先序相同。

**Independent Test**: 可用一個團的加入連結分別測試「團正常可加入」「團已解散」「團已滿」三種情境，獨立驗證導向流程與錯誤畫面，無需依賴開團列表的搜尋/篩選功能。

**Acceptance Scenarios**:

1. **Given** 使用者掃描某團的加入 QR Code（或點擊加入連結），**Then** 直接進入該團的加入流程（需要密碼則先驗證密碼，接續依登入狀態處理暱稱），不需經過開團列表搜尋。
2. **Given** 使用者掃描的 QR Code 對應的團已解散或人數已滿，**Then** 畫面顯示對應的明確提示訊息（如「此團已解散」「此團人數已滿」），且不可繼續加入流程，不會導向一般錯誤頁或空白頁。

---

### User Story 3 - 人數上限的兩層檢查與併發控制 (Priority: P1)

系統在使用者送出加入請求前先做一次快速的人數上限提示，並在真正建立加入記錄的當下以原子性條件更新作為唯一事實依據，確保即使多人幾乎同時搶最後名額，也不會有超過人數上限的加入成功。

**Why this priority**: 這是保護資料完整性（`current_member_count` 不可能超過 `max_members`）的關鍵正確性機制，任何加入路徑都必須遵守，與建立加入流程本身同等重要，缺一則系統可能產生超賣（overbooking）的錯誤資料。

**Independent Test**: 可對一個僅剩 1 個名額的團，模擬兩個幾乎同時送出的最終加入請求，獨立驗證僅一方成功、`current_member_count` 正確不超過上限；亦可獨立測試已滿的團在前置檢查階段就被擋下，均無需依賴其他使用者故事。

**Acceptance Scenarios**:

1. **Given** 某團目前人數已達人數上限，**When** 使用者透過開團列表點擊「加入」（非 QR Code 路徑），**Then** 系統顯示「此團人數已滿」，不進入密碼驗證或暱稱輸入步驟。
2. **Given** 某團目前人數已達人數上限（因此新使用者無法加入），**When** 團內有一位成員主動退出組團，**Then** 該團「目前人數」立即減少 1，此時新使用者透過加入連結進入即可正常通過人數上限檢查、成功加入。
3. **Given** 某團人數上限為 10 人、目前已有 9 位有效成員（僅剩 1 個名額），**When** 兩位不同使用者幾乎同時完成密碼驗證與暱稱輸入、同時送出最終加入請求，**Then** 系統僅有其中一位成功加入（`current_member_count` 正確變為 10），另一位收到「此團人數已滿」的錯誤訊息，不會出現兩人皆加入成功、實際人數超過上限的情況。
4. **Given** 某使用者在前置檢查當下該團尚有名額、通過檢查並開始輸入密碼與暱稱，**When** 在其送出最終加入請求前，該團最後 1 個名額已被另一位使用者搶先佔用，**Then** 該使用者送出時仍會被拒絕並顯示「此團人數已滿」，不會因為前置檢查曾經通過就被誤判為加入成功。
5. **Given** 某團的 `current_member_count` 欄位數值，**When** 與該團目前實際狀態為 active 的 Player 筆數比對，**Then** 兩者應隨時保持一致（加入、退出、被踢除皆在同一筆交易內同步更新此欄位）。

### User Story 4 - Guest 身分延續性 (Priority: P2)

Guest 使用者成功加入某團後，重新整理頁面或短暫斷線重連時，系統能正確識別出是同一人並還原原本狀態，而不是被當成新的加入者；若該團解散、或該 Guest 已退出/被踢除，系統則能正確判定其憑證已失效。

**Why this priority**: 這是「Guest 不需要註冊帳號」核心體驗的必要支撐——沒有它，Guest 每次重新整理頁面都會被迫重新走一次完整加入流程，體驗會嚴重劣化；但即使暫時沒有這個機制，Guest 仍能完成一次性加入，因此優先序次於基本加入流程本身。

**Independent Test**: 可讓一個 Guest 使用者加入某團後模擬重新整理頁面，獨立驗證狀態被正確還原；亦可分別對「團已解散」與「該 Guest 已退出/被踢除」兩種情境測試 Token 失效行為，均可獨立驗證，無需依賴會員登入相關功能。

**Acceptance Scenarios**:

1. **Given** Guest 使用者已成功加入某團並取得該團的 Guest Session Token，**When** 該使用者重新整理頁面或短暫斷線後重新連線，**Then** 系統辨識出同一 Guest 身分，直接還原其原本在輪替名單/賽程表中的狀態，不重複建立新的加入記錄、也不需要重新輸入暱稱。
2. **Given** 使用者的瀏覽器沒有任何該團的 Guest Session Token（例如換裝置或清除過資料），**When** 該使用者再次透過加入連結進入，**Then** 視為全新加入流程，需重新完成密碼驗證與輸入暱稱。
3. **Given** 某團已被管理員解散，**When** 持有該團舊 Guest Session Token 的使用者再次開啟該團的頁面，**Then** 該 Token 視為無效，畫面顯示「此團已解散」，無法用該 Token 還原任何狀態。
4. **Given** 某 Guest 使用者主動退出組團（或被管理員踢除），**When** 該使用者的瀏覽器之後重新開啟該團頁面，**Then** 系統判定其原本的 Guest Session Token 已失效，導向全新的加入流程（含通關密碼驗證，若該團有設密碼），而非直接還原其退出/被踢除前的狀態。
5. **Given** Guest 使用者已成功加入某團，**Then** 系統不提供任何修改該次加入暱稱的入口（不存在 Guest 版本的「個人設定頁」）；若該 Guest 想更換顯示名稱，需先「退出組團」，再重新走一次加入流程並輸入新暱稱，此舉會建立新的 Player 記錄與新的 Guest Session Token。

### User Story 5 - 開團列表篩選與可訪問性顯示 (Priority: P2)

使用者可依場地名稱、場地 ID、活動時間區間搜尋/篩選開團列表，並能透過圖示形狀與文字標籤（而非僅靠顏色）清楚分辨哪些團需要通關密碼。

**Why this priority**: 這是讓使用者在列表中「找到想加入的那一場」的體驗優化，建立在列表本身已存在的基礎之上；沒有篩選功能，使用者仍能瀏覽完整列表找到目標團，因此優先序次於加入流程本身。

**Independent Test**: 可在一個有多筆場次資料的開團列表上，分別測試場地名稱搜尋、時間區間篩選、以及色盲/灰階模式下的密碼狀態辨識，均可獨立驗證，無需依賴加入流程是否完成。

**Acceptance Scenarios**:

1. **Given** 使用者於開團列表搜尋欄輸入場地名稱，**Then** 列表即時篩選出符合條件的場次。
2. **Given** 使用者在開團列表套用「活動時間區間」篩選條件，**Then** 所有未填寫活動時間區間的團一律不會出現在篩選結果中；若使用者未套用時間篩選，這些團仍會正常顯示於完整列表。
3. **Given** 開團列表中同時存在需密碼與公開的團，**When** 色盲使用者（或以灰階模式檢視畫面）查看列表，**Then** 仍可透過鎖頭圖示的開/闔形狀與文字標籤（或輔助文字）正確分辨哪些團需要密碼，不需仰賴紅色/藍色的顏色差異即可判斷。

---

### User Story 6 - 已登入會員的加入差異化與個人化列表 (Priority: P3)

已登入會員加入團時不需要再輸入暱稱（直接使用會員暱稱），尚未設定暱稱的會員會先被導向設定流程；已登入會員檢視開團列表時，還能看到自己已加入的團等個人化資訊。

**Why this priority**: 這是會員帳號相對 Guest 的加分體驗（少一個步驟、多一層個人化），但即使沒有這個差異化，會員仍可以 Guest 方式完成加入，因此是三者中優先序最低的一個。

**Independent Test**: 可分別用「已設定暱稱的會員」與「尚未設定暱稱的會員」兩種帳號測試加入流程的差異，並檢視開團列表是否正確呈現個人化資訊，均可獨立驗證，無需依賴 Guest 相關流程。

**Acceptance Scenarios**:

1. **Given** 使用者已登入會員帳號且已設定暱稱，且密碼正確或該團無密碼，**When** 使用者點擊加入，**Then** 系統不顯示暱稱輸入頁，直接以會員暱稱完成加入。
2. **Given** 使用者已登入但尚未設定過暱稱，**When** 通過密碼驗證後，**Then** 導向首次登入的暱稱設定頁，設定完成後自動視為已加入該團，不需再次操作。
3. **Given** 已登入會員在某團已擁有一筆 active 狀態的 Player 記錄，**When** 該會員之後又透過該團的加入連結或 QR Code 再次進入，**Then** 系統直接導向其現有的輪替名單/賽程狀態，不建立新的 Player 記錄、不重新要求通關密碼、不重新執行人數上限檢查，行為比照 Guest 憑有效 Token 還原狀態的精神一致。
4. **Given** 已登入會員檢視開團列表的個人化「已加入的團」清單，**Then** 清單僅顯示目前仍為進行中（未解散）的團，該會員曾加入但已解散的團不會出現在此清單中。

---

### Edge Cases

- 使用者在前置人數上限檢查通過後，於密碼驗證或暱稱輸入過程中放棄離開（未送出最終加入請求），是否會佔用名額？（不會，名額僅在最終加入記錄真正建立、`current_member_count` 真正遞增時才視為佔用；中途放棄不留下任何記錄。）
- 同一位已登入會員是否可對同一團重複加入多次（產生多筆 Player 記錄）？（見 FR-020a：不會，系統偵測到該會員在該團已有 active 的 Player 記錄時，直接導向其現有狀態，不建立新記錄，行為比照 Guest Token 還原機制。）
- 開團列表在使用者瀏覽期間，某團剛好被解散或滿員，列表項目是否即時更新？（列表為瀏覽性質的查詢畫面，非需要即時 Ably 訂閱的操作畫面；若使用者點擊當下該團狀態已變化，仍會在前置檢查或最終保證階段被正確攔截並提示，不會導致加入成功但底層資料矛盾。）

## Requirements *(mandatory)*

### Functional Requirements

**防機器人驗證範圍**

- **FR-001**: 加入團流程本次 MUST NOT 整合 Cloudflare Turnstile 或任何 CAPTCHA 機制，維持零門檻的 Guest 加入體驗；濫用防範暫時仰賴人數上限、通關密碼、1 小時無活動自動解散等既有機制自然限縮。

**開團列表顯示與搜尋**

- **FR-002**: 開團列表 MUST 顯示：團名、開團者暱稱、目前人數/上限、比賽模式（單打/雙打）、場地名稱、時間、是否需要密碼。
- **FR-003**: 開團列表 MUST 提供依「場地名稱」與「場地 ID」搜尋/篩選功能，並 MUST 支援分頁瀏覽。
- **FR-004**: 開團列表 MUST 提供依「活動時間區間」篩選；使用者套用時間篩選條件時，未填寫活動時間區間的團 MUST 自動排除於篩選結果之外；使用者未套用時間篩選時，這些團 MUST 正常顯示於完整列表中。
- **FR-005**: 「是否需要密碼」狀態顯示 MUST NOT 純粹依賴顏色區分，MUST 同時滿足「圖示形狀」（例如鎖上/鎖開形狀的鎖頭圖示）與「文字標籤或輔助文字」（例如簡短文字標籤，或 `aria-label`／`title` 屬性）至少兩種區分方式；顏色僅可作為輔助的視覺強化手段，MUST NOT 作為唯一的區分依據。
- **FR-006**: 已登入會員檢視開團列表時，系統 MUST 額外呈現登入狀態的個人化資訊（例如自己已加入的團）；此清單 MUST 僅包含目前仍為「進行中」（未解散）狀態的團，MUST NOT 包含已解散的團。

**QR Code／分享連結加入路徑**

- **FR-007**: 管理員 MUST 可在管理頁取得該團專屬的「加入連結」，並 MUST 可顯示對應的 QR Code。
- **FR-008**: 加入連結 MUST 使用不可猜測的隨機 Token（MUST NOT 直接以流水號或組團編號拼湊）；掃描或點擊後 MUST 直接導向該團的加入流程，略過開團列表的搜尋/瀏覽步驟。
- **FR-009**: 若該團已解散、已達人數上限、或連結已失效，掃描/點擊後 MUST 顯示對應的明確錯誤畫面（如「此團已解散」「此團人數已滿」），MUST NOT 導向一般錯誤頁或空白頁。
- **FR-010**: 透過加入連結/QR Code 進入後的後續流程（是否需通關密碼、已登入/未登入的暱稱處理）MUST 與從開團列表點擊「加入」完全一致，僅進入點不同（略過列表搜尋）。

**人數上限檢查（兩層）**

- **FR-011**: 使用者從任一加入路徑（開團列表點擊「加入」、QR Code、分享連結）觸發加入流程時，系統 MUST 先執行前置檢查——讀取該團目前人數（`current_member_count`）是否已達人數上限；若已滿，MUST 顯示「此團人數已滿」，MUST NOT 繼續進行密碼驗證或暱稱輸入步驟。此前置檢查 MUST 適用於所有加入路徑，MUST NOT 僅限於 QR Code 路徑。
- **FR-012**: 「目前人數」MUST 僅計算輪替名單中狀態為 active（有效參與中）的 Player 數量，MUST NOT 包含狀態為 left（已退出）或 kicked（已被踢除）的成員；成員退出或被踢除時，其原本佔用的名額 MUST 立即釋放，供後續新加入者遞補。
- **FR-013**: 使用者完成密碼驗證與暱稱輸入、真正建立 Player 記錄的當下，系統 MUST 以原子性條件更新（`UPDATE ... WHERE current_member_count < max_members`）作為判斷是否仍有名額的唯一事實依據，MUST NOT 重新信任前置檢查當下讀到的數字。若此條件更新判定名額已滿（影響筆數為 0），MUST 在最後一步回饋「此團人數已滿」並中止加入，即使使用者先前已通過前置檢查、完成密碼驗證與暱稱輸入。
- **FR-014**: `current_member_count` 欄位 MUST 與該團目前實際狀態為 active 的 Player 筆數保持一致；加入、退出、被踢除 MUST 在同一筆交易內同步更新此欄位。

**通關密碼驗證（加入流程專用）**

- **FR-015**: 若該團設有通關密碼，系統 MUST 導向輸入通關密碼頁；密碼錯誤時 MUST 顯示明確錯誤訊息「通關密碼錯誤」，MUST 可重新輸入。
- **FR-016**: 此通關密碼驗證 MUST NOT 設任何錯誤次數限制或鎖定機制，MUST 允許使用者不斷重試直到輸入正確為止；此規則與管理 PIN 碼驗證（具備防暴力破解機制）為不同的兩套規則，MUST NOT 混用或共用同一套驗證機制或程式碼路徑。

**登入狀態分流（暱稱處理）**

- **FR-017**: 密碼驗證通過（或該團無需密碼）後，未登入使用者（Guest）系統 MUST 導向輸入暱稱頁；暱稱 MUST 為必填，去除前後空白後不可為空字串，且長度不可超過 20 字；不符合時 MUST 提示錯誤且不可送出。
- **FR-018**: 已登入且已設定暱稱的會員，系統 MUST NOT 顯示暱稱輸入頁，MUST 直接使用其會員暱稱完成加入。
- **FR-019**: 已登入但尚未設定暱稱的會員，系統 MUST 導向首次登入設定暱稱流程；設定完成後 MUST 自動接續完成加入，MUST NOT 另外導向加入團專用的暱稱輸入頁。
- **FR-020**: 若加入時使用的暱稱與該團內現有 active 成員的暱稱完全相同，系統 MUST 允許此次加入成功，MUST NOT 阻擋此次加入；僅於計分板、賽程頁、戰績、對戰紀錄等顯示畫面，MUST 自動為重複暱稱加上區分序號（例如「小明」與「小明⑵」），底層儲存的暱稱資料本身 MUST NOT 因此受影響。
- **FR-020a**: 已登入會員透過任一加入路徑（開團列表、QR Code、加入連結）進入某團的加入流程時，系統 MUST 先檢查該會員帳號在該團是否已擁有狀態為 active 的 Player 記錄；若有，系統 MUST 直接導向其現有的輪替名單/賽程狀態，MUST NOT 建立新的 Player 記錄，MUST NOT 重新要求通關密碼驗證，MUST NOT 重新執行人數上限檢查（FR-011、FR-013）；此規則與 Guest 透過 Guest Session Token 辨識同一人、還原狀態（FR-023）之精神一致，僅辨識依據由 Token 改為會員帳號與團的既有 active Player 記錄配對。
- **FR-021**: Guest 完成加入後，系統 MUST NOT 提供任何修改該次加入暱稱的入口；Guest 若欲更換顯示名稱，MUST 先退出組團，再重新走一次加入流程並輸入新暱稱；此舉 MUST 建立新的 Player 記錄與新的 Guest Session Token。

**Guest 身分延續性（Guest Session Token）**

- **FR-022**: Guest 完成加入後，系統 MUST 核發一組一次性識別碼（Guest Session Token），與該次加入建立的 Player 記錄一對一綁定，並以瀏覽器端可保存方式（例如寫入加入連結對應網址的 URL 參數，並同時存入 Cookie/LocalStorage 作為備援）交由前端保存；此 Token MUST 僅在該團範圍內有效，MUST NOT 可跨團使用，MUST NOT 具備會員帳號的任何權限。
- **FR-023**: Guest 使用者重新整理頁面或行動網路斷線後重新連線時，前端 MUST 先檢查是否持有該團的 Guest Session Token；若有且有效，系統 MUST 依此 Token 辨識出同一人，直接還原其在輪替名單/賽程表中的現有狀態，MUST NOT 建立新的 Player 記錄，MUST NOT 視為重新加入一次；若無此 Token，MUST 視為全新的加入流程，需走完整的密碼驗證與暱稱輸入步驟。
- **FR-024**: 團的狀態變為已解散時，該團所有 Guest Session Token MUST 立即視為無效；之後即使瀏覽器仍保留該 Token，MUST NOT 可再用它還原任何狀態。
- **FR-025**: Guest 主動退出組團或被管理員踢除時，其 Guest Session Token MUST 立即失效；此後若瀏覽器仍保留舊 Token 並重新開啟該團頁面，系統 MUST 將其視為無有效 Token，並導向全新的加入流程（含通關密碼驗證，若該團有設密碼），MUST NOT 誤判為有效 Token 並讓已退出/被踢除的人自動被重新加入。
- **FR-026**: Guest Session Token MUST NOT 需要獨立的過期時間機制——團閒置超過 1 小時的自動解散機制（見「開團與管理」規格）已確保該團所有 Guest Session Token 隨團解散規則一併失效。

**加入完成**

- **FR-027**: 加入成功後，使用者 MUST 被加入該團的輪替名單/賽程中，並可查看自己的輪替名單狀態。

### Key Entities *(include if feature involves data)*

- **Group（團，關聯實體）**: 本規格使用其既有的通關密碼、人數上限、`current_member_count`、加入連結 Token、狀態（進行中/已解散）等欄位進行加入資格判斷；這些欄位本身的定義與管理屬「開團與管理」規格範圍。
- **RosterEntry / Player（輪替名單項目）**: 本規格定義其加入流程產生行為——每次成功加入建立一筆新記錄，狀態初始為 active，顯示暱稱來源依登入狀態決定（會員暱稱或 Guest 輸入暱稱）。
- **Guest Session Token（訪客身分延續憑證）**: 沿用「開團與管理」規格已定義的實體，本規格補完其在加入流程中的完整生命週期行為——核發時機、儲存方式、有效範圍、以及三種失效觸發條件（團解散、Guest 主動退出、被管理員踢除）。
- **Member（會員帳號，關聯實體）**: 本規格僅涉及其暱稱欄位（用於已登入會員的加入流程）與「是否已完成首次暱稱設定」的狀態判斷；會員帳號本身的註冊、驗證、登入邏輯屬其他功能規格範圍。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 使用者從開團列表點擊「加入」到成功加入並看到自己在輪替名單中的狀態，在無需輸入密碼的情況下，可在 30 秒內完成整個流程（含暱稱輸入時間）。
- **SC-002**: 兩位使用者對同一團僅剩最後 1 個名額幾乎同時送出最終加入請求時，100% 只有一位成功加入，`current_member_count` 100% 不超過人數上限。
- **SC-003**: 已解散、已滿、或連結已失效的團，透過 QR Code/加入連結進入時，100% 顯示對應的明確錯誤訊息，0% 導向空白頁或一般錯誤頁。
- **SC-004**: Guest 使用者在同一團內重新整理頁面或短暫斷線重連，100% 被正確識別為同一人並還原原本狀態，不產生重複的 Player 記錄。
- **SC-005**: 通關密碼保護的團，使用者可不受次數限制重試直到輸入正確，0% 因連續輸入錯誤而被鎖定或要求額外的人機驗證。
- **SC-006**: 色盲使用者（或以灰階模式檢視）可透過非顏色的視覺線索（圖示形狀、文字標籤）100% 正確分辨開團列表中哪些團需要通關密碼。

## Assumptions

- 開團列表分頁機制的每頁筆數等技術細節留待 `/speckit-plan` 決定，不影響本規格定義的可觀察行為。
- 場地名稱與場地 ID 為兩個各自獨立的搜尋/篩選欄位（名稱可能為部分文字比對、ID 為精確比對），具體比對邏輯留待 `/speckit-plan` 決定。
- 活動時間區間篩選採「時間區間有重疊」的判斷邏輯（篩選條件的起訖時間與團設定的起訖時間有任何交集即視為符合），具體實作留待 `/speckit-plan` 決定。
- 通關密碼驗證失敗訊息、Guest 暱稱格式驗證等使用者可見文字，遵循「開團與管理」規格已建立的 i18n 架構慣例（語系檔 key／錯誤代碼），本規格不重複定義該架構本身。
- 已登入會員的「已加入的團」個人化列表資訊，其判斷依據為該會員帳號名下所有仍為 active 狀態的 Player 記錄所屬的團；此清單的呈現方式（是否分頁、排序方式）留待 `/speckit-plan` 決定。
- 加入連結 Token 採用與「場地管理」規格一致的 UUID v4 格式，比照本專案其他連結類型的既有慣例。
