# Feature Specification: 會員與好友系統（Member & Friend System）

**Feature Branch**: `[006-member-friends]`

**Created**: 2026-08-31

**Status**: Draft

**Input**: User description: "建立「會員與好友系統」功能：

使用者故事：作為長期使用者，我可以註冊會員帳號（Email + 密碼），註冊後需先完成 Email 信箱驗證（點擊驗證信中的連結）才能使用任何功能；完成驗證並設定暱稱後，登入即可查看自己的對戰紀錄、在「個人設定」頁編輯暱稱與修改密碼，並可搜尋、新增好友，處理好友邀請的接受/拒絕。

功能需求（節錄，已定案項目）：
- 註冊表單整合 Cloudflare Turnstile（僅註冊端點，登入/忘記密碼/修改密碼不納入）；Email 需系統內唯一（不分帳號是否已驗證），已被註冊時提示改走忘記密碼；不設計自動清除未驗證帳號的機制，忘記密碼流程本身即可解決此問題；Email 一律正規化為全小寫比對與儲存。
- Email 驗證機制：註冊後帳號為未驗證狀態並寄出驗證信；未驗證帳號可登入但僅能看到「請驗證你的信箱」提示與重新發送驗證信選項，任何其他功能一律鎖定；驗證連結有效期限（例如 24 小時）、UUID v4 隨機 Token；重新發送驗證信需登入後才可觸發，同帳號短時間內（例如 1 分鐘）僅能觸發一次。
- 忘記密碼流程不受驗證狀態影響，重設成功同時將帳號標記為已驗證（不需再點原驗證信）；忘記密碼與修改密碼皆會使其他裝置登入 session 失效，但忘記密碼會使「所有」裝置（含當前操作裝置）失效，修改密碼則保留當前操作裝置。
- 正確流程順序：註冊 →（未驗證，僅能看到驗證提示）→ 完成 Email 驗證 → 設定暱稱（僅未曾設定過的帳號需要）→ 正常使用。
- 使用者編號：註冊時自動產生、系統內唯一、一經產生不可更改；格式為 8 碼隨機英數字（排除易混淆字元），不可為連續遞增數字或 UUID 這類長字串；產生碰撞時重新產生直到唯一；於會員資訊頁與個人設定頁明顯可見並可一鍵複製；搜尋 API 需搭配速率限制。
- 個人設定頁：編輯暱稱（立即更新 Member 暱稱欄位，套用於尚未加入的新團；但目前進行中且已加入的團之 Player 記錄維持加入當下的暱稱快照，不回溯更新）；修改密碼（需驗證目前密碼，兩次新密碼需一致，成功後使其他裝置 session 失效但保留當前裝置）；帳號刪除功能本次不納入實作範圍。
- 忘記管理 PIN 碼（僅限已登入會員身份建立的團）：會員頁面列出該會員建立過的所有團，提供忘記 PIN 碼入口；僅需驗證登入狀態，不需重新輸入原 PIN 碼或會員密碼；重設成功同時核發新管理 Token 並直接導向管理頁，不要求重新輸入新 PIN 碼；舊 PIN 碼立即失效；此功能不適用於匿名建立的團，匿名建團的成功畫面需額外提醒務必記下編號與 PIN 碼。
- 好友列表：分頁顯示、可依暱稱或使用者編號篩選、可透過搜尋使用者編號新增好友；未驗證帳號不會出現在搜尋結果中；不可對自己發送邀請；搜尋結果的邀請按鈕依關係狀態顯示「待回覆」「待處理」「已是好友」等狀態標籤（一律用標籤取代按鈕，不整塊隱藏）。
- 好友邀請通知為非即時（不透過 Ably 或任何即時推播），無未讀 badge；拒絕後可重新發送邀請（建立新記錄，舊拒絕記錄保留）。
- 解除好友：二次確認、單方面動作不需對方同意、雙方列表即時同步、不主動通知對方、解除後可無限制重新加好友。

（完整驗收情境已於下方各使用者故事的 Given/When/Then 場景中完整轉譯，此處保留原始輸入之決策摘要。）"

## Clarifications

### Session 2026-08-31

- Q: 搜尋/比對使用者編號時應採大小寫敏感比對，還是大小寫不敏感比對？ → A: 大小寫不敏感比對（維持原始格式儲存與顯示）
- Q: 「忘記管理 PIN 碼」是否也應觸發與「主動重設管理 PIN 碼」相同的即時廣播通知機制？ → A: 是，沿用完全相同的廣播機制
- Q: 「忘記管理 PIN 碼」功能是否也適用於已解散的團（讓會員取回唯讀查閱權）？ → A: 適用，包含已解散的團
- Q: 「忘記密碼」觸發端點是否需要速率限制？ → A: 需要，依 IP 或目標 Email 做基本速率限制

### Session 2026-09-01

- Q: 「忘記密碼」送出 Email 後，若該 Email 查無對應帳號，回應是否需與查有帳號時不同？ → A: 一律回傳相同成功回應（不論帳號是否存在），避免帳號枚舉
- Q: 登入端點（FR-002 已排除 Turnstile）是否需要任何防暴力破解機制？ → A: 需要依來源 IP 做基本速率限制（不做帳號鎖定，避免被惡意鎖定他人帳號）

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 會員註冊與 Email 驗證 (Priority: P1)

使用者填寫 Email、密碼完成註冊，帳號初始為未驗證狀態並收到驗證信；未驗證期間登入僅能看到驗證提示，完成驗證後（若尚未設定過暱稱）才會被導向設定暱稱，之後即可正常使用完整功能。

**Why this priority**: 這是整個「會員與好友系統」的入口——沒有可用的會員帳號，就沒有後續的個人設定、好友系統、忘記管理 PIN 碼等任何功能，是本功能的最小可行閉環。

**Independent Test**: 可完整走過「填寫註冊表單 → 收到驗證信 → 點擊驗證連結 → 設定暱稱 → 正常使用」的流程獨立驗證，亦可測試 Email 重複註冊、Turnstile 驗證失敗、驗證連結逾期等分支，無需依賴好友系統或忘記管理 PIN 碼等其他功能。

**Acceptance Scenarios**:

1. **Given** 使用者填寫合法 Email 與相符的兩次密碼，**When** 送出註冊表單，**Then** 成功建立帳號（狀態為未驗證）並導向「請驗證你的信箱」畫面（不會直接導向設定暱稱頁），且系統已為該帳號產生一組唯一的使用者編號。
2. **Given** 使用者填寫合法的註冊表單內容但 Turnstile 驗證尚未完成（或驗證失敗），**When** 使用者送出表單，**Then** 系統拒絕建立帳號並提示「驗證失敗，請重新嘗試」，不可略過此驗證直接建立帳號。
3. **Given** 某 Email 已被其他會員帳號註冊過，**When** 使用者用同一組 Email 再次送出註冊表單，**Then** 系統提示「此 Email 已被註冊」，不可建立第二個帳號。
4. **Given** 某 Email 對應的帳號從未完成驗證（例如當初是被他人誤植信箱建立），**When** 該信箱真正的主人之後用同一組 Email 嘗試註冊，**Then** 系統同樣拒絕建立第二個帳號並提示可透過忘記密碼取回；**When** 該使用者接著使用忘記密碼流程成功設定新密碼，**Then** 可正常登入並取得該帳號完整控制權，帳號同時被標記為已驗證。
5. **Given** 使用者剛完成註冊，帳號狀態為未驗證，**Then** 系統寄出含驗證連結的 Email 到該信箱。
6. **Given** 使用者以未驗證帳號登入，**Then** 畫面僅顯示「請驗證你的信箱」提示與「重新發送驗證信」選項，無法使用開團、加入團、好友系統、對戰紀錄、個人設定等任何其他功能。
7. **Given** 使用者點擊驗證信中的連結完成驗證，且此為該帳號第一次通過驗證、尚未設定過暱稱，**Then** 系統接著導向「首次登入設定暱稱」流程，設定完成後才能正常使用完整功能。
8. **Given** 使用者收到的驗證連結已超過有效期限（例如 24 小時），**When** 使用者點擊該連結，**Then** 系統提示連結已失效，並引導使用者透過「重新發送驗證信」取得新的連結。
9. **Given** 已登入會員查看「會員資訊頁」或「個人設定頁」，**Then** 可看到自己的使用者編號並可一鍵複製；該編號為 8 碼隨機英數字組合，非連續遞增數字。

### User Story 2 - 登入與忘記密碼 (Priority: P1)

已註冊會員以 Email + 密碼登入；若忘記密碼，可透過 Email 收信重設，重設成功後所有裝置的登入狀態皆須以新密碼重新登入。

**Why this priority**: 登入是使用會員功能的基本前提，忘記密碼則是帳號救援的必要機制，兩者與註冊同屬最小可行閉環，優先序相同。

**Independent Test**: 可用一個已註冊帳號測試正常登入，並分別測試忘記密碼流程對多裝置 session 的影響，均可獨立驗證，無需依賴個人設定或好友系統。

**Acceptance Scenarios**:

1. **Given** 會員的帳號原本在手機與電腦兩個裝置皆處於登入狀態，**When** 該會員透過「忘記密碼」流程（Email 重設連結）完成密碼重設，**Then** 手機與電腦上原本的登入 session 皆隨即失效（不同於修改密碼會保留執行操作裝置的登入狀態），所有裝置皆需以新密碼重新登入。
2. **Given** 某帳號原本狀態為未驗證，**When** 使用者透過「忘記密碼」流程成功重設密碼，**Then** 該帳號同時被標記為已驗證，不需要使用者再另外點擊註冊時收到的那封獨立驗證信；若此帳號尚未設定過暱稱，重設密碼成功後應接續導向「首次登入設定暱稱」流程。
3. **Given** 某使用者（不論是否登入）短時間內對同一目標 Email 或來自同一 IP 對「忘記密碼」端點發出大量觸發請求，**Then** 系統依速率限制阻擋超過門檻的請求，不會讓該 Email 信箱被重複寄送的重設密碼信轟炸騷擾。

### User Story 3 - 個人設定：編輯暱稱與修改密碼 (Priority: P1)

已登入會員可在個人設定頁修改顯示暱稱（套用於未來新加入的團，不回溯影響進行中且已加入的團）與修改密碼（需驗證目前密碼，成功後使其他裝置登入狀態失效）。

**Why this priority**: 這是會員帳號日常最常使用的自我管理功能，且暱稱快照規則、密碼變更的 session 失效規則直接影響資料正確性與帳號安全，與登入/註冊同屬核心閉環。

**Independent Test**: 可用一個已驗證會員帳號，分別測試暱稱修改對「已加入進行中的團」與「尚未加入的新團」的不同影響，以及修改密碼對多裝置 session 的影響，均可獨立驗證。

**Acceptance Scenarios**:

1. **Given** 會員在個人設定頁修改暱稱並儲存，**Then** 會員資訊頁與後續加入新團時皆顯示新暱稱，但過去已完成比賽的對戰紀錄仍顯示當時加入時使用的舊暱稱。
2. **Given** 會員目前仍在某個尚未解散、進行中的團裡（該團的 Player 記錄是在修改暱稱之前建立的），**When** 該會員在個人設定頁修改暱稱並儲存，**Then** 該團的計分板、賽程頁、輪替名單等畫面仍顯示加入當下的舊暱稱，不會即時同步更新為新暱稱；僅有該會員之後新加入的團才會顯示新暱稱。
3. **Given** 會員在個人設定頁將暱稱修改為空白、或超過 20 個字元的內容，**Then** 系統提示格式錯誤，不可儲存。
4. **Given** 會員在個人設定頁修改密碼，**When** 輸入的「目前密碼」錯誤，**Then** 系統拒絕更新並顯示錯誤訊息；**When** 「新密碼」與「確認新密碼」不一致，**Then** 系統提示不可送出。
5. **Given** 會員同時在手機與電腦兩個裝置皆處於登入狀態，**When** 在電腦上成功修改密碼，**Then** 手機上原本的登入 session 隨即失效，手機需重新以新密碼登入才能繼續使用會員功能；電腦（執行修改的裝置）維持登入狀態。

### User Story 4 - 忘記管理 PIN 碼（會員限定復原機制） (Priority: P2)

已登入會員可在會員頁面看到自己過去建立過的所有團，並針對任一團一鍵重設管理 PIN 碼、無縫進入管理頁，不需重新輸入原 PIN 碼或會員密碼；此功能僅適用於會員身分建立的團，匿名建立的團無法使用。

**Why this priority**: 這是會員帳號相對匿名建團的重要加值——避免會員弄丟自己團的管理憑證就永久失去管理權，但即使沒有此功能，會員仍可用組團編號+PIN 碼手動重新驗證進入管理頁，因此優先序次於帳號本身的核心功能。

**Independent Test**: 可用一個會員帳號建立的團，觸發「忘記管理 PIN 碼」，獨立驗證重設流程、新 Token 核發、舊 PIN 碼失效；亦可用匿名建立的團驗證此功能確實不可用，均可獨立驗證。

**Acceptance Scenarios**:

1. **Given** 已登入會員曾以自己的帳號建立過某團，**When** 該會員在「會員頁面」對該團點擊「忘記管理 PIN 碼」並確認，**Then** 系統不要求輸入原 PIN 碼、也不要求重新輸入會員密碼，直接產生並顯示一組全新的管理 PIN 碼，原本的 PIN 碼立即失效、不可再用於進入管理頁。
2. **Given** 會員完成「忘記管理 PIN 碼」重設，**Then** 系統直接為該會員核發新的管理 Token 並導向管理頁，不要求會員再手動輸入一次剛顯示給他的新 PIN 碼重新驗證。
3. **Given** 某團為匿名（未登入）身份建立，**Then** 該團不會出現在任何會員的「會員頁面」團記錄列表中，也不提供任何「忘記管理 PIN 碼」的復原入口；若組團編號與 PIN 碼同時遺失，管理權限無法復原。
4. **Given** 另一位管理員正開著該團的管理頁、尚未觸發任何寫入操作，**When** 該會員完成「忘記管理 PIN 碼」重設，**Then** 該另一位管理員的畫面應在約 1 秒內透過即時事件廣播（`link_type: admin`）偵測到自己的管理 Token 已失效並顯示對應提示，行為與既有的「主動重設管理 PIN 碼」完全一致，不需要等到自己下一次嘗試寫入操作才發現。
5. **Given** 該會員以自己的帳號建立過的某個團目前已經解散，且已遺失該團的管理 PIN 碼，**When** 該會員在會員頁面對該團點擊「忘記管理 PIN 碼」並確認，**Then** 系統同樣重設一組全新的管理 PIN 碼並核發新的管理 Token，導向該團的唯讀管理頁供查閱歷史，不因該團已解散而拒絕此次重設請求。
4. **Given** 使用者以匿名身份成功建立團，**When** 查看建立成功後顯示組團編號與管理 PIN 碼的畫面，**Then** 畫面明確提醒「請務必截圖或記下這組編號與 PIN 碼，若同時遺失且未以會員身份建團，將無法復原管理權限」；若為已登入會員身份建立，則不顯示此提醒文字。

### User Story 5 - 搜尋與新增好友 (Priority: P2)

會員可透過使用者編號搜尋其他會員並發送好友邀請；搜尋結果依雙方目前的關係狀態顯示對應的按鈕或狀態標籤，避免重複發送邀請或對自己發送邀請。

**Why this priority**: 這是好友系統的入口功能，建立在會員帳號與使用者編號機制之上；沒有搜尋加好友的能力，好友系統的後續功能（回覆邀請、解除好友）就無從發生，優先序次於帳號核心功能。

**Independent Test**: 可用兩個已驗證會員帳號，互相搜尋對方的使用者編號並測試各種關係狀態（尚未有關係、已發送待處理、已是好友、搜尋自己、搜尋未驗證帳號）下按鈕/標籤的正確呈現，均可獨立驗證。

**Acceptance Scenarios**:

1. **Given** 使用者搜尋自己的使用者編號，**Then** 系統不提供「發送邀請」操作，或點擊後明確提示「不可加自己為好友」。
2. **Given** A 已發送一筆待處理邀請給 B，**When** A 再次搜尋 B 的使用者編號，**Then** 搜尋結果的邀請按鈕顯示「待回覆」而非可再次點擊的「發送邀請」，不會建立第二筆待處理邀請；**When** B 搜尋 A 的使用者編號，**Then** 按鈕顯示「待處理」並導向「回覆好友申請」頁。
3. **Given** A 與 B 已經是好友，**When** A 搜尋 B 的使用者編號，**Then** 搜尋結果顯示「已是好友」狀態標籤（不可點擊），不提供可再次發送邀請的按鈕。
4. **Given** 某使用者編號對應到一個尚未完成 Email 驗證的帳號，**When** 已驗證的會員搜尋該編號，**Then** 系統顯示查無此使用者編號，不可對其發送好友邀請。
5. **Given** 某使用者短時間內對「搜尋使用者編號」功能發出大量查詢請求（例如嘗試枚舉掃描），**Then** 系統依速率限制阻擋超過門檻的查詢，不會讓對方能有效率地掃描出系統內所有會員編號。
6. **Given** 某會員的使用者編號為「aB3dEfGh」，**When** 另一位使用者輸入「Ab3DefGh」（大小寫不同但字元相同）進行搜尋，**Then** 系統仍正確找到該會員，不因大小寫輸入差異判定為查無此使用者編號；搜尋結果與該會員個人頁面顯示的使用者編號 MUST 仍為原始產生時的大小寫格式「aB3dEfGh」。

### User Story 6 - 回覆好友邀請與解除好友 (Priority: P2)

會員可在好友列表依暱稱或使用者編號篩選、可在「回覆好友申請」頁接受或拒絕收到的邀請、也可隨時解除既有的好友關係（單方面動作，不需對方同意）。

**Why this priority**: 這是好友關係生命週期的後半段（接受、拒絕、解除），建立在搜尋加好友（US5）已存在的基礎之上，優先序相同（P2），但邏輯上依賴前者先產生邀請記錄。

**Independent Test**: 可用兩個已建立待處理邀請或既有好友關係的會員帳號，分別測試接受、拒絕、拒絕後重新發送、解除好友、解除後重新發送、好友列表篩選等情境，均可獨立驗證。

**Acceptance Scenarios**:

1. **Given** 會員的好友列表中有多位好友，**When** 使用者在好友列表輸入部分暱稱或部分使用者編號進行篩選，**Then** 列表僅顯示暱稱或使用者編號包含該關鍵字的好友，其餘好友暫時不顯示。
2. **Given** 收到好友邀請的使用者按下「接受」，**Then** 雙方互為好友並出現在彼此的好友列表中；按下「拒絕」則邀請關閉，不建立好友關係。
3. **Given** A 發送邀請給 B、B 選擇「拒絕」，**When** A 之後再次搜尋 B 並發送新的邀請，**Then** 可正常送出，建立一筆新的待處理邀請記錄，先前「拒絕」的記錄仍保留、不受影響。
4. **Given** A 與 B 為好友，**When** A 點擊「解除好友」並在確認彈窗按下確認，**Then** 該筆好友記錄轉為「已解除」狀態，A、B 雙方的好友列表皆立即不再顯示對方，且系統不會對 B 發出任何通知。
5. **Given** A 已解除與 B 的好友關係，**When** A 之後透過「搜尋使用者編號」搜尋 B 並重新發送好友邀請，**Then** 可正常送出邀請，不因先前已解除過好友關係而受到任何限制。
6. **Given** A 點擊「解除好友」但在確認彈窗中按下取消，**Then** 好友關係維持不變，雙方好友列表皆不受影響。

### Edge Cases

- 使用者編號產生時剛好與現有編號重複（機率極低）？（見 FR-019：視為產生失敗，重新產生一次直到取得未使用的編號為止，不需額外告警或人工介入。）
- 未驗證帳號嘗試觸發「搜尋使用者編號」或「好友邀請」等其他功能？（依 FR-009，未驗證帳號登入後任何其他功能一律鎖定，僅能看到驗證提示，不會進入好友系統相關頁面。）
- 使用者同時在多個分頁觸發「重新發送驗證信」？（依 FR-011 之速率限制，短時間內第二次觸發會被拒絕並提示需稍後再試。）
- 忘記密碼流程中途，原帳號因故已被標記為已驗證（例如已透過驗證信驗證過）？（重設密碼成功時再次標記為已驗證為冪等操作，不產生錯誤或副作用。）
- 會員在「忘記管理 PIN 碼」功能重設 PIN 碼的同時，另一位管理員正在使用該團的舊 PIN 碼進行一般的重新驗證？（比照「開團與管理」規格既有的管理憑證版本衝突處理原則，重設後舊 PIN 碼立即失效，任何仍在使用舊憑證的操作將被判定為版本不符而拒絕。）

## Requirements *(mandatory)*

### Functional Requirements

**防機器人驗證（僅限註冊端點）**

- **FR-001**: 會員註冊表單 MUST 整合 Cloudflare Turnstile（Free 方案）小工具；使用者送出註冊表單時 MUST 一併夾帶 Turnstile 驗證 token，後端在建立會員帳號之前 MUST 先確認該 token 有效，驗證失敗 MUST 拒絕本次註冊請求並提示「驗證失敗，請重新嘗試」，MUST NOT 略過此驗證直接建立帳號。
- **FR-002**: 登入、忘記密碼、修改密碼等其他會員相關端點 MUST NOT 納入此 Turnstile 驗證範圍。
- **FR-002a**: 登入端點 MUST 具備基本防暴力破解機制，依來源 IP 做速率限制（短時間內同一來源 IP 的登入嘗試次數超過門檻 MUST 被拒絕）；此機制 MUST NOT 採帳號鎖定方式（不可因連續輸入錯誤密碼而鎖定特定帳號本身），以避免惡意人士刻意用他人已知 Email 反覆輸入錯誤密碼、藉此鎖定該帳號本人無法登入。此規則與管理 PIN 碼之帳號鎖定機制（見「開團與管理」規格）為不同的兩套防護策略，適用情境不同（管理 PIN 碼鎖定的是單一團的管理權限，登入鎖定的則是會員個人帳號，後者被惡意鎖定的代價遠高於前者）。

**會員註冊與 Email 唯一性**

- **FR-003**: 會員註冊表單 MUST 收集 Email、密碼、確認密碼；MUST 驗證 Email 格式合法、兩次密碼輸入一致，不符合時 MUST 提示錯誤且不可送出。
- **FR-004**: Email MUST 於系統內唯一；若輸入的 Email 已被其他會員帳號註冊過（不分該帳號是否已完成驗證），系統 MUST 提示「此 Email 已被註冊，若這是你的信箱，可透過忘記密碼取回帳號控制權」，MUST NOT 建立第二個帳號。
- **FR-005**: 系統 MUST NOT 設計任何自動清除未驗證帳號或釋放其佔用 Email 的排程機制；真正的信箱主人 MUST 可透過「忘記密碼」流程（見 FR-013）取回帳號完整控制權。
- **FR-006**: 會員註冊、登入、Email 唯一性檢查時，Email MUST 先正規化為全小寫再進行比對與儲存（僅做大小寫正規化，MUST NOT 做特定信箱服務商的進階正規化，如 `.`／`+alias` 忽略規則）；顯示與後續所有使用情境（登入、忘記密碼、驗證信寄送地址）MUST 皆以正規化後的小寫版本為準。

**Email 驗證機制**

- **FR-007**: 會員註冊成功後，帳號初始狀態 MUST 為「未驗證（unverified）」，系統 MUST 同時寄出一封含驗證連結的 Email 到使用者填寫的信箱。
- **FR-008**: 使用者點擊驗證連結後，帳號狀態 MUST 轉為「已驗證（verified）」。
- **FR-009**: 未驗證的會員 MUST 仍可用 Email + 密碼正常登入，但登入後 MUST 僅顯示「請驗證你的信箱」提示與「重新發送驗證信」選項；MUST NOT 可使用任何其他功能，包含但不限於開團、以會員身分加入團、好友系統、查看對戰紀錄、修改個人設定。
- **FR-010**: 驗證連結 MUST 具備合理的有效期限（例如 24 小時），MUST 使用不可猜測的隨機 Token（UUID v4）；逾期後使用者 MUST 可透過「重新發送驗證信」取得新的連結，逾期連結被點擊時 MUST 提示連結已失效。
- **FR-011**: 「重新發送驗證信」為登入後才可觸發的功能，同一帳號在短時間內（例如 1 分鐘內）MUST 僅能觸發一次重新發送，超過限制 MUST 拒絕並提示稍後再試。

**正確流程順序**

- **FR-012**: 註冊完成後，使用者登入時 MUST 先看到「請驗證你的信箱」畫面（未驗證狀態下 MUST NOT 顯示設定暱稱畫面）；完成 Email 驗證後，若該帳號尚未設定過暱稱，系統 MUST 接著導向「首次登入設定暱稱」流程；設定完成後即可正常使用完整功能。

**登入與忘記密碼**

- **FR-013**: 系統 MUST 提供「忘記密碼」流程：使用者輸入 Email 後系統寄出重設密碼信，使用者點擊信中連結後可設定新密碼；此流程 MUST NOT 受帳號驗證狀態影響（即使帳號尚未驗證，仍可透過此流程重設密碼）。若輸入的 Email 查無對應帳號，系統 MUST 回傳與查有帳號時完全相同的成功回應（僅靜默不寄信），MUST NOT 揭露該 Email 是否已註冊，以避免帳號枚舉風險。
- **FR-013a**: 「忘記密碼」觸發端點（輸入 Email 送出重設信的步驟）MUST NOT 需要登入即可觸發，MUST 搭配基本速率限制（依來源 IP 或目標 Email 限制短時間內的觸發次數），避免任何人對任意已知 Email 重複觸發造成該信箱被大量重設密碼信轟炸的騷擾風險；此速率限制之必要性與「重新發送驗證信」（FR-011，已受登入閘門保護、風險來源不同）互為對照，MUST NOT 因兩者皆屬「Email 驗證/密碼相關寄信」而誤用同一套防護假設。
- **FR-014**: 忘記密碼流程重設密碼成功的同時，系統 MUST 一併將該帳號狀態標記為已驗證（不需使用者額外點擊原本的驗證信）；若該帳號尚未設定過暱稱，重設成功後 MUST 接續導向「首次登入設定暱稱」流程。
- **FR-015**: 忘記密碼重設密碼成功後，系統 MUST 使該會員在所有裝置/瀏覽器上既有的登入 session 全部失效（含當前執行重設操作的裝置），所有裝置皆 MUST 需以新密碼重新登入。

**使用者編號**

- **FR-016**: 每個會員帳號於註冊成功時，系統 MUST 自動產生一組唯一的「使用者編號」；此編號 MUST 於會員資訊頁與個人設定頁明顯可見，並 MUST 提供一鍵複製。
- **FR-017**: 使用者編號一經產生 MUST NOT 可更改。
- **FR-018**: 使用者編號格式 MUST NOT 使用連續遞增的數字，MUST NOT 直接使用 UUID v4 這類長字串；MUST 採用較短的隨機英數字組合（例如 8 碼，混合大小寫字母與數字，並排除容易混淆的字元如 0/O、1/I/l）。
- **FR-019**: 資料庫層級 MUST 對使用者編號欄位建立唯一性約束；產生新編號時若與現有編號重複，MUST 視為產生失敗並重新產生，直到取得未使用的編號為止，不需額外的告警或人工介入機制。
- **FR-019a**: 使用者編號的搜尋、比對與唯一性檢查（含 FR-019 之碰撞檢查、FR-035 之好友搜尋）MUST 採大小寫不敏感比對，MUST NOT 因使用者輸入的大小寫與原始產生時不同而判定為查無此編號、或誤判兩組僅大小寫不同的編號為互不相同；使用者編號本身 MUST 仍以產生當下的原始大小寫格式儲存與顯示。
- **FR-020**: 「搜尋使用者編號」API MUST 搭配基本速率限制，限制同一來源（IP 或帳號）在短時間內的查詢次數。

**會員資訊頁**

- **FR-021**: 會員資訊頁 MUST 提供：登出、對戰紀錄、好友、個人設定入口、本人使用者編號顯示。

**個人設定頁 - 編輯暱稱**

- **FR-022**: 會員 MUST 可在個人設定頁修改自己的顯示暱稱；暱稱 MUST 為必填，去除前後空白後不可為空字串，長度不可超過 20 字，不符合時 MUST 提示錯誤且不可儲存。
- **FR-023**: 暱稱儲存後 MUST 立即更新 `Member` 實體的暱稱欄位本身，並自此刻起套用於尚未加入的新團。
- **FR-024**: 目前仍在進行中、尚未解散、且該會員已加入的團，其對應 Player 記錄顯示的暱稱 MUST 維持「加入當下」的暱稱快照，MUST NOT 因會員之後修改暱稱而回溯同步更新；Player 記錄 MUST 於建立當下複製一份會員當時的暱稱存入自身欄位，MUST NOT 以即時查詢 Member 表當下暱稱值的方式呈現（Player 實體本身 MUST 具備暱稱欄位，登入會員與 Guest 皆使用同一套欄位，僅資料來源不同）。

**個人設定頁 - 修改密碼**

- **FR-025**: 會員修改密碼 MUST 先輸入目前密碼進行驗證，再輸入新密碼與確認新密碼；目前密碼錯誤時 MUST 拒絕更新並顯示錯誤訊息；新密碼與確認新密碼不一致時 MUST 提示不可送出。
- **FR-026**: 修改密碼成功後，系統 MUST 使該會員在其他裝置/瀏覽器上既有的登入 session 全部失效，MUST 保留本次執行修改密碼的這個裝置的登入狀態。

**帳號刪除（明確排除範圍）**

- **FR-027**: 本規格 MUST NOT 於個人設定頁提供帳號刪除功能；此功能留待後續規劃完整規格後再行補上。

**忘記管理 PIN 碼（僅限會員身分建立的團）**

- **FR-028**: 已登入會員的會員頁面 MUST 列出該會員過去以登入身份建立過的所有團（含組團編號），不論該團目前是否已解散，每筆記錄旁 MUST 提供「忘記管理 PIN 碼」入口；已解散的團 MUST NOT 因解散狀態而被排除於此列表或此功能之外——依「開團與管理」規格既有規則，已解散團的組團編號與管理 PIN 碼仍可用於進入唯讀管理頁查閱歷史，會員 MUST 仍可透過此功能取回該唯讀查閱權，MUST NOT 因遺失 PIN 碼而永久喪失查閱自己已解散團歷史紀錄的能力。
- **FR-029**: 匿名（未登入）身份建立的團 MUST NOT 出現在此團記錄列表中，MUST NOT 提供「忘記管理 PIN 碼」入口；此排除規則 MUST NOT 受該團是否已解散影響（不論進行中或已解散，匿名建立的團一律不適用此功能）。
- **FR-030**: 觸發「忘記管理 PIN 碼」時，系統 MUST 僅驗證該會員目前的登入狀態，MUST NOT 要求重新輸入原本的管理 PIN 碼，MUST NOT 要求重新輸入會員密碼進行 step-up 驗證。
- **FR-031**: 驗證通過後，系統 MUST 直接為該團重設一組全新的 6 碼管理 PIN 碼並完整顯示給該會員（供其記錄），原本的管理 PIN 碼 MUST 立即失效。
- **FR-032**: 重設成功的同時，系統 MUST 直接為該會員核發一組新的管理 Token（效力與權限範圍與一般「組團編號＋管理 PIN 碼」驗證通過後核發的管理 Token 相同），前端 MUST 憑此 Token 直接導向該團的管理頁，MUST NOT 要求會員再手動輸入一次剛顯示的新 PIN 碼重新驗證。
- **FR-032a**: 「忘記管理 PIN 碼」在功能效果上與「開團與管理」規格已定案的「主動重設管理 PIN 碼」完全相同（皆使舊 PIN 碼與舊管理 Token 失效、核發新 Token），MUST 沿用完全相同的即時事件廣播通知機制（`link_type: admin`，廣播至團層級通知頻道，見「場地管理」規格）——任何正開著該團管理頁、尚未觸發寫入操作因而還沒被既有管理憑證版本檢查擋下的其他管理員，MUST 同樣能提早收到通知，MUST NOT 因為此次重設是透過「忘記管理 PIN 碼」（登入驗證）而非原本的 PIN 碼二次確認觸發，就採用不同或缺漏的通知路徑。
- **FR-033**: 開團表單提交成功、顯示組團編號與管理 PIN 碼的畫面，若為匿名（未登入）建立的團，MUST 額外顯示明確提醒文字（例如「請務必截圖或記下這組編號與 PIN 碼；若同時遺失且未以會員身份建團，將無法復原管理權限」）；若為已登入會員身份建立，MUST NOT 顯示此額外提醒。

**好友列表與搜尋**

- **FR-034**: 好友列表 MUST 分頁顯示好友，MUST 提供依暱稱或使用者編號篩選功能（輸入關鍵字比對好友列表中符合的暱稱或使用者編號子字串）。
- **FR-035**: 會員 MUST 可透過「搜尋使用者編號」查找其他會員並發送好友邀請。
- **FR-036**: 若搜尋到的使用者編號對應到一個尚未完成 Email 驗證的帳號，系統 MUST 視為「查無此使用者編號」，MUST NOT 顯示該帳號資訊，MUST NOT 可對其發送好友邀請。
- **FR-037**: 若搜尋到的使用者編號對應到自己，系統 MUST 拒絕顯示「發送邀請」操作，MUST NOT 建立此類 `FriendRequest` 記錄。
- **FR-038**: 搜尋結果的邀請操作區塊 MUST 依雙方目前的關係狀態，統一以「按鈕 → 依關係狀態顯示對應標籤」的方式呈現（MUST NOT 因狀態不同而改用整塊隱藏等不一致的呈現方式）：(a) 若自己已發送、對方尚未回覆的待處理邀請存在，MUST 顯示「待回覆」（不可再次點擊發送）；(b) 若對方已發送、自己尚未處理的待處理邀請存在，MUST 顯示「待處理」（點擊導向「回覆好友申請」頁）；(c) 若雙方已是好友，MUST 顯示「已是好友」（不可點擊）。
- **FR-039**: 同一組使用者之間任何時刻 MUST 最多只有一筆狀態為「待處理」的 `FriendRequest` 記錄。

**好友邀請回覆**

- **FR-040**: 使用者收到好友邀請時，MUST 可在「回覆好友申請」頁選擇「接受」或「拒絕」；接受後雙方 MUST 互為好友並出現在彼此的好友列表中；拒絕後 MUST 關閉該邀請，MUST NOT 建立好友關係。
- **FR-041**: 好友邀請通知 MUST 為非即時呈現——MUST NOT 透過即時推播機制通知，MUST NOT 提供未讀數量 badge 或跳出提示；使用者 MUST 需自行進入「好友」頁面或「回覆好友申請」頁才能看到待處理的邀請清單。
- **FR-042**: 邀請被拒絕後，MUST NOT 阻擋雙方之後任一方重新發送邀請；重新發送時 MUST 建立一筆新的 `FriendRequest` 記錄，舊的「拒絕」記錄 MUST 予以保留、不覆寫或刪除。

**解除好友**

- **FR-043**: 好友列表中每位好友項目旁 MUST 提供「解除好友」操作入口，觸發前 MUST 提供二次確認彈窗。
- **FR-044**: 確認解除後，該筆 `FriendRequest` 記錄 MUST 立即轉為「已解除」狀態，雙方的好友列表 MUST 即時同步不再顯示對方。
- **FR-045**: 解除好友時，系統 MUST NOT 對被解除的一方發送任何通知。
- **FR-046**: 雙方解除好友關係後，MUST 仍可透過「搜尋使用者編號」流程重新發送好友邀請，MUST NOT 設任何冷卻時間或次數限制。

### Key Entities *(include if feature involves data)*

- **Member（會員帳號）**: 屬性含 Email（正規化小寫、系統內唯一）、密碼雜湊、暱稱、使用者編號（8 碼隨機英數、系統內唯一、不可變更）、驗證狀態（unverified/verified）。
- **EmailVerificationToken／PasswordResetToken（Email 驗證與密碼重設憑證，關聯實體）**: 隨機識別 Token（UUID v4）與有效期限，分別供信箱驗證連結與忘記密碼重設連結使用；驗證/重設完成或逾期後即失效。
- **Player（輪替名單項目，關聯實體，見「賽程與輪替名單」規格）**: 本規格為其新增暱稱快照需求——不論登入會員或 Guest，皆使用同一套暱稱欄位；登入會員的 Player 記錄於建立當下複製 Member 當時的暱稱值，MUST NOT 即時查詢 Member 表當下暱稱值。
- **FriendRequest（好友邀請／好友關係）**: 記錄兩位會員之間關係的單一資料列，狀態涵蓋「待處理」「已接受（好友）」「已拒絕」「已解除」；發起方與接收方欄位區分邀請方向；狀態轉換即代表待處理邀請、成立好友關係、拒絕、解除四個階段的呈現依據。
- **Group（團，關聯實體，見「開團與管理」規格）**: 本規格使用其管理 PIN 碼、管理憑證版本等既有欄位，「忘記管理 PIN 碼」功能對其執行與既有「主動重設管理 PIN 碼」相同效力的重設操作。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 註冊送出後，100% 的請求要嘛立即建立帳號（狀態未驗證）並觸發驗證信寄送，要嘛因 Turnstile 驗證失敗或 Email 重複被明確拒絕並說明原因，不會出現「送出後不知結果」的情況。
- **SC-002**: 未驗證帳號嘗試存取任何非「驗證提示」相關的功能頁面，100% 被導向「請驗證你的信箱」畫面，0% 可繞過此限制。
- **SC-003**: 修改密碼或忘記密碼重設後，受影響裝置的登入 session，100% 於該裝置下一次發出請求時被判定為失效並要求重新登入。
- **SC-004**: 使用者編號搜尋結果，100% 正確排除未驗證帳號與使用者自己本身；好友邀請按鈕狀態，100% 正確反映雙方目前關係（可發送／待回覆／待處理／已是好友）四者之一。
- **SC-005**: 「忘記管理 PIN 碼」功能，僅會員身分建立的團可使用；匿名建立的團，0% 可透過任何途徑取回已遺失的管理權限。
- **SC-006**: 解除好友後，雙方好友列表 100% 於下次查看時同步不再顯示對方，且 0% 收到任何形式的主動通知。

## Assumptions

- 驗證信、忘記密碼信、Email 寄送等外部服務（SMTP／寄信商）整合細節留待 `/speckit-plan` 決定，本規格僅定義觸發時機與內容需求（需含可點擊的有效連結）。
- 密碼複雜度規則（最短長度、字元種類要求）留待 `/speckit-plan` 決定，採業界常見的最低安全標準；本規格僅要求「輸入格式驗證存在」（例如兩次輸入需一致），不預先限定具體規則細節。
- `FriendRequest` 以單一資料列承載「待處理邀請」與「好友關係」兩種語意（狀態機：pending → accepted／rejected；accepted → unfriended），避免額外維護分離的好友關係表與資料同步問題；實際欄位與索引設計留待 `/speckit-plan` 決定。
- Cloudflare Turnstile 的技術整合細節（API 呼叫方式、金鑰管理）留待 `/speckit-plan` 決定，本規格僅定義業務層面的驗證時機與失敗行為。
- 好友邀請與好友列表在使用者主動查看當下才反映最新狀態（非即時），符合 FR-041 之設計決定，不需額外的輪詢或心跳機制；此與計分板/控制板等需要秒級即時同步的場景在急迫性上有本質差異，故不比照相同的即時性標準。
