# Quickstart: 管理頁分數控制板支援比賽詳細設定

驗證 [contracts/schedule-api-additions.md](./contracts/schedule-api-additions.md) 與管理頁畫面。決策見 [research.md](./research.md)，欄位與元件狀態見 [data-model.md](./data-model.md)。

## 前置準備

沿用既有本地開發環境。**這次沒有 migration**——沒有新資料表、沒有新欄位、沒有新端點、沒有新語系 key。

部署順序：**後端先、前端後**。新欄位是純新增且有預設值，舊版前端搭新版後端完全不受影響（看不到新欄位而已）；新版前端搭舊版後端時，`detailed_scoring_enabled` 讀到 `undefined` 會被當成關閉，管理頁退回現行的一鍵加分——**不會壞，只是功能尚未生效**。因此嚴格來說順序可互換，但先後端可讓功能一次到位。回滾：前端退版即可，後端的新欄位留著不影響任何既有行為。

自動化測試：

```bash
# 後端（於 apps/api）
python -m pytest tests/contract/test_detailed_scoring_toggle.py # 新增：排程快照的 current_match.detailed_scoring_enabled 反映比賽快照
python -m pytest tests/contract/test_admin_score_endpoints.py   # 既有：管理員加分回傳 score_event_id
python -m pytest tests/contract/test_shot_placement_endpoint.py # 既有：管理員路徑記錄落點
python -m pytest tests/contract/test_undo_match_completion_endpoint.py  # 既有：管理員路徑撤銷賽末點
ruff check app/ tests/ && mypy app/

# 前端（於 apps/web）
npm test -- --watch=false
npm run lint && npx tsc --noEmit -p tsconfig.app.json
```

> 從 `.claude/worktrees/` 執行：後端把主 checkout 的 `apps/api/.venv/bin` 放到 `PATH`（`conftest.py` 會 shell out 到 `alembic`，光用絕對路徑呼叫 python 不夠），前端 symlink 主 checkout 的 `node_modules`。**背景測試跑完之前不要結束回合**——worktree 會被清掉。

手動情境需要：一個已啟用「比賽詳細設定」的團、至少 1 面場地、4 位球員、一場進行中的比賽，以及開著的**開團管理頁面**（已通過管理 PIN 驗證）。對照組請另開同一場地的**公開控制頁面連結**。

## 情境 1：詳細設定開啟，管理頁加分即可記錄（US1，FR-001～FR-004、SC-001）

管理頁 →「場地控制」區塊，找到進行中的那一場。按左側的「+1」。

**預期**：
- 比分**立刻**加一，不等任何視窗（FR-002）。
- 同一次按壓就跳出詳細記錄視窗，不需要再按第二次（FR-003）。
- 視窗內容與公開控制頁面完全相同：球場圖可點落點、得分／失分球員、結束方式選項、發球失誤預選（FR-004）。
- 填完按「確認」→ 視窗關閉，可立即繼續計分。

**對照**：到比賽紀錄頁看這一分，應與從公開控制頁面記的分完全一樣，看不出來源差異（FR-014、SC-006）。

## 情境 2：詳細設定關閉時一切照舊（FR-001、FR-010、SC-004）

到管理頁的「比賽詳細設定」把開關**關掉**，然後**換輪或開新的一場**（既有比賽沿用建立當下的快照，不會改變）。在新的一場按「+1」。

**預期**：比分加一，**不跳任何視窗**，點擊次數與本功能實作前完全相同。按「-1」同樣不跳視窗（FR-010）。

## 情境 3：設定快照不回溯（憲章原則 III，FR-015）

在一場**詳細設定為開啟**的比賽進行到一半時，回到同一頁把團的開關關掉，再回場地控制按「+1」。

**預期**：這場比賽**仍然**跳出詳細視窗——它依的是建立當下的快照，不是團的當下設定。反向亦然：比賽建立時是關閉的，中途打開團開關，這場仍維持一鍵加分。

## 情境 4：略過與取消這一分（US2，FR-006～FR-009、SC-005）

**4a 略過**：按「+1」，視窗跳出後按「略過」。
**預期**：視窗關閉，那一分**保留**，該分不留任何詳細資料。

**4b 取消（比賽未結束）**：按錯邊的「+1」，視窗跳出後按「取消這一分」。
**預期**：那一分被收回，雙方比分回到按下前的數字，視窗關閉。

**4c 取消賽末點**：把比賽打到差一分，按下決勝的「+1」（比賽因此結束），在視窗中按「取消這一分」。
**預期**：比賽**回到進行中**，比分正確，不是停在已結束（FR-008）。

**4d 取消失敗**：同 4c，但在按「取消這一分」之前先在管理頁按「Next Round」讓賽程往前推進。
**預期**：場地控制板上出現可讀的失敗提示（`ROUND_ALREADY_ADVANCED` 的中文句子，而非錯誤代碼），比分與比賽狀態不會變成不一致（FR-009）。

## 情境 5：視窗不被即時更新抽掉（US3，FR-011、FR-012、SC-003）

重複 4c 的賽末點，但這次**不要**立刻動作——讓「比賽結束」的即時推播抵達（管理頁其他區塊會跟著重畫），停留在視窗裡數秒再完成記錄。

**預期**：
- 視窗**始終在畫面上**，內容不變，仍可確認／略過／取消（FR-011）。
- 視窗背後那塊控制板顯示的比分**已包含剛記的這一分**（FR-012）。
- 視窗關閉後，該場地區塊才更新到真正的賽後狀態（下一場／等待中／已結束），不會卡在凍結畫面。

**同時檢查其他場地**：在 A 場的視窗開著時，讓 B 場從公開連結計分。
**預期**：B 場的區塊**照常即時更新**——凍結只影響 A 場自己這一塊，不是整頁停更（research.md Decision 7）。

## 情境 6：防重複計分（FR-013）

在詳細設定開啟的比賽上**快速連按兩次**同一個「+1」。

**預期**：只加一分、只開一個視窗。簡易模式下連按兩次也只加一分（本功能順帶補上的 `ScoreTapGuard`，research.md Decision 5）。

## 情境 7：離線行為（FR-018）

切斷網路（或停掉 Ably 連線）直到管理頁出現離線提示。

**預期**：「+1」「-1」「提前結束」全部停用，與公開控制頁面同一套規則。恢復連線後，畫面以伺服器最新狀態為準。

## 情境 8：詳細資料記錄失敗不影響比分（Edge Case，FR-016）

按「+1」開啟視窗後，切斷網路再按「確認」。

**預期**：那一分**保留**（它早在按下時就已送出並套用），不會因為詳細記錄失敗而被回滾；比賽可繼續正常計分。

## 情境 9：加分未被接受時視窗自行關閉（Edge Case，FR-017）

讓「+1」被後端拒絕（例如在另一個視窗先把同一場比賽「提前結束」，再回管理頁按「+1」）。

**預期**：詳細視窗自動關閉，不會停在視窗裡要求替一個不存在的得分填資料。
