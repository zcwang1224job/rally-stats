# Feature Specification: 全站導覽規劃（行動裝置優先）

**Feature Branch**: `[009-site-navigation-shell]`

**Created**: 2026-09-02

**Status**: Draft

**Input**: User description: "規劃web 頁面各個功能應該有的導覽功能，設計上主要以平板及手機等裝置為主要考量"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 全站導覽殼層與登入狀態感知 (Priority: P1)

使用者瀏覽首頁、揪團列表、會員專區（含個人設定、跨團對戰紀錄）、登入/註冊/忘記密碼等頁面時，畫面上有一致的導覽方式：可隨時回首頁、可看到自己目前是訪客還是已登入會員、已登入時可直接看到登出入口。手機上導覽以精簡選單呈現，平板與桌面則展開為橫向導覽列。

**Why this priority**: 目前系統完全沒有全站導覽殼層——每個頁面幾乎只能靠直接輸入網址或既有流程跳轉的方式抵達，且沒有任何「登出」入口。這是使用體驗上影響最廣、最基礎的缺口，優先度最高。

**Independent Test**: 可獨立在手機與平板兩種螢幕寬度下，分別從首頁、揪團列表、會員專區任一頁面開啟導覽選單，驗證選單項目正確、登入狀態顯示正確、且能成功導向其他頁面，無需依賴其他使用者故事。

**Acceptance Scenarios**:

1. **Given** 訪客（未登入）在手機寬度瀏覽首頁，**When** 開啟導覽選單，**Then** 看到「登入」「註冊」等入口，不會看到任何已登入會員專屬的項目（例如登出、會員暱稱）。
2. **Given** 已登入會員在平板寬度瀏覽會員專區任一頁面，**When** 檢視導覽殼層，**Then** 看到自己的暱稱與登出入口，且導覽列以橫向展開方式呈現（非手機的精簡選單）。
3. **Given** 已登入會員點擊登出，**When** 登出動作完成，**Then** 本機登入狀態被清除，畫面導向首頁或登入頁，且再次檢視導覽殼層時顯示訪客狀態。

---

### User Story 2 - 首頁作為導覽樞紐 (Priority: P1)

使用者造訪首頁時，能直接看到並點擊進入系統的所有主要入口：瀏覽現有揪團列表、建立新的揪團場次、登入或註冊會員（訪客時），或直接前往會員專區（已登入時）——而不是像目前只看到兩個管理相關的連結。

**Why this priority**: 首頁是大多數使用者的第一個入口，目前首頁的連結完全沒有涵蓋「瀏覽揪團」「登入」這兩個核心動線，與 User Story 1 同屬最基礎的導覽缺口，優先度並列最高。

**Independent Test**: 可獨立開啟首頁，在手機與平板寬度下分別確認四類入口（瀏覽揪團、建立揪團、登入/註冊或會員專區）皆存在且可點擊抵達對應頁面，無需依賴其他使用者故事。

**Acceptance Scenarios**:

1. **Given** 訪客造訪首頁，**When** 檢視頁面內容，**Then** 看到「瀏覽揪團列表」「建立揪團場次」「登入」「註冊」四類入口。
2. **Given** 已登入會員造訪首頁，**When** 檢視頁面內容，**Then** 「登入」「註冊」入口改為「前往會員專區」入口，其餘入口不變。

---

### User Story 3 - 會員專區內部導覽 (Priority: P2)

已登入會員在會員首頁、個人設定頁、跨團對戰紀錄頁之間，能透過導覽殼層直接切換，不需要每次都先回到會員首頁再重新點擊；同時能在這幾頁的任何一頁直接完成登出，不需要先切換到特定頁面才能登出。

**Why this priority**: 建立在 User Story 1 已提供的殼層基礎上，是會員專區內部動線的細化，重要性次於「殼層本身存在」與「首頁入口完整」。

**Independent Test**: 可獨立以已登入會員身分，從會員首頁出發，驗證能直接切換到設定頁、對戰紀錄頁，並在任一頁完成登出，無需依賴 User Story 4。

**Acceptance Scenarios**:

1. **Given** 已登入會員在跨團對戰紀錄頁，**When** 使用導覽殼層，**Then** 可直接切換到個人設定頁，不需要先返回會員首頁。
2. **Given** 已登入會員在個人設定頁，**When** 點擊登出，**Then** 登出成功，行為與 User Story 1 情境 3 一致。

---

### User Story 4 - 團管理頁的返回路徑 (Priority: P2)

管理員在團管理頁操作時，能透過明確的導覽方式返回首頁，結束本次管理操作；但這個返回路徑不會讓其他人略過「組團編號 + 管理 PIN 碼」的驗證機制直接看到或操作這個團的管理頁。

**Why this priority**: 目前團管理頁沒有任何返回首頁的方式，使用者只能手動修改網址；此問題明確但影響範圍較 User Story 1、2 小（管理員操作頻率較低），優先度列第二梯次。

**Independent Test**: 可獨立進入一個團的管理頁，驗證有明確的「返回首頁」導覽項目，點擊後正確導向首頁且不影響該團的管理 PIN 驗證機制，無需依賴其他使用者故事。

**Acceptance Scenarios**:

1. **Given** 管理員在團管理頁，**When** 點擊「返回首頁」，**Then** 畫面導向首頁；**When** 之後想再次進入同一個團的管理頁，**Then** 仍須透過既有的組團編號 + 管理 PIN 碼重新驗證，不因先前造訪過而略過驗證。

---

### Edge Cases

- 計分板、單一/全部場地控制板、加入連結等透過 QR Code 或深連結開啟的頁面，是否也會被加上全站導覽殼層？（不會，這些頁面刻意維持精簡呈現，見 FR-010，避免佔用球場邊行動裝置的有限畫面空間、避免操作者不慎點擊導覽項目而中斷計分/控制流程。）
- 團內成員視圖（一般成員導覽：賽程/戰績/對戰紀錄/退出組團）是否會同時出現本次新增的全站殼層與既有的底部導覽列，造成兩層導覽？（不會，此頁面維持既有規格（008）已建立的獨立底部導覽列，不套用本規格的全站殼層，見 FR-009。）
- 已登入會員造訪首頁後，首頁的行動呼籲入口應如何呈現？（見 User Story 2 情境 2，「登入/註冊」改為「前往會員專區」。）
- 管理員從團管理頁返回首頁，是否等同於失去該團的管理權限？（是，這與既有安全模型一致——是否需要重新驗證取決於瀏覽器是否仍保有有效的管理 Token，並非本規格另外定義的新規則；返回首頁本身不主動使 Token 失效。）

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系統 MUST 在首頁、揪團列表、會員專區（含個人設定、跨團對戰紀錄）、認證相關頁面（登入/註冊/忘記密碼/重設密碼/信箱驗證）提供一致的全站導覽殼層。
- **FR-002**: 導覽殼層 MUST 顯示使用者目前是訪客還是已登入會員；已登入時 MUST 提供會員身分入口與登出入口，未登入時 MUST 提供登入與註冊入口。
- **FR-003**: 導覽殼層在手機寬度下 MUST 以精簡方式呈現（例如可展開/收合的選單），MUST NOT 佔用過多垂直畫面空間；在平板與桌面寬度下 MAY 展開為橫向常駐導覽列。
- **FR-004**: 導覽殼層 MUST 隨時提供返回首頁的方式。
- **FR-005**: 首頁 MUST 提供以下入口：瀏覽揪團列表、建立揪團場次；訪客時 MUST 額外提供登入與註冊入口，已登入會員時 MUST 改為提供前往會員專區的入口。
- **FR-006**: 系統 MUST 提供會員登出功能；登出後 MUST 清除本機登入狀態（含既有的 access/refresh token），並 MUST 將畫面導向首頁或登入頁。
- **FR-007**: 會員專區之間（會員首頁、個人設定、跨團對戰紀錄）MUST 可透過導覽殼層直接互相切換，MUST NOT 要求使用者必須先返回會員首頁才能前往其他會員頁面。
- **FR-008**: 團管理頁 MUST 提供返回首頁的導覽方式；此返回動作 MUST NOT 繞過或弱化既有的組團編號 + 管理 PIN 碼驗證機制——重新進入該團管理頁時，驗證規則 MUST 與既有規格（001-create-manage-group）完全一致。
- **FR-009**: 團內成員視圖（005-member-view 已建立之賽程/戰績/對戰紀錄/退出組團底部導覽）MUST NOT 套用本規格新增的全站導覽殼層，維持既有獨立設計，避免同一畫面出現兩層導覽。
- **FR-010**: 計分板、單一場地控制板、全部場地控制板、加入連結預覽等透過 QR Code 或深連結開啟的頁面 MUST NOT 套用全站導覽殼層，維持既有的精簡呈現。
- **FR-011**: 全站導覽殼層之視覺呈現 MUST 沿用既有規格（008-sport-minimalist-ui）已定案的運動簡約風視覺語言與觸控尺寸標準（最小 44×44 可點擊區域），MUST NOT 引入不一致的視覺風格。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 使用者從首頁出發，在不需要輸入網址的情況下，可抵達揪團列表、建立揪團頁面，以及（依登入狀態）登入/註冊頁面或會員專區。
- **SC-002**: 已登入會員從會員專區任一頁面開始，最多 2 次點擊即可完成登出。
- **SC-003**: 找 5 位以上未曾使用過本系統的受測者，於手機寬度下操作導覽殼層的展開/收合與頁面切換，90% 以上可在無人協助的情況下獨立完成。
- **SC-004**: 計分板、控制板等深連結頁面之可視內容區域，不因本次導覽規劃而縮小或增加額外的畫面元素。

## Assumptions

- 本規格純粹新增/調整導覽殼層之呈現與頁面間的跳轉連結，不改變任何既有頁面的核心業務邏輯、API 合約或資料模型。
- 響應式斷點沿用 008-sport-minimalist-ui 已定案之 768px（平板）、1024px（平板橫向/桌面）。
- 團管理頁「返回首頁」不等於主動使該團的管理 Token 失效；Token 的有效期與失效規則沿用既有規格（001-create-manage-group），本規格不另外定義。
- 團內成員視圖（group-member-view）之底部導覽列維持 005/008 規格的既有設計，本規格僅負責其餘頁面（首頁、揪團列表、會員專區、認證頁面、團管理頁）的導覽規劃。
- 全站導覽殼層之具體元件形式（例如漢堡選單 vs. 抽屜選單、頁首固定 vs. 隨捲動隱藏）留待 `/speckit-plan` 決定，不影響本規格定義的可觀察行為。
