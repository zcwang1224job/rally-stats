# Feature Specification: 多活動支援與比賽類型外掛基礎（Sport Type Plugin Foundation）

**Feature Branch**: `feature/sport-type-plugin-foundation`

**Created**: 2026-09-24

**Status**: Draft

**Input**: User description: "讓 Rally Stats 支援任何以回合或場次分勝負的活動，並建立可擴充的比賽類型外掛架構。新增活動目錄（sports 資料表，內建羽球、桌球、匹克球、網球搶十、撞球、飛鏢、桌遊、電競、其他，會員可自訂活動：選類型＋填參數）。每種活動由「比賽類型外掛」定義規則、可記錄的事件、統計指標與頁面呈現；本期實作三種類型：隔網回合制（承接現有羽球全部功能，行為與測試零變更）、局數制（每局只有勝負、先贏 N 局、可選局內比分）、通用（只有比分與勝負）。通用參數：每隊人數（本期 1 或 2）、達標或手動結束、達標分／領先分／上限（可空）、手動結束可平手、加分級距、場地與分數名詞。比賽紀錄採「薄脊椎、厚外掛表」：現有 score_events 一般化為 match_events 脊椎（順序、種類、時間、操作者、可選分數變化），每個類型外掛用自己的型別化資料表存細節並外鍵到脊椎；羽球既有發球與落點表原地改由隔網回合制外掛擁有，不遷移；核心不得直接查詢外掛表。儀表板與比賽詳細頁改為伺服器回傳區塊清單（manifest），前端依類型外掛註冊的元件渲染，未知區塊有通用退路；不同類型的儀表板與詳細頁內容各自不同（局數制顯示逐局清單與局勝率，通用顯示比分走勢），跨團統計依類型分頁籤不混算。控制板依類型切換（+1/−1 與發球、逐局勝負、+N）。開團第一步選活動，開團後不可改；match_mode 改為 team_size；既有資料回填羽球。開團列表與我的團可依活動篩選，分享圖卡帶活動名。中英文雙語。範圍外：每隊 3 人以上、計分累計制與打席制類型、每場超過 2 隊、局盤制、非羽球的發球與落點模組。"

> 註：本規格是 `docs/multi-sport-plan.md`（本機規劃文件，v3.1）第 0 期＋第 1 期的正式化。規劃文件中的架構草圖（脊椎表、外掛表、區塊清單）屬於實作方向，留給 `/speckit-plan` 定案；本規格只描述使用者與維護者可觀察的行為與約束。

## 背景：為什麼要做

Rally Stats 目前是羽球專用：計分規則、發球站位、落點球場、單雙打人數、文案，全都以羽球為唯一前提，連「這個團是什麼運動」都沒有紀錄。但揪團、排點、即時計分、排行榜、歷史戰績這套骨架，對任何「以回合或場次分勝負」的活動都成立：桌球、匹克球、撞球、飛鏢、桌遊、電競……都是「一群人到場、分隊輪流上場、一場一場記結果」。

若只是把「羽球」改成參數，能開團計分，但每種活動的儀表板與比賽詳細頁會千篇一律（撞球不需要 deuce 勝率，桌遊不需要落點圖，卻沒地方放「逐局清單」）。因此本功能同時做兩件事：

1. **對使用者**：開團第一步選活動，之後計分方式、控制板、計分板、詳細頁、儀表板都是該活動該有的樣子；活動目錄不夠用時可以自訂。
2. **對維護者**：建立「比賽類型外掛」架構，讓日後新增一種比賽類型、或替既有類型加一個統計功能，都是「加一個模組」，不用修改核心。羽球是第一個搬進外掛的類型，搬完後行為與既有測試必須零變更，以此證明架構可行。

## Clarifications

### Session 2026-09-24（規劃階段已定案，記錄於此以免重問）

- Q: 比賽紀錄要用單一通用事件表，還是各類型自己維護資料表？ → A: 各類型外掛擁有自己的型別化資料表；核心只保留一條很薄的「事件脊椎」提供全域順序、時間、操作者與可選的分數變化。非得分事件（例如換局、發球）也在脊椎上占一個序號。
- Q: 羽球、桌球、匹克球、網球是否共用一個「隔網回合制」類型？ → A: 是；差異靠參數與功能模組開關（本期非羽球活動的發球與落點模組關閉）。
- Q: 自訂活動能自訂到什麼程度？ → A: 只能選一種既有類型並填該類型的參數；不能自訂事件或統計。
- Q: 第一批類型？ → A: 隔網回合制（承接羽球）、局數制、通用三種；計分累計制（籃球）與打席制（棒球）留待下一期與多人隊伍一起做。
- Q: 我的團跨團統計遇到不同類型怎麼呈現？ → A: 不做跨類型合併（分頁方式於下方 clarify 修訂為依活動）。
- Q: 各類型的前端程式是否獨立載入？ → A: 是；沒有用到該類型的使用者不需要下載其程式。

### Session 2026-09-24

- Q: 儀表板與「我的團」跨團統計的分頁籤，依「比賽類型」還是依「活動」？ → A: 依活動分頁籤（羽球、桌球、撞球、每個自訂活動各一頁）；各頁的指標與區塊仍由該活動所屬的類型決定。
- Q: 非隔網回合制的活動要不要有單場比賽分享圖卡？ → A: 所有類型都有單場卡，共用版面（活動名、比分或局數、勝方、雙方成員）；亮點區塊由該類型提供，本期局數制與通用不提供亮點則省略該區塊。
- Q: 「核心不得依賴特定活動、新增類型不改核心」如何驗收？ → A: plan 階段明列核心與類型模組的目錄邊界，並加入自動化檢查（核心不得引用任何類型模組、類型模組不得互相引用、每種類型宣告的區塊都有對應呈現或通用退路），納入 CI 必要關卡。
- Q: 開團列表與我的團的活動篩選器如何處理別人的自訂活動與訪客的「其他」團？ → A: 篩選器列出內建活動各一項，再加一個「自訂／其他」項涵蓋所有非內建的團；「我的團」額外列出會員自己的自訂活動各一項。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 既有羽球團一切如舊 (Priority: P1)

我是現有的羽球團管理員或球友。系統升級後，我開團、加入、排點、用控制板計分（含發球站位與落點）、看計分板、看排行榜、看比賽詳細頁與儀表板、產生分享圖卡，每一個畫面、每一個數字都跟升級前一模一樣。我甚至不會發現系統現在支援別的活動，除非我去開新團時看到多了「選活動」這一步（預設仍是羽球）。

**Why this priority**：這是本功能的安全網。把羽球從核心搬進外掛是整個架構的成敗關鍵；搬家過程若改變任何既有行為，後續每一種新類型都建立在不可信的地基上。所有既有自動化測試 MUST 在不修改斷言的前提下全數通過（允許純結構性的搬移，例如 import 路徑）。

**Independent Test**：對升級前後的同一份資料，走完「開羽球團 → 加入 → 排點 → 計分（含發球與落點）→ 結束 → 排行榜 → 詳細頁 → 儀表板 → 分享圖卡」，逐畫面比對；並執行升級前既有的全部自動化測試。

**Acceptance Scenarios**:

1. **Given** 升級前已存在的團（進行中或已解散）、比賽、發球紀錄、落點紀錄, **When** 系統升級完成, **Then** 這些團 MUST 全部被視為「羽球」活動，且其排行榜、對戰紀錄、詳細頁、儀表板、我的團統計的每一個數值 MUST 與升級前完全一致。
2. **Given** 使用者開新團並在「選活動」步驟保持預設, **When** 送出, **Then** 建立的 MUST 是羽球團，後續所有畫面與行為 MUST 與升級前的羽球團一致（含預設團名「{暱稱}的羽球團」與預設場地「球場一」）。
3. **Given** 升級前的全部自動化測試, **When** 在升級後的程式上執行, **Then** MUST 全數通過，且測試檔的斷言內容 MUST NOT 被修改（僅允許搬移路徑等結構性調整）。
4. **Given** 羽球團的控制板, **When** 計分員操作 +1／−1、發球站位、落點, **Then** 計分板、全部場地控制板、成員視圖 MUST 如升級前即時同步。

### User Story 2 - 開團時選活動，用該活動的規則計分 (Priority: P1)

我想揪一場撞球搶五。開團第一步我從活動目錄選「撞球」，系統自動帶入撞球的預設：每隊 1 人、先贏 5 局、局數制。我可以調整先贏幾局。開團後，控制板變成「這一局 A 勝／B 勝」，計分板顯示雙方局數，到 5 局就自動結束。換成桌球，我選「桌球」，預設 11 分、領先 2 分、無上限、單打或雙打；控制板是 +1／−1，但不會出現羽球的發球站位與落點。

**Why this priority**：這是使用者能感知的核心價值：終於能用同一套系統揪不同活動。沒有它，架構工作只是重構。

**Independent Test**：從開團表單選「撞球」與「桌球」各開一團，各完成一場比賽，驗證預設參數、控制板樣式、結束條件、排行榜勝負。

**Acceptance Scenarios**:

1. **Given** 使用者進入開團表單, **When** 表單載入, **Then** 第一步 MUST 是選活動，目錄 MUST 至少包含：羽球、桌球、匹克球、網球（搶十）、撞球、飛鏢、桌遊、電競、其他；每個活動 MUST 顯示中英文名稱與圖示。
2. **Given** 使用者選了「撞球」, **When** 進入下一步, **Then** 表單 MUST 自動帶入撞球的預設參數（每隊 1 人、局數制、先贏 5 局、不記局內比分），且只顯示該活動允許的每隊人數選項。
3. **Given** 使用者選了「桌球」並開團完成, **When** 計分員開啟控制板, **Then** 控制板 MUST 提供 +1／−1，MUST NOT 顯示發球站位與落點輸入；計分板 MUST NOT 顯示發球資訊。
4. **Given** 桌球團採預設 11 分、領先 2 分、無上限, **When** 比分達 10:10 之後持續交替得分到 15:13, **Then** 系統 MUST 在 15:13 判定結束（無上限時只看領先 2 分）。
5. **Given** 撞球團先贏 5 局, **When** 計分員記到某隊第 5 局勝, **Then** 比賽 MUST 自動結束並記錄勝方；排行榜 MUST 以「場」計勝負（一場＝一次先贏 N 局的對戰），不以局計。
6. **Given** 團已建立, **When** 管理員嘗試變更活動, **Then** 系統 MUST 拒絕並說明活動在開團後不可更改；其他團設定（人數上限、排程機制、達標分等）仍可依既有規則修改。
7. **Given** 任一非羽球活動的團, **When** 使用者查看團名預設值與場地預設名, **Then** MUST 依該活動的名詞（例如「{暱稱}的撞球團」「球桌一」）。

### User Story 3 - 局數制活動有自己的計分板、詳細頁與儀表板 (Priority: P1)

我打完一場撞球搶五。點進比賽詳細頁，看到的不是羽球的比分走勢與落點圖，而是「逐局清單」：第 1 局 A 勝、第 2 局 B 勝……每局若有記局內比分也一併顯示。我的儀表板在「撞球」頁籤下顯示局勝率、先贏第一局後的勝率、平均決勝局數，而不是發球得分率或 deuce 勝率。

**Why this priority**：這是「不同類型的頁面各自不同」的第一個實例，證明頁面可以依類型組裝，而不是同一頁隱藏幾格。

**Independent Test**：用撞球團完成 2 場比賽後，開詳細頁與儀表板，驗證區塊內容與數值。

**Acceptance Scenarios**:

1. **Given** 一場已完成的局數制比賽, **When** 使用者開啟比賽詳細頁, **Then** MUST 顯示逐局清單（局序、勝方、局內比分若有），MUST NOT 顯示隔網回合制專屬區塊（發球、落點、deuce、match point）。
2. **Given** 一場進行中的局數制比賽, **When** 觀眾開啟計分板, **Then** MUST 顯示雙方局數、目前第幾局、先贏幾局；若開團時啟用局內比分，MUST 一併顯示本局比分。
3. **Given** 開團時啟用「記局內比分」, **When** 計分員在控制板記錄本局, **Then** MUST 可輸入本局雙方比分再標記勝方；未啟用時只需標記勝方。
4. **Given** 計分員誤記一局, **When** 按「復原上一局」, **Then** 該局紀錄 MUST 被移除、局數回退，且計分板即時同步。
5. **Given** 會員在撞球團完成至少 1 場比賽, **When** 開啟儀表板並切到「撞球」頁籤, **Then** MUST 顯示局數制的指標（至少：場勝率、局勝率、先贏第一局後的場勝率、平均局數），MUST NOT 混入其他類型團的數據。
6. **Given** 會員同時有羽球團、桌球團與撞球團的紀錄, **When** 開啟我的團統計, **Then** MUST 依活動分頁籤（羽球、桌球、撞球各一頁），各頁籤內的數值 MUST 只來自該活動的團；羽球頁 MUST 與升級前的儀表板一致。

### User Story 4 - 自訂活動 (Priority: P2)

我們社團玩的是目錄裡沒有的「躲避球對抗」。我登入後在開團第一步選「自訂」，取名、選一種比賽類型（通用），填每隊人數 2、手動結束、可平手、加分級距 1。之後這個活動出現在我的目錄裡，下次開團可直接選。

**Why this priority**：目錄永遠不完整；自訂活動讓「任何回合制活動」的承諾成立，但它建立在 US2 之上。

**Independent Test**：以會員身分建立一個自訂活動並用它開團、完成一場，再以第二次開團驗證可重用。

**Acceptance Scenarios**:

1. **Given** 已驗證的會員在開團第一步, **When** 選「自訂活動」, **Then** MUST 可輸入活動名稱（中文或英文，1–20 字）、選一種比賽類型（本期：隔網回合制、局數制、通用）、並填該類型的參數；系統 MUST 依類型驗證參數範圍。
2. **Given** 會員建立了自訂活動, **When** 下次開團, **Then** 該活動 MUST 出現在其目錄的「我的自訂」區，且只有建立者看得到。
3. **Given** 未登入的訪客開團, **When** 到選活動步驟, **Then** MUST 可選內建活動與「其他」（通用類型、當場填參數、不保存為可重用活動）；MUST NOT 提供保存自訂活動。
4. **Given** 自訂活動已被某個團使用, **When** 建立者刪除該活動, **Then** 既有團 MUST 不受影響（仍顯示原活動名稱），該活動只從建立者的目錄中移除。

### User Story 5 - 通用類型：只有比分與勝負 (Priority: P2)

我們打的是沒有標準規則的趣味賽：每隊 2 人，計分員手動加分（有時一次加 2 分），時間到宣布結束，分高者勝，同分算平手。系統只需要幫我記比分、宣布結果、算排行榜，不需要任何專屬統計。

**Why this priority**：通用類型是所有未歸類活動的退路，也是「其他」與訪客開團的預設；它的價值在覆蓋面而非深度。

**Independent Test**：用「其他」開團，設定加分級距 1 與 2、手動結束、允許平手，完成一場平手與一場勝負，驗證排行榜。

**Acceptance Scenarios**:

1. **Given** 通用類型團設定加分級距為 1 與 2, **When** 計分員開控制板, **Then** MUST 顯示 +1 與 +2 按鈕（各隊）及復原；不顯示發球或局數。
2. **Given** 手動結束且允許平手, **When** 比分 7:7 時計分員按「結束比賽」, **Then** 系統 MUST 記錄平手，排行榜 MUST 顯示該場為平手（勝—敗—平），名次仍依勝場。
3. **Given** 手動結束且不允許平手, **When** 同分時按「結束比賽」, **Then** 系統 MUST 拒絕並提示需先分出勝負。
4. **Given** 通用類型的比賽詳細頁, **When** 使用者開啟, **Then** MUST 顯示比分走勢與逐次加分時間軸（通用區塊），MUST NOT 顯示任何類型專屬區塊。

### User Story 6 - 依活動找團、看戰績、分享 (Priority: P2)

我是會員，想找附近有沒有桌球團。開團列表可以依活動篩選；「我的團」也能依活動篩選；每張團卡與分享圖卡都標示活動名稱，貼到群組時別人一眼就知道這是哪種活動的戰績。

**Why this priority**：讓多活動在瀏覽與傳播層面可辨識；不影響計分核心。

**Independent Test**：建立羽球、桌球、撞球各一團，在開團列表與我的團分別篩選，並產生分享圖卡確認活動名稱。

**Acceptance Scenarios**:

1. **Given** 開團列表有多種活動的團, **When** 使用者選活動篩選, **Then** 篩選選項 MUST 為內建活動各一項＋「自訂／其他」一項；選某內建活動時列表 MUST 只顯示該活動的團，選「自訂／其他」時 MUST 顯示所有非內建活動的團；每張團卡 MUST 顯示該團記錄的活動名稱與圖示。
2. **Given** 會員的我的團列表，且會員有一個自訂活動「躲避球對抗」, **When** 依活動篩選, **Then** 選項 MUST 包含內建活動、「自訂／其他」與「躲避球對抗」；選「躲避球對抗」時 MUST 只列使用該自訂活動的團；既有其他篩選（身分、狀態、日期、場數）MUST 可同時生效。
3. **Given** 任一團或比賽的分享圖卡, **When** 產生, **Then** 圖卡 MUST 標示活動名稱；羽球圖卡除新增活動名稱外，版面與內容 MUST 與升級前一致。
4. **Given** 一場已完成的撞球（局數制）比賽, **When** 會員產生單場比賽圖卡, **Then** 圖卡 MUST 顯示活動名、雙方局數、勝方與雙方成員，MUST NOT 出現空白的亮點區塊或隔網回合制的走勢圖。

### User Story 7 - 維護者新增一種比賽類型不必改核心 (Priority: P2)

我是本專案的維護者。下一期要加「計分累計制」（籃球）。我只需要新增一個類型模組（規則、可記錄的事件、專屬紀錄的儲存、統計指標、儀表板與詳細頁的區塊、控制板與計分板的呈現），在目錄加一列「籃球」，補上文案，就能開籃球團；不需要修改開團流程、排點、即時同步、排行榜、我的團、分享圖卡的程式，也不需要修改任何既有類型。

**Why this priority**：這是「可擴充」的可驗證定義。放在 P2 是因為它靠 US1–US3 的實作自然達成，但 MUST 有明確的驗收方式，否則會在實作中被妥協掉。

**Independent Test**：以「通用」或「局數制」類型的實作為樣本，列出其觸及的檔案；驗證其中沒有任何檔案屬於核心（開團、排點、即時同步、排行榜、我的團、分享）或其他類型。

**Acceptance Scenarios**:

1. **Given** 新增一種比賽類型, **When** 檢視其改動範圍, **Then** MUST 只包含：該類型自己的模組（前後端）、活動目錄資料、文案；MUST NOT 修改核心流程或其他類型的程式。
2. **Given** 任一類型回傳的頁面區塊清單, **When** 前端遇到它不認識的區塊種類, **Then** MUST 以通用方式呈現（例如通用數值表格）而不是空白或錯誤。
3. **Given** 替既有類型新增一個統計功能（例如局數制加「連勝局數」）, **When** 檢視改動, **Then** MUST 只在該類型模組內新增紀錄、指標與區塊，MUST NOT 修改核心。
4. **Given** 核心程式, **When** 檢查, **Then** MUST NOT 依特定活動或類型名稱做分支判斷（例如「如果是羽球就……」）；所有差異 MUST 由活動參數與類型模組提供。
5. **Given** 有人在核心程式中引用了某個類型模組，或讓兩個類型模組互相引用, **When** 執行品質關卡, **Then** 自動化檢查 MUST 失敗並阻擋合併。

### Edge Cases

- 開團時選了活動但參數超出該類型允許範圍（例如先贏 0 局、加分級距為空、達標分小於領先分）：MUST 在送出前即時提示並拒絕。
- 達標分設定為「上限可空」且領先 2 分：比分可無限交替，系統 MUST 正確持續判定，不因超過任何預設上限而異常。
- 局數制啟用局內比分但計分員只標勝方未填比分：MUST 允許（局內比分為選填）。
- 局數制「復原上一局」在第 0 局：MUST 無動作並提示。
- 通用類型手動結束、允許平手、比分 0:0 按結束：MUST 記錄平手（0:0 平手是合法結果）。
- 訪客用「其他」開團未保存活動：該團的活動名稱 MUST 顯示為使用者當場輸入的名稱，不得顯示「其他」。
- 自訂活動名稱與內建活動同名：MUST 允許（目錄分區顯示），但同一會員不得建立兩個同名自訂活動。
- 儀表板頁籤的歸類：內建活動與已保存的自訂活動以活動本身為準；訪客用「其他」開團（未保存）的團，以團記錄的活動名稱歸入同名頁籤，並在頁籤標示為「其他」類的活動。
- 升級前已解散的羽球團：我的團最終排名、對戰紀錄與詳細頁 MUST 與升級前一致。
- 舊資料的單打／雙打設定：MUST 對應為每隊 1 人／2 人，且排程機制的限制（固定搭檔、個人混搭僅限雙打）MUST 維持。
- 隔網回合制的非羽球活動（桌球、匹克球、網球搶十）本期關閉發球與落點：儀表板 MUST 不顯示發球／落點／結束型態指標，詳細頁 MUST 不顯示落點與發球區塊，但比分走勢、逐點時間軸、領先／落後勝率、endgame／deuce／match point 等只依比分即可計算的指標 MUST 照常提供。
- 兩種語言：活動名稱、名詞（場地／分數／成員）、類型專屬區塊標題 MUST 都有中英文；自訂活動名稱以使用者輸入為準，不翻譯。
- 前端載入某類型模組失敗（例如網路中斷）：頁面殼 MUST 顯示可重試的錯誤，不得整頁崩潰。

## Requirements *(mandatory)*

### Functional Requirements

**活動目錄與自訂活動**

- **FR-001**: 系統 MUST 提供活動目錄，內建至少：羽球、桌球、匹克球、網球（搶十）、撞球、飛鏢、桌遊、電競、其他；每個內建活動 MUST 有中英文名稱、圖示、所屬比賽類型、預設參數、允許的每隊人數選項。
- **FR-002**: 每個活動 MUST 歸屬於恰好一種比賽類型；本期類型為隔網回合制、局數制、通用。內建活動的類型對應：羽球／桌球／匹克球／網球（搶十）→隔網回合制；撞球／飛鏢／桌遊／電競→局數制；其他→通用。
- **FR-003**: 已驗證會員 MUST 能建立自訂活動：名稱（1–20 字）、比賽類型、該類型的參數；自訂活動只對建立者可見與可用，且可被建立者刪除；刪除 MUST NOT 影響已使用該活動的團。
- **FR-004**: 未登入的開團者 MUST 只能選內建活動或「其他」（通用類型、當場填參數、不保存）。
- **FR-005**: 內建活動目錄本期由資料初始化提供，不提供使用者介面維護（管理後台另案）。

**開團與通用參數**

- **FR-006**: 開團流程的第一步 MUST 是選活動；預設選項 MUST 為羽球。
- **FR-007**: 每個團 MUST 記錄其活動與比賽類型，且開團後 MUST NOT 允許變更活動；系統 MUST 拒絕變更要求並說明原因。
- **FR-008**: 所有類型共用的通用參數 MUST 包含：每隊人數（本期允許 1 或 2）、結束方式（達標或手動）、達標分、需領先分數、上限（可為空）、手動結束是否允許平手、加分級距（一組正整數）、場地名詞、分數名詞、成員名詞。各類型 MUST 可宣告額外的專屬參數。
- **FR-009**: 選定活動後，表單 MUST 自動帶入該活動的預設參數，且只顯示該活動允許的每隊人數與該類型適用的參數；使用者可在允許範圍內修改。
- **FR-010**: 每隊人數 MUST 取代既有的單打／雙打設定；既有資料 MUST 對應為 1／2；既有「固定搭檔、個人混搭僅限雙打」與「最少人數＝2×每隊人數」的規則 MUST 維持。
- **FR-011**: 預設團名後綴與預設場地名稱 MUST 依活動決定（例如「的羽球團」「球場一」、「的撞球團」「球桌一」），並可由系統共用設定調整。
- **FR-012**: 開團表單 MUST 對參數做即時驗證：達標分 ≥ 領先分、上限（若有）≥ 達標分、加分級距至少一個正整數、先贏局數 ≥ 1。

**計分、事件與比賽結束**

- **FR-013**: 每場比賽 MUST 有一條依發生順序排列的事件紀錄，每筆至少含順序、種類、時間、操作者，得分事件另含隊別與分數變化；非得分事件（例如換局）MUST 也在同一順序中。
- **FR-014**: 每種比賽類型 MUST 宣告它接受的事件種類；系統 MUST 拒絕該類型未宣告的事件。
- **FR-015**: 各類型專屬的紀錄細節（例如羽球的發球與落點、局數制的局內比分）MUST 由該類型自行保存，並與事件順序關聯；核心功能（時間軸、走勢、分享、復原、即時同步）MUST 透過類型提供的介面取得，MUST NOT 直接讀取類型專屬紀錄。
- **FR-016**: 達標模式的勝負判定 MUST 依「達標分且領先指定分數，或達到上限（若有）」；上限為空時 MUST 只看領先分數。
- **FR-017**: 手動模式 MUST 由計分員宣告結束，分高者勝；允許平手時同分記平手，不允許時 MUST 拒絕結束。
- **FR-018**: 控制板 MUST 依類型呈現對應操作：隔網回合制為 +1／−1（羽球另含發球站位與落點）、局數制為標記本局勝方（可選局內比分）與復原上一局、通用為依加分級距的 +N 與復原。
- **FR-019**: 計分板 MUST 依類型呈現對應內容：隔網回合制顯示比分（羽球另含發球資訊）、局數制顯示局數與本局狀態、通用顯示比分；所有類型 MUST 維持既有的即時同步、免登入開啟、大字體與行動裝置支援。
- **FR-020**: 排行榜、最終排名、我的團場數、參賽歷史 MUST 對所有類型以「場」為單位計算勝／敗／平，並列規則沿用既有。

**頁面呈現：儀表板與比賽詳細頁**

- **FR-021**: 比賽詳細頁與會員儀表板的內容 MUST 由該比賽類型決定「有哪些區塊、各區塊的資料」，前端依區塊種類選擇對應的呈現方式；遇到不認識的區塊種類 MUST 以通用方式呈現。
- **FR-022**: 隔網回合制（羽球）的詳細頁與儀表板 MUST 與升級前完全一致（區塊、順序、數值、互動）。
- **FR-023**: 局數制的詳細頁 MUST 至少包含逐局清單（局序、勝方、局內比分若有）與局數走勢；儀表板 MUST 至少包含場勝率、局勝率、先贏第一局後的場勝率、平均局數、對手分析。
- **FR-024**: 通用類型的詳細頁 MUST 至少包含比分走勢與逐次加分時間軸；儀表板 MUST 至少包含場勝率、勝敗平場數、對手分析。
- **FR-025**: 隔網回合制的非羽球活動 MUST 提供只依比分即可計算的指標（得失分、領先／落後／平手時勝率、endgame、deuce、match point 轉換），MUST NOT 顯示發球、落點、結束型態指標。
- **FR-026**: 我的團跨團統計與會員儀表板 MUST 依活動分頁籤（內建活動、每個自訂活動各一頁），各頁籤只彙整該活動的團，指標與區塊由該活動所屬的類型決定；MUST NOT 跨活動合併任何數值。會員只有一種活動的紀錄時 MUST 直接顯示該活動的內容，不顯示頁籤列。
- **FR-027**: 團內基準比較與對手分析等既有的類型無關功能 MUST 對所有類型可用。

**瀏覽、篩選與分享**

- **FR-028**: 開團列表與我的團 MUST 可依活動篩選，並在每張團卡顯示活動名稱與圖示；篩選 MUST 可與既有篩選並用。篩選選項為：每個內建活動各一項，加上「自訂／其他」一項（涵蓋所有非內建活動的團）；「我的團」MUST 額外列出會員自己的自訂活動各一項。團卡上的活動名稱 MUST 顯示該團實際記錄的名稱（自訂或「其他」團顯示使用者輸入的名稱）。
- **FR-029**: 團分享圖卡與單場比賽分享圖卡 MUST 對所有類型可用並標示活動名稱。單場卡共用版面（活動名、比分或局數、勝方、雙方成員）；亮點區塊由該比賽類型提供，類型未提供亮點時 MUST 省略該區塊而不留白。羽球圖卡除新增活動名稱外 MUST 與升級前一致（含既有亮點）。

**相容性與遷移**

- **FR-030**: 升級時既有的團、比賽與所有紀錄 MUST 自動歸為羽球，且所有既有畫面的數值 MUST 與升級前一致。
- **FR-031**: 升級前的全部自動化測試 MUST 在不修改斷言的前提下通過。
- **FR-032**: 羽球既有的發球與落點紀錄 MUST 原地保留，不做資料搬移。

**可擴充性（維護者可驗證的約束）**

- **FR-033**: 新增一種比賽類型 MUST 只需要：新增該類型模組（規則、事件、專屬紀錄、統計、頁面區塊、控制板與計分板呈現）、活動目錄資料、文案；MUST NOT 修改核心流程或其他類型。
- **FR-034**: 核心程式 MUST NOT 依特定活動或類型名稱做分支；所有差異 MUST 來自活動參數與類型模組。
- **FR-034a**: 核心與各類型模組的邊界 MUST 在實作計畫中以明確的目錄清單定義，並由自動化檢查強制：核心 MUST NOT 引用任何類型模組、類型模組之間 MUST NOT 互相引用；此檢查 MUST 納入既有的 lint／型別檢查關卡，失敗即阻擋合併。
- **FR-035**: 每種類型的前端程式 MUST 可獨立載入；未使用該類型的使用者 MUST NOT 需要下載其程式。
- **FR-036**: 每種類型 MUST 附帶其規則（事件→狀態、勝負判定）、統計指標、頁面區塊的自動化測試；核心 MUST 有契約測試驗證「每種類型宣告的區塊種類都有對應呈現或通用退路」。

**語言與無障礙**

- **FR-037**: 所有新增文案（活動名稱、名詞、參數說明、類型專屬區塊標題與指標名稱、錯誤訊息）MUST 提供中文與英文。
- **FR-038**: 新增的控制板操作與區塊 MUST 符合既有的行動裝置優先與無障礙要求（觸控目標大小、鍵盤可操作、狀態不只靠顏色）。

### Key Entities

- **活動（Sport）**：使用者選擇的對象，例如羽球、撞球、自訂的「躲避球對抗」。屬性：名稱（雙語或使用者輸入）、圖示、所屬比賽類型、預設參數、允許的每隊人數、是否內建、建立者（自訂時）。
- **比賽類型（Sport Type）**：定義一類活動的規則、可記錄的事件、統計指標與頁面區塊；本期三種。由維護者以模組提供，不是使用者資料。
- **團的活動設定**：團所選的活動、比賽類型、通用參數與類型專屬參數；開團後活動不可變。
- **比賽（Match）**：一次對戰；快照開團時的活動與參數；結果為 A 勝／B 勝／平手。
- **比賽事件（脊椎）**：一場比賽中依序發生的事，含順序、種類、時間、操作者、可選的隊別與分數變化。
- **類型專屬紀錄**：附屬於某筆事件的細節，由該類型自行定義與保存（羽球發球與落點、局數制的局內比分）。
- **頁面區塊清單**：某場比賽或某會員儀表板由類型產出的「區塊種類＋資料」序列，前端據此組頁。
- **指標目錄**：每種類型宣告的儀表板指標（名稱、計算方式、方向）；核心的聚合與基準比較只依目錄運作。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 升級前既有的全部自動化測試在升級後 100% 通過，測試斷言零修改。
- **SC-002**: 對同一份升級前資料，羽球團的排行榜、詳細頁、儀表板、分享圖卡逐項比對零差異。
- **SC-003**: 使用者從開團表單選「撞球」到完成一場搶五比賽並看到排行榜，全程不需查看說明，在 3 分鐘內完成。
- **SC-004**: 撞球（局數制）、其他（通用）、桌球（隔網回合制、無發球落點）三種團各自的詳細頁與儀表板，區塊內容彼此不同且與本規格 FR-022～FR-025 相符。
- **SC-005**: 以「局數制」與「通用」兩個類型的實作為樣本，各自的改動檔案清單中 0 個檔案屬於核心流程或其他類型；且邊界自動化檢查在 CI 中啟用並通過。
- **SC-006**: 未使用局數制的使用者載入羽球頁面時，不會下載局數制的前端程式。
- **SC-007**: 所有新增文案在中英文各有對應，缺漏為 0。
- **SC-008**: 新增類型的前端遇到未知區塊種類時 100% 以通用方式呈現，無空白或錯誤。

## Assumptions

- 本期每隊人數只開放 1 或 2；每場固定 2 隊。多人隊伍與更多類型（計分累計制、打席制）於下一期。
- 「其他」活動為通用類型；訪客開團的「其他」不保存為可重用活動。自訂活動需已驗證會員。
- 局數制本期的「復原」以局為單位（復原上一局）；隔網回合制與通用的復原以一次加分為單位，沿用既有 −1 語意。
- 隔網回合制的非羽球活動本期關閉發球追蹤與落點；桌球每 2 分換發等專屬發球規則留待後續模組。
- 內建活動的預設參數（本期）：羽球 21／2／30、每隊 1 或 2；桌球 11／2／無上限、每隊 1 或 2；匹克球 11／2／無上限、每隊 1 或 2；網球（搶十）10／2／無上限、每隊 1 或 2；撞球先贏 5 局、每隊 1；飛鏢先贏 3 局、每隊 1；桌遊先贏 1 局、每隊 1 或 2；電競先贏 2 局、每隊 1 或 2；其他：手動結束、允許平手、加分級距 1、每隊 1 或 2。實際數值可在 plan 階段調整，不影響規格。
- 既有共用設定（預設團名後綴、預設場地名）改為依活動查表；管理後台另案。
- 專案憲章的定位需同步由「羽球揪團與即時計分系統」修訂為「回合制對戰活動揪團與即時計分系統」，並新增「核心不得寫死特定活動」與「新增類型必附測試」原則；於 plan 階段透過 `/speckit-constitution` 完成。
- 中英文雙語沿用既有翻譯機制；自訂活動名稱以使用者輸入為準。

## Out of Scope（留待後續）

- 每隊 3 人以上、隊伍成員表、固定隊伍模式。
- 計分累計制（籃球、足球：+1/+2/+3、每節、犯規）與打席制（棒球）類型。
- 每場超過 2 隊（麻將、個人排名賽）、錦標賽淘汰／分組。
- 局盤制（幾局幾勝的上層結構、網球完整局盤）。
- 非羽球活動的發球追蹤與落點模組（桌球換發、匹克球落點、網球換發換邊）。
- 自訂事件種類或自訂統計（等同自訂類型模組）。
- 一團混打多種活動。
- 內建活動目錄的管理後台介面。
